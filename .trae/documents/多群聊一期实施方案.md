# 多群聊一期实施方案（微信同款：建群 + 邀请 + 多群收发）

## 背景

当前系统只有一个全局大群聊：`Conversation.Target=''` / `Message.ToUser=''` 表示群聊，注册即自动入群，`handleGroupChat` 广播给所有用户。用户需要微信同款的多群聊能力（选好友建群、邀请入群需确认、多群独立收发）。

已确认决策：① 邀请需被邀请人确认（复用好友申请链路模式）；② 建群/邀请选人仅限好友；③ 新群支持文字+图片+文件；④ 保留现有全局群（target='' 路径零改动，零回归）。

核心编码方案：新群会话目标 = `'g' + 群ID`（如 `g1`），存于 `Conversation.Target` 与 `Message.ToUser`（varchar(32) 容量足够）。现有 ''（全局群）/ 用户名（私聊/AI）语义不变。

## 一、数据模型（新建 `im-server/model/group.go`，参照 FriendRequest 风格）

```go
// Group 群聊信息表 im_group
ID uint primaryKey / Name string varchar(64) / OwnerID string varchar(32)
Avatar string varchar(255)（一期为空，前端默认头像）/ CreateTime time.Time

// GroupMember 群成员表 im_group_member
ID / GroupID uint / UserID string varchar(32)
复合唯一索引 idx_group_user(group_id, user_id)
Role int8（1群主 2成员，二期扩展管理员）/ JoinTime time.Time

// GroupInvite 群邀请表 im_group_invite
ID / GroupID uint / FromUser string / ToUser string
Status int8（0待处理 1已同意 2已拒绝，与 FriendRequest 对齐）
Message string varchar(255) / CreateTime time.Time
普通索引 idx_invite_to(to_user, status)
```

- 三表加入 `store/mysql.go:38` 的 AutoMigrate 列表。
- **不做 (group_id,to_user) 唯一索引**：微信允许拒绝后再次邀请。防重复改为：邀请时查同群同人 Status=0 的在途邀请则拦截；已是群成员则拦截。
- **保留字防护**（[auth.go:42](e:/SourceCodeIM/im-server/server/auth.go#L42) registerUser）：TrimSpace 校验后增加规则——用户名匹配 `^g\d+$` 拒绝注册（新增 ErrReservedUsername「该用户名不可用」，并加入 isAuthBusinessError）。存量用户不受影响（群 target 解析只查 im_group 表）。

## 二、协议设计（protocol/message.go 追加，71 起）

收发消息复用现有 1（GROUP_CHAT 文字）/34（GROUP_IMAGE）/69（GROUP_FILE），仅 `to_user='gN'`，不新增消息类型。

```
71 MsgTypeGroupCreate       上行   content JSON {name, members:["u1","u2"]}（选自好友）
72 MsgTypeGroupCreateResp   下行   建群回执 {group_id, name, members, create_time}
73 MsgTypeGroupListSync     下行   群列表全量同步 {groups:[{group_id,name,avatar,owner,member_count,members:[{username,name,role,avatar}],create_time}]}
                                   （登录推送 + 成员/信息变更时向全群推送；前端据此维护 groupMap 缓存）
74 MsgTypeGroupInvite       上行   content JSON {group_id, members:["u2"]}
75 MsgTypeGroupInviteNotice 下行   被邀请人收 {invite_id, group_id, name, from_user, from_name, member_count}
76 MsgTypeGroupInviteResp   上行   content JSON {invite_id, accept:true/false}
77 MsgTypeGroupMemberNotice 下行   成员变更通知 {group_id, action:"create"/"join", users:[...], member_count}
                                   （action=join 时同时作为邀请结果回执发给邀请人，复用一帧）
```

## 三、服务端改动（新建 `im-server/server/group.go` 归口 + 少量文件修改）

新文件 `server/group.go`：

1. `isGroupTarget(t string) bool`：`len(t)>1 && t[0]=='g'` 且查 im_group 存在（服务端以查表为准，不信前缀）。
2. `getGroupMemberIDs(groupID uint) []string`：查 im_group_member（一期直查，复合索引足够快；预留下一步 Redis 缓存位）。
3. `handleGroupCreate`：校验 name 非空/members 均为好友→建 im_group + 成员行（含群主 Role=1）→对每个成员 touchConversation(gID,"已创建群聊「name」")→逐成员 sendGroupListSync（73）。
4. `handleGroupInvite`：校验邀请人是成员→目标均非成员→在途邀请去重→写 im_group_invite(Status=0)→被邀请人在线推 75，离线记日志（登录补推兜底）。
5. `handleGroupInviteResp`（状态机，仿 friend.go:115 handleFriendRequestResp）：校验 invite 归属与 Status=0→改 Status→同意则插 im_group_member（幂等：先查）→全群推 73 + 77（含新成员）→邀请人收 77 回执（同意/拒绝文案）→新成员 touchConversation + sendGroupListSync。
6. `pushPendingGroupInvites(c)`：登录补推 Status=0 且 create_time < loginTime 的邀请（仿 friend.go:310 pushPendingRequests，防重复弹）。
7. `sendGroupListSync(username)`：查用户所在群+成员列表，推 73 到该用户全部在线连接（hub.GetAll 遍历，多端同步）。

现有文件修改：

8. [server.go:221](e:/SourceCodeIM/im-server/server/server.go#L221) 分发 switch：CallSignal 之后追加 71/74/76 三个 case。
9. handleGroupChat（[server.go:388](e:/SourceCodeIM/im-server/server/server.go#L388)）：**开头**加群分流——`msg.ToUser` 命中 isGroupTarget 时：校验发送者是成员→落库 to_user='gN'（msg_type=1 不变，FromName 昵称沿用）→按成员集合过滤在线连接定向发送（遍历成员 hub.GetAll）→在线成员逐个 touchConversation(gN, 摘要)+notifyConvUpdate→离线成员逐个 queueOffline。**原全局群路径（ToUser==''）代码不动**；@AI 唤醒分支一期仅全局群生效（gN 前缀优先分流，不进 @AI）。
10. handleHistory（[server.go:633](e:/SourceCodeIM/im-server/server/server.go#L633)）：群分支参数化——原 `to_user = ''` 改为变量 `to_user = ?`（''=全局群，'gN'=指定群），msg_type IN(1,4,5) 与 names 昵称映射逻辑不变。

## 四、前端改动（im-client/web/js/）

## 七、风险与规避

- **用户名撞 target**：保留字拦截先落地（步骤 1）；服务端 target 解析以查表为准双保险。
- **判定点遗漏**：isGroupTarget 收口 + 第 7/8 条清单逐条实测；全局群 '' 路径代码不动是最大安全垫。
- **离线入队量**：按成员入队（优于现全局群全表扫描）；getGroupMemberIDs 预留 Redis 缓存位，群规模大时启用。
- **并发同意/重复入群**：插成员前重查幂等；Status=0 才可响应。
- **移动端**：APP 共用 web 资源自动覆盖，编译 APK 后生效。

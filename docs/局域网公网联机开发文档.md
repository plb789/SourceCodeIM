# 一、背景与目标

## 1.1 背景

项目已上架自研游戏（游戏中心 / 游戏库），用户诉求是：**让原本只能在物理局域网内联机的游戏，可以跨公网对其他玩家联机**，体验对齐 Steam 的「局域网联机跨公网」。

Steam 侧的做法是 `ISteamNetworkingSockets`（P2P 打洞优先 + SDR 中继兜底）+ `Steam Lobby`（房间/匹配）。本项目**不需要引入任何新中间件**——所需三大底座在仓库里已经全部具备，且与通话/会议/文件直传/远程协助共用同一条链路：

| 已有能力 | 位置 | 说明 |
|---------|------|------|
| 内置 TURN/STUN 中继 | `im-server/server/turn.go` | pion/turn v4 与 im-server 同进程，`config.yaml` `turn:` 节配置，STUN 与 TURN 同端口 3478，中继端口段 `min_port~max_port` |
| 中继对外地址与线路跟随 | `turn.go`（阶段一百四十二 / 一百四十五） | `public_ip` 支持 IP 或域名；域名场景驻留巡检 goroutine，上游剔除线路自动重建 TURN，零重启切换 |
| 信令下发 ICE 配置 | `turn.go TurnICEServers()` / `call.go callInjectICE()` | 经信令帧向双方下发 iceServers，未启用 TURN 时客户端退化为纯 P2P，零改动兼容 |
| P2P 信令实战骨架 | `im-server/server/filep2p.go`（msg_type=91，阶段一百五十六） | `probe → accept（先到先得锁定赢家）→ offer/answer/candidate → ping 保活 → 懒清理 + 看门狗`，服务端判定 + 客户端分流 |
| 通话信令状态机 | `im-server/server/call.go`（msg_type=70，阶段一百四十一） | invite/accept/offer/answer/candidate 完整状态机，好友与黑名单校验、from_user 归口防伪造、多端转发、超时兜底 |
| DataChannel 实战 | `im-client/web/js/remote-engine.js` | 远程协助已用 `createDataChannel('remote-input', {ordered:true})` 点对点直传控制事件 |
| 房间态广播惯例 | `msg_type=105`（位置共享） | `state` 全量广播 + 成员变更推送，可直接复用同款范式 |

## 1.2 目标

1. 为游戏提供「**P2P 打洞直连优先、TURN 中继兜底**」的跨公网联机能力，打洞失败自动降级、玩家无感；
2. 提供**房主 + 加入者**的房间模型（对标 Steam Lobby）：建房、加入、成员态、房间态广播、超时回收；
3. 提供**两种接入形态**：自研游戏用原生 SDK（形态一），第三方游戏零改动走通用端口隧道（形态二）；
4. **服务端数据归口原则不破坏**：服务端只见信令，不经手任何游戏字节（与文件 P2P 直传同水位）；
5. **对现有功能零回归**：不改动通话/会议/远程/文件直传的既有代码路径。

## 1.3 非目标（功能一期不做）

- 虚拟网卡（TUN/Wintun）——即「真·局域网」路线（对标 ZeroTier / Hamachi），涉及驱动与管理权限，另案评估；
- 手机端（APK）联机——Capacitor WebView 端口隧道受系统限制，功能一期仅支持 PC 端（与文件 P2P 直传的「手机端回退」策略一致）；
- Mesh 多点拓扑、观战、断线重连——留功能三期；**房主转让已于功能二期落地（见 §12.2）**；
- 只认广播发现、且完全不支持手动输入 IP 的老游戏——功能一期不覆盖（见「十三、风险与边界」）。

# 二、Steam 的实现原理（对标依据）

## 2.1 三层机制

Steam 把「局域网联机跨公网」拆成三层，本项目逐层对标：

| 层 | Steam | 职责 |
|---|---|---|
| 发现 / 匹配层 | Steam Lobby | 服务端把玩家拉进同一房间，交换身份与端点信息（房间号 / 邀请） |
| NAT 穿透层 | STUN + UDP 打洞 | 双方各自向公网 STUN 探到自己的公网映射端点，再互发探测包顶开各自 NAT 映射，形成 P2P 直连 |
| 中继兜底层 | SDR（Steam Datagram Relay） | 打洞失败时（对称 NAT / CGNAT / 企业防火墙）改走 Valve 全球中继骨干；顺带隐藏真实 IP、优化跨运营商路由 |

游戏侧实际调用的是 `ISteamNetworkingSockets`：一个「打洞优先 + 中继兜底」的 P2P 连接 API，**前提是游戏集成了 Steamworks SDK**。

## 2.2 两处必须澄清的认知

1. **Steam 本身不做虚拟网卡**。对「只认真·局域网广播发现」的老游戏，Steam 官方也没有「虚拟局域网」能力；这类需求业界靠第三方虚拟网卡工具（ZeroTier / Hamachi / Radmin VPN / Tailscale）解决。
2. **Steam Remote Play Together 不是「局域网模拟」**。它是把房主的画面/音频/输入串流给其他人，属「本地同屏游戏」的远程化，与本文的「网络联机」是两条完全不同的技术路线。

# 三、总体架构

两条链路（对应 Steam 的穿透层 + 中继层）：

```
                         ┌──────────────────────────────┐
                         │  im-server（信令归口）        │
                         │  109 房间层 / 110 连接层      │
                         │  房间成员 · ICE 候选交换       │
                         └──────────────┬───────────────┘
                                        │ 控制信令（WS，现有长连接）
         ┌──────────────────────────────┴──────────────────────────────┐
         │                                                              │
    ┌────▼─────┐                                                  ┌─────▼────┐
    │  房主 PC  │◀══ ① 打洞直连（WebRTC DataChannel，P2P） ════════▶│ 加入者 PC │
    │ 游戏主机  │                                                  │          │
    └────┬─────┘                                                  └─────┬────┘
         │                    ┌────────────────────┐                    │
         └──── ② 中继兜底 ───▶│ TURN 中继（turn.go）│◀── 中继兜底 ────────┘
           （打洞失败 / 强制） └────────────────────┘ （打洞失败 / 强制）
```

- **① 直连**：`host → srflx` 候选优先，UDP 打洞成功即点对点直传，不经服务端；
- **② 中继**：打洞失败自动降级 TURN，服务端在分配时给出 relay 地址（`XOR-RELAYED-ADDRESS`），双方各自连中继转发；
- **信令面**：全程走现有 WebSocket，仅新增 msg_type 分支，游戏字节**永不进入**服务端。

**拓扑：功能一期采用星型（房主为 hub）**。局域网游戏的天然语义就是「主机 + 加入者」，房主与每个加入者各建一条 WebRTC 连接，房主负责转发。Mesh 留功能三期。

# 四、两种接入形态

路线必须回答一个问题：**游戏怎么把数据交给我们？** 两条路都做，功能一期先做形态二。

## 4.1 形态一：原生 SDK（对标 ISteamNetworkingSockets）

游戏集成项目提供的联机 SDK，直接调用 API 收发数据包。

- 优点：最干净、延迟最低，可用 WebRTC 的**不可靠无序通道**（`ordered=false` + `maxRetransmits=0`），**语义等价 UDP**，正合游戏需求；
- 前提：游戏是自研的（游戏中心上架的自研游戏完全满足）；
- 分期：放功能二期。

## 4.2 形态二：通用端口隧道（功能一期先做，游戏零改动）

客户端在本地启动一个**端口映射隧道**，把游戏对「房主机器」的连接，经 WebRTC/TURN 隧道转发到房主本机的真实游戏端口。

```
加入者游戏 ──▶ 加入者本地隧道 ──[ 公网 · WebRTC / TURN ]──▶ 房主本地隧道 ──▶ 房主游戏
 连本地地址      监听 :host_port      打洞直连 或 中继兜底       还原 :host_port      监听 :host_port
```

关键点：

1. **加入者本地隧道监听的端口号 = 房主游戏的真实端口号**，因此游戏侧看到的 `IP:端口` 与「真的在局域网里连房主」完全一致，游戏**零感知**；
2. 游戏数据走 DataChannel（或中继），**不占用** WS 发送队列（`send_queue_size`），不挤压聊天消息；
3. 适用于「支持手动输入主机 IP 直连」的游戏（多数支持局域网联机的游戏同时允许直连）。

## 4.3 直连 IP 与端口的来源（重点）

最常见的误解是「要填对端的公网 IP」。**不是。**

### 玩家在游戏里填什么

| 填法 | 适用 | 说明 |
|---|---|---|
| 本机局域网 IP + 端口（如 `192.168.1.50:7777`） | **推荐，兼容性最好** | 隧道监听 `0.0.0.0:端口`，连本机 LAN IP 同样被隧道截获；很多游戏只接受「像局域网 IP」的地址，拒绝 `127.0.0.1` |
| `127.0.0.1:端口` | 大多数游戏 | 本机隧道在该地址监听，游戏以为连的是「房主机器」 |
| 真实公网 IP | **不适用** | 那条路要求房主路由器做端口映射（外网端口转发到游戏机），家宽基本不可行——这正是要有隧道的原因 |

### 端口号从哪来（第 1 层：房主本机探测）

房主端隧道启动时枚举本机监听套接字（Windows `GetExtendedTcpTable` / `GetExtendedUdpTable`，或解析 `netstat -ano`），按**游戏进程名 / 可执行路径**过滤，找出游戏进程占用的监听端口 → 自动填入房间信息，经 109 房间态 / 110 信令下发；探测失败或端口不固定时允许房主**手动指定**。加入者从房间信息拿到 `host_port` 后，本地隧道 bind 同一端口号。

### 对端真实网络地址从哪来（第 2 层：隧道层自动发现，玩家不接触）

1. **STUN**：内置 pion/turn（同端口 3478）兼作 STUN 服务器，双方各自探到自己的**公网映射端点**（srflx 候选）；
2. **信令交换**：经现有 WebSocket 的 110 信令互报候选（`callInjectICE` 顺带下发 iceServers）；
3. **UDP 打洞**：双方往对端公网端点互发探测包，顶开各自 NAT 映射 → P2P 直连建立；
4. **中继兜底**：打洞失败改走 TURN，**对端连地址都不用知道**——服务端在中继分配时直接给出 relay 地址，双方各自连服务端中继转发。

> 一句话：**IP 不是「获取房主的公网 IP」，而是隧道在本机伪造一个「看起来就是局域网」的入口；真实对端地址由 STUN + 信令 + 打洞自动得到，失败则由服务端给中继地址。**

# 五、信令协议设计

## 5.1 msg_type 规划

现有 msg_type 已排到 **108**（`MsgTypeMomentSync`），本次顺延：

| msg_type | 名称 | 职责 |
|---|---|---|
| **109** | `GAME_ROOM_SIGNAL` | 房间层：`create / join / leave / kick / ready / start / state / list / chat / closed` |
| **110** | `GAME_NET_SIGNAL` | 连接层：`probe / accept / offer / answer / candidate / relay / ping / abort` |
| **111** | `GAME_INVITE` | 邀请卡片（落库 + 离线推送，见 `server/gameinvite.go`；与红包 86 / 分享卡片 92 同范式） |
| **112** | `GAME_LOBBY_SIGNAL` | 联机大厅：`enter / ping / leave / msg`（在场心跳 + 大厅聊天，不落库） |

> 实现状态：109 / 110 / 111 / 112 均已在服务端落地（`protocol/message.go` 249~265 行；处理入口 `server/gamenet.go`、`server/gameinvite.go`）；9 为通用错误帧。

## 5.2 房间层（109）

沿用项目既有的 **action 模式**（同 70 通话 / 90 远程 / 91 文件直传 / 105 位置共享）：

- `create`：房主建房（可选**房间口令**，服务端 SHA-256 哈希存储；携带 `game_id / game_name / game_mode / max_players / host_port`），服务端分配房间号；`max_rooms` / `max_per_user` 由 Lua 原子校验；
- `join` / `leave`：加入 / 退出；服务端做**成员校验**（好友或同群）+ **口令校验** + **黑名单拦截** + 满员校验（见「十、安全与水位」）；
- `kick`：房主踢人（被踢者收 `closed`）；
- `ready`：成员就绪切换（房主不参与准备）；
- `start`：房主开局（要求除房主外成员全部就绪），房间态置 `playing`；
- `state`：全量广播房间态（成员列表、房主、`host_port`、`status`、各成员就绪态），对齐 105 的 `state` 广播惯例；
- `list`：房间列表（供 UI 展示）；
- `chat`：房内聊天；服务端广播**含发送者本人回显**（房间不存在 / 非成员时回通用错误帧 9 + `content`），不落库；
- `closed`：房主退出 / 超时回收 / 被踢时广播关房。

### 5.2.1 大厅层（112）

- `enter` / `ping` / `leave`：大厅在场心跳（Redis ZSET `im:game:lobby`，score = 心跳秒，45s 惰性剔除），`enter` 回复在场名单；
- `msg`：大厅聊天广播（含发送者本人回显），不落库。

## 5.3 连接层（110）

**整体照搬 `filep2p.go` 的成熟骨架**：`probe → accept（先到先得锁定赢家）→ offer/answer/candidate（复用 `callInjectICE` 注入 iceServers）→ ping 保活 → 懒清理 + 看门狗`。

- 服务端：`from_user` 归口防伪造（沿用现有强校验）、在线判定、转发；
- 客户端：分流与降级决策；
- **不改动** filep2p 的任何既有代码路径，仅新增一组独立分支。

### 5.3.1 字段契约（服务端已实现，客户端按此对接）

110 帧 `content` 公共字段：`action` / `conn_id`（连接唯一标识，加入者生成）/ `room_id`（仅 probe 用）/ `platform`（仅 accept 用）；`sdp` / `candidate` 等媒体字段**原样透传不解析**。

| action | 方向 | 服务端行为 |
|---|---|---|
| `probe` | 加入者 → 房主 | 逐项校验「总开关 / 发起端为 PC 端 / 房间存在 / 目标必须是该房间房主 / 发起者是房间成员 / 房主端在线 / 并发水位」后转发房主全部在线端；任一不满足即回发起方 `probe_fail(reason)`，不让其白等超时 |
| `accept` | 房主 → 加入者 | 会话表**先到先得**锁定唯一赢家（房主多端在线全部自动 accept）；后到端收 `abort(already_accepted)`，杜绝双通道 |
| `offer` / `answer` / `candidate` | 双向 | 校验会话存在与参与者身份后按 `conn_id` 定向转发（`callInjectICE` 注入 iceServers） |
| `relay` | 双向 | 「已降级走中继」通知帧，服务端仅透传（供 UI 提示，不改变链路） |
| `ping` | 双向 | 刷新会话活跃 + **续期房间 TTL**（联机期房间活跃由 110 共同维持）+ 转发对端喂其看门狗；建议 15s 一次 |
| `abort` | 双向 | 转发对端 + 清理会话；客户端按 `reason` 决定重试或回退 |

- `reason` 枚举：`unsupported`（发起端非 PC）/ `offline`（房主端不在线）/ `forbidden`（非成员或目标非房主）/ `room_closed`（房间不存在或已关闭）/ `busy`（并发水位或 conn_id 冲突）/ `timeout`（15s 未 accept 或 30s 无 ping）/ `already_accepted`（多端竞态落败）/ `kicked` / `left` / `host_left`（服务端收口）；
- 服务端主动收口：房间关闭 → `abort(host_left/empty)`；成员退出 → `abort(left)`；成员被踢 → `abort(kicked)`；会话超时或房间键消失 → `abort(timeout/room_closed)`，防孤儿隧道；
- `host_port` 以**房间态**为准（109 建房时落 Redis），不信客户端自报；
- 两级超时兜底：客户端按 `negotiate_timeout`（默认 10s）先自行收口，服务端懒清理 15s/30s 兜底（同 filep2p 口径，不启用定时器风暴）。

## 5.4 连接状态机（单对房主↔加入者）

```
idle ──probe──▶ probing ──accept──▶ negotiating ──offer/answer/candidate──▶ connected
                    │                     │                                     │
                  超时/拒绝             协商超时 / ICE 失败                    断开
                    ▼                     ▼                                     ▼
                 aborted              fallback(TURN) ──成功──▶ connected        closed
```

- 协商超时沿用文件直传口径（`negotiate_timeout`，默认 10 秒）；
- ICE 候选优先级 `host → srflx → relay`；ICE 失败自动降级中继。

# 六、数据面设计

## 6.1 通道选型

| 用途 | 通道 | 参数 |
|---|---|---|
| 游戏数据（形态一） | DataChannel | `ordered=false` + `maxRetransmits=0`（不可靠无序，等价 UDP）；对可靠性敏感的游戏可按房间配置改可靠 |
| 游戏数据（形态二） | DataChannel（端口映射转发） | UDP 端口走不可靠通道；TCP 端口走可靠有序通道 |
| 控制 / 保活 | DataChannel（独立通道名） | `ordered=true` |

同一条 `RTCPeerConnection` 可开多条 DataChannel，控制与数据分离互不阻塞。

## 6.2 端口映射与转发（形态二）

- 加入者隧道维护「本地 `0.0.0.0:host_port` → 该房间对端 DataChannel」的映射表；收到本地 UDP/TCP 包按房间路由到对应通道；
- 房主隧道维护「DataChannel → 本机 `127.0.0.1:host_port`」的反向映射；
- 需处理：NAT 映射保持（心跳）、丢包重传策略（可靠 vs 不可靠分端口取舍）、连接空闲回收。

## 6.3 中继兜底

- `iceServers` 由 `callInjectICE` 统一下发，服务端**不感知**最终走直连还是中继；
- `game_net.relay_only` 可强制走中继（企业网 / 调试用）；
- 中继带宽与端口容量见「九、对现有功能的影响分析」。

# 七、房间与成员管理

- 房主建房（可选房间口令），加入者经房间号 / 邀请进入；
- 成员上限 `max_members`；房主退出则房间关闭（**房主转让已于功能二期落地**，见 §12.2 `transfer` 信令）；

# 九、对现有功能的影响分析（重点）

## 9.1 结论速览

| 现有功能 | 共享点 | 是否受影响 | 说明 |
|---|---|---|---|
| 1v1 语音/视频通话 | TURN 中继端口 + 出口带宽 | **会** | 打洞失败时争抢中继端口段 |
| 群会议 | 同上 | **会** | 多成员会议本身已吃多个中继端口 |
| 向日葵式远程控制 | TURN 中继 + WS 信令 | **会（弱）** | 同上；信令链路不受影响 |
| 文件 P2P 直传 | TURN 中继 + WS 信令 | **会（弱）** | 数据走 DataChannel，只争中继端口 |
| 上述全部的信令 / ICE 注入 / 在线判定 | `callInjectICE`、`hub.HasCall`、msg_type 分发 | **不会** | 全新增调用点，不改既有代码路径 |

## 9.2 TURN 中继端口是唯一硬瓶颈（量化）

`turn.go` 的中继端口段为 `min_port=49160 ~ max_port=49200`，**仅 41 个 UDP 端口**；每次走中继的对端连接占 1 个，`MaxRetries=10` 用完即报错。（**2026-10-15 已扩容至 `49160~49960`（800 个）**，见 §9.4-1 与 §12.1；本段保留扩容前的口径，用于还原当时的风险论证。）

- 一路 1v1 通话双方都走中继 = 占 **2 个**端口 → 41 端口**最坏只够约 20 路通话**；
- 现有占用方已有四家：通话 / 群会议 / 文件直传 / 远程协助；
- 新增游戏联机若一个 6 人房间全部走中继 = 占 **6 个**端口 → **3 个这样的房间就吃掉通话中继容量的一半**。

后果不是崩溃，而是**「打洞失败的通话号突然建不起来」**——表现隐蔽、排查困难，属第一优先级。

## 9.3 全信令层为什么零回归

- `callInjectICE`（`call.go`）是**纯函数**：只往 content 塞 `ice` 字段，TURN 未启用时原样返回。游戏联机只是**新增一个调用点**；
- `hub.HasCall`（`hub.go`）是**只读判定**，游戏端若需类似能力是新增方法；
- 109/110 只是 msg_type 分发里多两个 `case` 分支；
- 游戏数据走 DataChannel，不占 WS 发送队列，不挤压聊天消息。

## 9.4 规避措施（功能一期 1~3 必做；4~5 已降级功能二期，并已于 2026-10-15 落地）

1. **扩中继端口段（必须）→ ✅ 已完成（2026-10-15）**：`min_port~max_port` 已从 41 个（`49160~49200`）扩到 **800 个**（`49160~49960`），并同步 `config.yaml` / `config - linux.yaml` / `turn.go` 缺省 / `config.go` 注释四处；**仅剩安全组放行同段（UDP）**（部署动作）。这是唯一能同时保护通话与游戏的关键动作。
2. **游戏默认直连优先**：`relay_only=false`；功能二期可给 `game_net` 单独设中继配额 / 端口子段，避免与通话抢同一池，甚至独立中继实例。
3. **功能一期限制规模**：房间人数上限 ≤6 + `max_per_user=2`，控制中继端口与带宽峰值（星型拓扑房主扇出最大）。
4. **（功能二期）中继占用量可观测 → ✅ 已完成（2026-10-15）**：`srv.AllocationCount()`（`turn.go` 注释预留口径）已接入监控——
   - **服务端**：`turn.go` 归口 `turnAllocationStats()`（现占用 / 启动以来峰值 / 端口段容量），并起 60s 采样协程 `turnAllocSampler()`（零占用静默；有占用每轮输出；归零输出一次释放行）；
   - **指标**：`GET /admin/api/metrics` 的 `business` 增 `relay_enabled` / `relay_allocations` / `relay_capacity` / `relay_alloc_peak`；
   - **告警**：`alerts.go` 增规则 `relay_high`——占用 ≥80% 容量时报 error（30s 评估周期，回落自动 clear）；
   - **后台**：管理后台仪表盘增「TURN 中继占用」卡片组（当前占用 / 端口容量 / 占用峰值）。
   - **实测（2026-10-15）**：建 2 路真实 TURN 分配 → 采样日志 `当前中继会话 2/801（启动以来峰值 2）`；临时把 `max_port` 改 `49164`（容量 5）建 4 路分配 → 30s 内出 `错误 [relay_high] TURN 中继占用 4/5（≥80% 容量…）`，`/admin/api/metrics` 同步读到 `relay_enabled=true allocations=4 capacity=5 peak=4`，后台卡片显示「4 / 5」「5 个」「4 个」。

   - **注**：TURN 分配存活至自身生命周期到期，客户端主动 Close 不触发服务端立即 deallocate（RFC 5766 标准行为），故「释放行」需等到期后下一轮采样才出现。
5. **（功能二期）客户端并发提示 → ✅ 已完成（2026-10-15）**：口径为**仅联机侧最小改动**（通话窗 / 远程窗只上报状态，不加任何 UI）——

# 十、安全与水位

对齐现有最强水位：

- **登录名归口防伪造**：`from_user` 由服务端归口，客户端不可伪造；
- **房间强校验**：房间成员必须互为好友或同群成员，非成员一律拒绝；
- **黑名单拦截**：沿用通话/文件直传的黑名单口径；
- **房间口令**：归一化为服务端校验，不经客户端自行判定；
- **流量与并发水位**：`max_per_user`（单用户并发房间数）、`max_members`（单房间成员数）、`max_rooms`（全局房间数）；
- **服务端不落库游戏数据**：与文件 P2P 直传同水位，服务端只见信令。

# 十五、容量与扩展（上万级联机可行性）

## 15.1 Steam 的支撑模型

Steam 能把「上万人在不同游戏联机」做成常态，核心是把**「游戏数量」与「基础设施压力」解耦**：

1. **控制面（matchmaking / lobby / identity）轻量且分布**：只交换元数据（房间、玩家、端点），不触碰游戏字节；分片 + 多地域，因此「上万个房间」只是元数据规模；
2. **数据面绝大多数是 P2P 直连**：游戏流量在玩家之间直连，不经 Valve；
3. **中继（SDR）是唯一承重部件，但被铺成全球 PoP 集群 + 私有骨干**：用户连最近接入点，中继是**无状态 UDP 转发**（按 backend ticket 路由），可水平铺量——本质是机房 + 带宽堆出来的能力；
4. **不按游戏隔离设施**：传输层通用，「不同游戏」不构成乘数压力。

**结论：压力点在「中继总带宽 + 就近接入」，且中继只承载打洞失败的那部分，与游戏数量无关。**

## 15.2 现状分层体检

| 层 | 现状（实测） | 上万级可行性 |
|---|---|---|
| 信令层（WS / 房间态） | 单实例为进程内内存 map（`im-server/server/hub.go`），**已支持多实例集群**（`config/config.go` `cluster_enabled` + Redis pub/sub 总线，`deploy/nginx-im.conf` 反代多实例） | **可水平扩展**；文档口径单机 500–800 在线，1 万需约 15~20 个实例 |
| 游戏数据面 | WebRTC DataChannel，P2P 直连不过服务端 | **天然可扩展**，与人数无关；**是上万的唯一前提** |
| 中继兜底（TURN） | pion/turn 与 im-server **同进程且绑定单机**（`deploy/nginx-im.conf`：「通话/会议 TURN 中继绑定具体机器」），端口段 800 | **天花板** |

## 15.3 量化：中继是天花板

按「一对全中继连接 = 双方各 1 个 allocation = 2 个端口」计：

| 场景 | 端口消耗 | 800 端口/节点可承载 |
|---|---|---|
| 1v1 全中继 | 2 | 400 路 |
| 6 人房间全中继（星型 5 连接） | 10 | 80 个房间 |
| 1 万个 6 人房间全中继 | 100k | 需 125 个中继节点 |

带宽侧：按每会话 50~100 kbps 双向过服务器估，**1 万并发全中继 ≈ 1~2 Gbps 常态出口**。且 TURN 与 im-server 同进程时，中继洪峰会**挤占信令 CPU**。

## 15.4 结论

- **上万人在不同游戏「直连为主」联机 → 架构上可行**：服务端只吃信令（体量极小），信令层多实例能力已存在，补齐即可；
- **上万「并发走中继」→ 现有架构不可行**：中继单机、同进程、带宽与端口硬绑定，必须独立成集群 + 就近接入（相当于自建缩小版 SDR），成本随并发线性上升，带宽是大头；
- **「不同游戏」不构成乘数**：与 Steam 同理，共享一套通用信令 + 传输设施，不按游戏分资源。

## 15.5 扩容路径（四步）

1. **信令层扩容**：打开 `cluster_enabled`，多实例 + nginx 反代 + Redis 总线（现成能力），在线名单走集群态 `im:ulist`；
2. **中继拆出独立集群**：多节点、多地域、就近接入——这一步才有资格谈上万，否则「绑定具体机器」的限制会直接堵死横向扩展；
3. **房间态入 Redis**：房间表 + TTL 从单机内存迁出，保证跨实例可见与回收；
4. **容量策略**：坚持直连优先，中继按**打洞失败率**预留容量，接入 `AllocationCount()` 监控与限流。

## 15.6 集群模式下的信令归口要求（必做）

109 / 110 房间信令在集群模式下**必须走 Redis 总线归口**（`sendToUser` 跨实例信封），否则多个 im-server 实例部署时，房间成员分布在不同实例上会**漏推**——这是 `filep2p` / `call` 那套单机信令在多实例下的已知坑，新增模块不得重蹈。

# 十六、中继集群部署方案（2026-10-14 已定）

## 16.3 节点注册与健康摘除（路线 C 的服务端部分）

- 每个 TURN 节点用**独立进程**运行，周期性上报心跳，键固定为 `turn:nodes:{node_id}` → `{domain, region, port_range, allocations, max_allocations, bandwidth, ts}`；
- **双上报通道（按配置切换，16.1 决策 4）**：`nodes_report_mode: redis` 由节点自己直写 Redis（复用现有 `redis_addr`，要求中继机与 Redis 内网互通）；`nodes_report_mode: server` 由节点 POST 到信令实例的新端点 `POST /api/turn/node-report`（请求头带 `nodes_report_token`，与 config 一致），服务端校验后**代写**同一键——Redis 完全不对外暴露，跨机房/异运营商首选；
- **心跳节奏与容错**：节点每 5s 上报一次，`node_health_ttl`=15s（容忍连续 2 次丢失不摘除）；单次 Redis 抖动或网络抖一下不会把候选摘空；
- **水位降权**：节点上报 `allocations / max_allocations`，超过 `node_load_watermark`（如 85%）则该节点**不再纳入新候选**，但**不影响已建立会话**；
- **降级兜底（关键）**：Redis 不可用时退化为 `static_candidates` 静态列表，联机与中继仍可用。

> 指标口径（实测确认）：`allocations` 取 pion 现成 API `Server.AllocationCount()`（[turn.go](file:///e:/SourceCodeIM/im-server/server/turn.go#L182) 已留注释位）；也可用 `ServerConfig.EventHandler`（`OnAllocationCreated` / `OnAllocationDeleted` / `OnAuth`）做生命周期事件留痕。**per-session 带宽 pion 不提供**，`bandwidth` 只能取节点网卡计数（`/proc/net/dev`）或云监控 API，不要指望从 TURN 内部读。

## 16.4 凭证方案（集群化的前提，集群一期改为短期凭证）

**起因**：原方案是"全套长期凭证三节点一致"，但那等于把一把**共享密钥**摊在整个集群里——一旦泄漏（抓包/配置外泄/离职），任何人都能白嫖中继带宽做流量放大，且密钥无法收敛（轮换一次就得全集群同步重启）。集群一期改为**短期凭证（coturn REST 同款）**。

- **主方案：短期凭证（`auth_mode: short_term`）**
  - 所有节点共用同一个 `credential_secret`（**HMAC 共享密钥**，各节点必须完全一致）+ 同一个 `realm`；
  - 服务端每次下发 iceServers 时**现生成**凭证：`username = "<过期时间戳>:<user>"`、`password = base64(HMAC-SHA1(credential_secret, username))`，`credential_ttl`（建议 600s）内有效，过期即拒；
  - 泄漏的凭证最长只有 `credential_ttl` 寿命，且可与用户名绑定 → 滥用面从"永久"收敛为"十分钟"；
  - **客户端零改动**：凭证仍由服务端经 `callInjectICE` 注入 `ice` 字段（通话 / 会议 / 文件直传 / 远程协助 / 游戏联机五路共用同一注入点）；
- **回退方案：长期凭证（`auth_mode: long_term`）**：保留现有 `username` / `password` 单一账号实现不变（[turn.go](file:///e:/SourceCodeIM/im-server/server/turn.go#L144-L153) 现逻辑），用于短期凭证链路出问题时的兜底切换；
- **两模式都要求**：各节点 `realm` 一致（realm 参与摘要认证的 MD5，不一致直接认证失败）；每节点**独立域名或独立公网 IP**（中继会话绑定具体机器，严禁共享同一轮询域名）；
- **实现依据（已实测）**：pion/turn v4.1.4 内置 `turn.LongTermTURNRESTAuthHandler(secret, logger)` 与 `turn.GenerateLongTermTURNRESTCredentials(secret, user, ttl)`，无需自研认证算法；`AuthHandler` 返回的 key 即 RFC 5766 的 `MD5(username:realm:password)` 字节，与现有实现语义一致，切换不动协议栈。

## 16.5 多候选下发

- `TurnICEServers()` 由「返回单条」改为**返回多条**：`candidates_max` 约束的是**节点数**（建议 2~4），实际下发条目 = 选中节点数 × 2（`turn:` 与 `turns:`）+ 1 条 `stun:`（任取一个健康节点，STUN 只需一条做 srflx 收集）；
- 客户端 ICE **并发探测全部候选**，原生自动选最快可达路径，**无需自研选路**；探测开销与候选条目数成正比（每条 TURN 候选都会触发一次 allocation 尝试），所以不要贪多；
- 游戏联机与通话/会议/文件直传/远程**共用同一套候选下发**（`callInjectICE` 的 `m["ice"] = ice` 注入点，[call.go](file:///e:/SourceCodeIM/im-server/server/call.go#L180)），因此 109/110 无需额外处理，**客户端也零改动**（浏览器/Electron 原生支持多条 iceServers）；
- `relay_only=true` 时，指定延迟最低的健康节点（其余节点不参与，减少无用的 allocation 探测）。

## 16.6 实现要点：复用而非重写

**不要把 TURN 换成 coturn**。现 `im-server/server/turn.go`（pion/turn + 凭证 + 端口段 + 域名巡检 + 线路故障自动跟随）是成熟资产，抽取方式是：

- 同一代码库增加「**仅 TURN 模式**」：配置项 `turn.standalone: true`（16.1 决策 5）。分支落点在 [main.go](file:///e:/SourceCodeIM/im-server/main.go#L65-L96) —— `standalone` 时跳过 MySQL 初始化、`prewarm`、hub/总线/全部定时循环与 HTTP 路由注册，只保留 `StartTURN` + 心跳上报循环（`nodes_report_mode: redis` 时仍需 `store.InitRedis`；`server` 模式则不碰 Redis，只出向 HTTPS 上报）。**注意现状**：`StartTURN` 现位于 L333，其前面已挂了一堆路由与初始化，必须在最前面就分流，不能只"少调一个 StartTURN"；
- 保持凭证 / 端口段 / 域名巡检逻辑与现有实现**完全一致**，避免双份实现漂移；
- **同机部署端口互斥（集群一期先跑单节点时必须处理）**：TURN-only 进程会占 `3478`（UDP+TCP）、`5349`（TCP）、`49160~49960`（UDP）；同一台机器上的 im-server 必须 `turn.enabled: false`（只做信令，候选由注册表下发），否则抢端口/抢端口段；
- **TURN over TLS 挂法（已实测）**：pion/turn v4.1.4 本身不建 TLS 监听，需自己 `tls.Listen("tcp4", "0.0.0.0:5349", &tls.Config{MinVersion: tls.VersionTLS12, Certificates: []tls.Certificate{cert}})`，把该 `net.Listener` 传进 `ServerConfig.ListenerConfigs[].Listener` 即可（与现有明文 TCP 监听同一路径，pion 官方 `examples/turn-server/tls` 同款写法）；
- **DTLS 明确不做（实测结论）**：v4.1.4 源码里 DTLS 只出现在 `server_config.go` 的一句注释里，**没有实现、没有示例、没有测试**，`PacketConnConfigs` 要的是 `net.PacketConn` 而 DTLS 只能给 `net.Listener`。因此集群一期只做 **TURN over TLS（TCP 5349）**，不承诺 DTLS（5349/UDP）——这是与 coturn 的已知能力差，需要在文档与验收口径上写清；
- TLS 证书按节点独立域名签发（即可用 ACME/Let's Encrypt + systemd timer 自动续期），证书轮换后需重启 TURN 进程（或集群二期做热加载）。

## 16.7 配置新增（`turn` 节扩展）

```yaml
  tls_enabled: true             # true=额外监听 5349 TCP；证书按节点独立域名签发
  tls_port: 5349                # TURN over TLS 监听端口（TCP）
  tls_cert_file: ""             # 证书路径（fullchain.pem）；tls_enabled=true 时为空则启动报错
  tls_key_file: ""              # 私钥路径（privkey.pem）
  # ---- 节点心跳上报（16.1 决策 4）----
  nodes_report_mode: redis      # redis=节点直写 Redis（需内网互通） / server=POST 到信令实例由服务端代写
  nodes_report_interval: 5      # 心跳间隔秒（< node_health_ttl，容错 2 次）
  nodes_report_url: ""          # server 模式：信令实例上报地址（多实例可填多个，逗号分隔轮询）
  nodes_report_token: ""        # server 模式：上报鉴权令牌（各节点与服务端一致；空则 server 模式启动报错）
  node_id: ""                   # 本节点标识（注册表键名 turn:nodes:{node_id}；空则用域名）
  node_region: ""               # 本节点地域/线路标记（如 telecom / unicom，仅供运维展示）
  node_max_allocations: 400     # 本节点最大并发 allocation（上报用，超过即触发水位降权）
```

**同步要求**：`config.yaml` 与 `config - linux.yaml` 必须同步（项目规则）。

## 16.8 部署规格与落地步骤（集群一期：信令 2 实例 + 中继先 1 台再扩 2 台）

### 目标拓扑与规模

```
公网 ──▶ nginx 反代 ──▶ im-server ×2（只跑信令，cluster_enabled=true，共用现有 MySQL/Redis）
                             │  读 turn:nodes:* 注册表组装候选
                             │  下发多候选 iceServers（每节点独立域名）
                    ┌────────┴────────┐
            TURN-A（第 1 台·先跑）      TURN-B（第 2 台·后扩·异运营商）
            独立进程 · 独立域名         同左，realm 与 credential_secret 完全一致
            3478(UDP/TCP) + 5349(TCP) + 49160~49960（800 端口）
```

- **集群一期先上 1 台（16.1 决策 6）**：在现有服务器上跑 TURN-only 独立进程，im-server 侧 `turn.enabled: false` 让出 3478/5349/端口段（见 16.6 端口互斥）。先把 standalone + 心跳 + 短期凭证 + TLS + 单候选链路跑通，**再扩第 2 台**验证多候选自动选路与健康摘除；
- 信令侧 **2 实例** + nginx 反代（现成能力），Redis / MySQL 复用现有部署，**不新增组件**。注意 `nodes_report_mode: redis` 要求中继机与 Redis 内网互通，否则切 `server` 模式（Redis 不对外暴露）。

### 单节点容量口径（800 端口段）

| 约束 | 上限 | 说明 |
|---|---|---|
| allocation 数 | 400 对并发 | 1 对全中继连接 = 双方各 1 allocation = 2 端口 |
| 出口带宽 | 400 对 × 100 kbps ≈ 40 Mbps | 游戏小包高频，带宽不是首要瓶颈 |
| 包处理 CPU | 与 pps 正相关 | 8 核可承载数万 pps，需实测标定 |

### 集群一期规模测算

≤6 人房间全中继 = 10 端口/房间；500 房间若全走中继 = 5000 端口；按真实打洞失败率 **15~25%** 只落到 750~1250 端口 → **2 台各 400 对（合计 800 对）覆盖且有余量**。结论：中继按失败率预留容量，**直连优先才是成本关键**。

> 单节点阶段（只上第 1 台）需注意：1 台 = 400 对 / 800 端口，而 500 房间 × 20% 失败率 ≈ 1000 端口，**已超单节点容量**。因此单节点期间房间规模按 **≤300 房间**控（或临时下调 `game_net.max_rooms`），扩第 2 台后再放开到 500。

### 域名与凭证

- 每节点独立域名：`turn-a.example.com` / `turn-b.example.com`，各自 A 记录指向自身公网 IP（**严禁共享同一轮询域名**——中继会话绑定具体机器）；
- 各节点 `realm` 与 `credential_secret`（`auth_mode: short_term`）**必须完全一致**（见 16.4）；长期凭证回退模式下才是 `realm` / `username` / `password` 三者一致；
- 集群二期同一域名同时用于 TLS 证书（5349）与中继报告地址，**一张证书一条链路**，DNS 与证书一起规划；
- 客户端凭证由服务端按会话现生成下发 → 节点新增/切换/摘除、密钥轮换对客户端完全无感。

### 心跳载体（双模式，见 16.1 决策 4）

- **`nodes_report_mode: redis`**：中继节点直写 `turn:nodes:{node_id}`，`redis_addr` 用现有配置，**不新增组件**；需为每台中继机开放 Redis 访问（仅内网 + 密码鉴权，不对公网暴露）；
- **`nodes_report_mode: server`**：节点 POST `nodes_report_url`（可填多个信令实例、逗号分隔轮询）到 `POST /api/turn/node-report`，请求头带 `nodes_report_token`，服务端校验后**代写**同一个 `turn:nodes:{node_id}` 键；Redis 不对外暴露，跨机房/异运营商首选；
- 上报字段 `{domain, region, port_range, allocations, max_allocations, bandwidth, ts}`，**节点每 5s 上报、`node_health_ttl: 15` 秒过期即摘除**（容忍连续 2 次丢失）；
- Redis 不可用时按 16.3 降级为 `static_candidates`（写死各节点域名），中继与联机仍可用。

### 单节点部署步骤

1. **同一代码库编译**，以 `turn.standalone: true` 启动：只起 TURN/STUN（含 5349 TLS）+ 心跳上报，不起 IM 服务、不连 hub、不注册任何 HTTP 路由（分支落点见 16.6）；`nodes_report_mode: redis` 时仍需 Redis 连通；
2. `config.yaml`（中继机这份）：`enabled: true`、`standalone: true`、`public_ip` = 本节点专属域名、`port: 3478`、`min_port: 49160`、`max_port: 49960`、`node_id` / `node_region` / `node_max_allocations`、`auth_mode: short_term` + `credential_secret`（各节点一致）、`tls_enabled: true` + `tls_cert_file` / `tls_key_file`；
3. **im-server 侧同步**：`turn.enabled: false`（同机时让端口）、`nodes_registry: true`、`node_health_ttl` / `candidates_max` / `node_load_watermark` / `static_candidates` 按 16.7 配齐；
4. **TLS 证书**：按本节点域名签发（ACME / Let's Encrypt fullchain+privkey），systemd timer 自动续期，续期后重启本 TURN 进程（集群一期不做热加载）；
5. **网络放行**：3478（UDP+TCP）、5349（TCP，TURN over TLS）、49160~49960（UDP）、心跳出向（Redis 或信令实例 HTTPS）；
6. **常驻**：systemd 服务 + 开机自启 + 日志轮转 + **内核调优**（见下节，写入部署脚本，不可省）；
7. **心跳上报**按上节口径周期性写入（每 5s / TTL 15s）；
8. **监控**：节点是独立进程、没有 HTTP 口，**不能直接接现有仪表盘**；指标只能经注册表字段回传，由信令实例读取后聚合展示（`allocations`=`AllocationCount()`、`bandwidth`=网卡计数、`ts`=新鲜度、摘除/水位事件由信令侧计算）。

### 内核与 conntrack 调优清单（16.1 决策 7 第 3 项，中继机必做）

800 个 UDP 中继端口 + 高频小包是**内核面**的压力，不是端口的压力；不调优会在高并发下先丢包再掉会话。

| 项 | 建议值 | 原因 |
|---|---|---|
| `net.core.rmem_max` / `wmem_max` | 16~32 MB | UDP 中继收发缓冲区，默认值偏小会丢包 |
| `net.core.netdev_max_backlog` | 5000+ | 高 pps 时网卡队列排队长度 |
| `nf_conntrack_max` | ≥ 64k（或按内存放大） | 每条 allocation 至少 2 条表项（客户端↔中继、中继↔peer），800 端口 × 并发会撞表满 |
| `net.netfilter.nf_conntrack_udp_timeout` | 60s | 默认 30s 偏短，中继会话心跳间隔大于它时表项被过早回收 |
| `net.netfilter.nf_conntrack_udp_timeout_stream` | 180s | 有流量时用长超时 |
| `net.core.somaxconn` / `net.ipv4.tcp_max_syn_backlog` | 1024+ | TURN over TCP/TLS（3478 TCP、5349）建连队列 |
| `fs.file-max` / `LimitNOFILE` | 65535+ | 每 allocation 一个 socket |
| `net.ipv4.ip_local_port_range` | 避开 49160~49960 | 防本机出向临时端口与中继端口段相撞 |
| RSS/RPS 多队列 | 队列数对齐核数 | 高 pps 下把包处理摊到多核（iptables 规则少时收益最明显） |

> 调优后必须**实测标定**（16.9 压测项），不能只写参数不看数据；标定口径：单节点 400 对全中继并发下 `suggested_pps` / 丢包计数（`netstat -su` 的 receive buffer errors）/ 出口带宽。

### 灰度顺序

1 台真机（现有服务器，TURN-only 独立进程 + 短期凭证 + TLS + 单候选）跑通 → 验证通话 / 会议 / 文件直传 / 远程协助四路**零回归** → 扩第 2 台（异运营商/异域名，验证多候选自动选路 + 停止一个节点自动摘除）→ 打开 `cluster_enabled`（验证房间信令跨实例不漏推）→ 端口与带宽压测（按上节口径调优标定）→ 上线。

## 16.10 验收清单

- [ ] 手动停掉一个 TURN 节点 → 新会话候选自动剔除该节点，**已建立会话不受影响**；
- [ ] Redis 不可用 → 降级为静态候选，中继与联机**仍可用**；
- [ ] 两实例 im-server + 房间成员跨实例 → 房间信令**不漏推**；
- [ ] 多候选场景下客户端**自动选到最低延迟节点**；
- [ ] 单节点水位超限 → 不再承接新会话，存量会话正常；
- [ ] 心跳双模式各验一次：`redis`（节点直写注册表）与 `server`（节点 POST `/api/turn/node-report`，Redis 不对外暴露时）；
- [ ] 节点上报中断 10s（两次心跳丢失）后台 `node_health_ttl: 15` 到期才摘除，**不出现单次抖动即摘空**；
- [ ] 短期凭证：凭证在 `credential_ttl` 内可用、过期后**被拒**；凭证轮换后通话/会议/文件直传/远程/联机五路**均无感**；
- [ ] TURN over TLS：在**只放行 TCP 5349** 的网络环境（模拟企业网）下能成功走中继；
- [ ] TURN-only 进程与 im-server 同机时不抢端口（im-server `turn.enabled: false`，3478/5349/端口段仅 TURN 进程占用）；
- [ ] 内核调优后在「单节点 400 对全中继」压测下无丢包堆积，pps / 出口带宽数据达标定值；
- [ ] 单节点上线（第 1 台）后通话 / 会议 / 文件直传 / 远程协助四路**零回归**。

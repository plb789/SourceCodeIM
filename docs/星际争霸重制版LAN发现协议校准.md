# 星际争霸重制版（SC:R）LAN 发现协议校准

> 2026-10-17 实测校准（pktmon 双机抓包：.15 房主建主 / .25 浏览+进房）。原始抓包（%TEMP% pcapng）
> 已于 2026-10-18 清理——全部协议结论已逐字节消化进本文档，复测路径见 §五。
> 用途：联机大厅 SC:R 适配的设计依据（复用 war3 适配的端口让渡/代理直投底座）。
>
> **2026-10-18 增补**：投递机制微测结论（§四）与自适应反射器终版设计（§三）；同网端到端加入验证通过（§六）。

## 一、端口行为（实测）

| 端口 | 协议 | 用途 | 备注 |
|---|---|---|---|
| UDP 6112 | 游戏/会话 | 独占绑定（`0.0.0.0:6112`），房内对等流量为 **protobuf 直询单播**（无广播） | 提权运行，SO_REUSEADDR 旁路绑定实测 EACCES |
| UDP 5353 | **mDNS 发现** | 加入组播 224.0.0.251，多进程可共存（无需提权） | 适配的切入点 |
| TCP 65044/65045 等回环 | 客户端内部 IPC | 与联机无关 | |
| :443 | Battle.net 在线服务 | 与 LAN 无关 | |

与 War3 1.24 的差异：**不绑 TCP 6112**；发现不走 UDP 广播而走 **mDNS**。

## 二、发现协议（DNS-SD / mDNS，224.0.0.251:5353）

### 1. 服务域名结构

- 服务类型：`_blizzard._udp.local`
- 浏览选择器（PTR 查询）：`_stare9._sub._blizzard._udp.local`（另有 `_pnm._sub._blizzard._udp.local`）
- 实例名：`PNM:<角色名>._blizzard._udp.local`（PNM = Player NaMe，角色名即战网昵称）

### 2. 记录组成

| 记录 | 内容 |
|---|---|
| PTR(33) | `_stare9._sub._blizzard._udp.local` → `PNM:<角色名>._blizzard._udp.local` |
| 66（暴雪私有类型） | **protobuf 属性块**（见下），携带玩家与房间全部信息 |
| TXT(16) | 附加属性 |
| SRV(33) | `PNM:<角色名>...` → 主机名 + 端口 6112（客户端点加入时查询） |
| A(1) | `<主机名>.local` → 本机 IP（客户端解析后直连 UDP 6112） |

### 3. 66 号记录的 protobuf 属性块（逐字节实测样本）

```
0a 0a "attributes"                 # attributes 子消息
12 17 0a 0b "LanToonName" 12 06 <角色名UTF-8>
1a 18 0a 0a "program_id" 12 0a "1398030674"
1a 13 0a 09 "toon_name"  12 06 <角色名UTF-8>
1a 2e 0a 0a "lobby_info" 12 20
    08 <varint>                    # 房间状态
    10 00                          # 字段2
    1a 06 <房主角色名>              # 房间名
    20 01                          # 字段4
    2a 0c "0.0.0.0:6112"           # 连接端点（端口 6112，地址由 A 记录/来源解析）
    1a 20 0a 04 "guid" 12 18 <guid> # 会话 guid
```

另见加入方自身记录带 `filter`（空值）属性——浏览状态标记，用途待验证。

### 4. 发现流程时序（实测）

```
浏览端                          房主端
  │ PTR _stare9._sub._blizzard    │
  │ ────────────────────────────> │ （建主期间周期性应答）
  │ <── 66/TXT: PNM:房主+属性块 ── │
  │ SRV PNM:房主... / A 主机名.local│
  │ ────────────────────────────> │
  │ <── SRV(主机名:6112)/A(IP) ─── │
  │══ UDP 6112 protobuf 直连 ═════│（房间协商与对局，全部直询单播）
```

## 三、适配设计要点（已实施：mDNS 自适应反射器，2026-10-18 终版）

**实现架构（game-mdns.js）——原始记录反射器 + 原生可达性自适应**（曾试作合成应答器：protobuf 属性块
组装的细微偏差致 SC:R 解析崩溃，实测后废弃；曾试作回环单播投递：被先绑定者独收、游戏收不到，实测后废弃）：

1. **房主端（role=host）**：捕获含线格式 `_blizzard` 标签的响应帧（原始记录：PTR/66/
   lobby_info 端点 "0.0.0.0:6112" 等，**房间名/人数/guid 全为真实数据**）→ 原样 hex 经中继链
   （gn-broadcast-gi → 渲染层 → ctl 通道）发加入方；探测激发见第 4 条（自适应启停，
   公布窗口内禁止——实测致「无法公布此游戏[错误5:9]」）
2. **加入方（role=join）——同网/跨网自适应**，判据 = 「原生通告是否可达」这一实测事实
   （不依赖登记 IP：多网卡机器的登记口常非联机口，子网判定曾致误判）：
   - 观测判据：mDNS 应答含本会话 guid（66 号记录 protobuf 内提取）且来源非本机（自源过滤，
     防把注入包的组播回环副本误计为原生通告）
   - **原生在场**（首包中继后 6s 宽限内观测到）：全程静默——原生直连。任何注入记录都会与原生
     记录同实例不同 rdata，SC:R 判冲突拒加入（实测根因）
   - **原生缺席**（宽限期满仍未观测到）：注入补丁记录（仅原地补丁 6 字节：66 号记录端点端口
     6112→隧道端口，同长度改写；A/SRV 补丁为无害空转——SC:R 通告不含这两类记录）+ 缓存应答
     本机查询 + 5s 周期重通告。应答/注入统一延后到宽限期满（宽限期内只听不说，杜绝同网污染）
   - 自愈：注入后原生恢复 → 自动转静默，已注入记录由原生重通告（cache-flush）自然覆盖清除
3. **应答策略（实例级精确匹配）**：ANY/SRV 查询只对缓存内 PTR 指向的实例名应答——不对任意
   `_blizzard` 名应答：本机游戏对自己实例的探测/冲突查询若被回以房主记录会自名冲突（污染其身份）
4. **房主端探测激发（跨网生命线，2026-10-18 增补）**：跨网后加入端浏览查询到不了本机游戏，而
   游戏仅建房时主动通告数秒后归于静默（Bonjour 语义，实测 10s 嗅探零通告）——纯被动监听跨网
   永远无帧可中继（跨网列表为空的实测根因）。故观测到本机游戏应答（=建房完成，避开公布窗口）
   后启动 4s 周期 PTR 浏览查询激发应答（实测本机游戏对查询正常应答 51B/173B，同机来源不拒绝）；
   30s 无应答自动停止。⚠ 探测若在建房公布窗口内运行会干扰公布致「无法公布此游戏[错误5:9]」
   （实测）——全程禁止发布前探测；30s 静默自停保证探测不跨越下一次建房
5. **组播成员多接口加入 + 30s 自愈刷新**：套接字缺省只在「绑定时刻的默认接口」加组，接口切换
   （实测：以太网→手机热点）后成员关系随旧接口失效，本机游戏经新接口发的通告/查询全部收不到
   （捕获静默的实测根因之一）。同套接字对多接口重复加组合法幂等
6. **连接原理**：
   - 原生直连模式：加入方 SC:R 直连房主真实 IP:6112，平台隧道闲置待命（同网实测走此路径）
   - 注入模式：加入方看到的记录与原生逐字节一致（仅端点端口差 1 位数字），连接目标 =
     127.0.0.1:<隧道端口> → 命中现有隧道 → DataChannel → 房主 SC:R:6112
7. **数据层**：现有隧道底座直接复用（UDP 数据面；protobuf 地址无关性已静态验证——5675 帧零地址痕迹）
8. **游戏注册**：后台游戏名须含「星际」（gnGameKind 路由依据）+ 进程 StarCraft.exe
9. **防火墙**：须放行 im-client.exe 的 UDP 5353 入出站（mDNS 组播）

## 四、投递机制实测（Windows，2026-10-18 本机微测）

双套接字同绑 UDP 5353 同段端口（SO_REUSEADDR）+ 加入 224.0.0.251 组，实测投递语义：

| 发送方式 | 本机监听者 | 局域网成员 | 结论 |
|---|---|---|---|
| 组播（TTL 0/255 均同） | ✅ 各得副本（回环副本源 = 真实网卡 IP，非 127.0.0.1） | ✅（TTL 0 仅路由器不转发，同网段仍可达） | **唯一能送达游戏的通道** |
| 单播 → 127.0.0.1 / 本机任一 IP | ⚠ **仅「先绑定者」独收**，后绑定者收不到 | ✅ | 反射器先于游戏绑定 5353 → 单播永远被代理自收 |

由此定案：

1. 旧「回环单播投递」方案失效（加入方房间列表消失）的实证根因 = 单播先绑定者独收，游戏从未收到应答
2. 注入/应答必须走组播；同网段下注入记录房主游戏也会收到 → 同网必须静默（自适应设计的由来）
3. 本机默认组播出口按路由 metric 选定（实测为以太网口而非 205 无线口）——房主游戏原生通告
   同网可达实测成立，推翻「多网卡组播不可达」的早期猜测

## 五、抓包与解析方法（复刻路径）

1. pktmon 提权抓包（UAC + 标记文件控制窗口）：`pktmon filter add SC6112 -p 6112` / 全 UDP：`filter add SCUDP -t udp`
2. `pktmon etl2pcap` 转 pcapng
3. Node 脚本：pcapng 块遍历 → Ethernet/IPv4/UDP → 6112/5353 载荷 → protobuf 字段树 / DNS 记录解码

# 基于Go的即时通信（IM）聊天系统开发方案及开发文档

# 一、项目概述

## 1\.1 项目背景

即时通讯是互联网基础应用，传统IM系统架构复杂、部署成本高、轻量交互场景适配性差。本项目基于Go语言开发服务端，搭配轻量化Web前端客户端，搭建一套高可用的即时通讯系统，支持多客户端在线、实时文字群聊/私聊、大文件稳定传输、在线用户管理等核心功能，具备高并发、低延迟、易部署、可扩展的特点。

## 1\.2 核心功能目标

- **系统基础能力**：服务端高并发处理、异常断线重连、离线消息缓存推送、用户头像自定义上传修改、多端适配（WEB\+PC端同步）、三套主题切换（浅色/深色/跟随系统）、非法消息过滤、日志记录、数据缓存与持久化、**消息高级处理、安全风控、多媒体通信、用户权限管理**

- **用户基础功能**：客户端连接服务端、用户注册登录、上线/下线、在线用户列表实时同步、个人资料编辑、登录态持久化、多设备同时在线管理

- **文字聊天功能**：全员群聊、指定用户私聊、消息实时推送、消息广播、聊天记录持久化、消息已读未读状态、消息撤回、消息删除、聊天记录分页检索

- **多媒体通信功能**：纯文字消息、图片消息、表情包消息、文件传输、超大文件分片续传、预览类文件在线预览

- **消息高级能力**：离线消息推送、消息时序保序、消息去重、本地聊天缓存、云端消息同步、会话置顶、会话清空、消息关键词搜索

- **社交互动能力**：在线状态展示、输入状态实时提示、群成员管理、单聊会话固化、最近会话列表自动维护

- **安全风控能力**：非法敏感词过滤、违规消息拦截、登录异常校验、文件格式\&大小风控、日志溯源审计

- **个性化UI能力**：复刻微信同款界面布局与交互样式、浅色/深色/跟随系统三套主题、用户自定义头像、双端界面精准适配、本地主题偏好持久化、微信风气泡样式、会话列表样式、输入栏功能布局

- **系统运维能力**：全链路操作日志、消息日志、文件传输日志、服务异常捕获、缓存自动清理、数据持久化备份基础能力

- **AI智能问答能力（新增拓展功能）**：内置AI智能问答机器人、私聊AI对话、群聊AI智能应答、上下文记忆、问答日志持久化、AI回复限流风控、适配双端微信风格UI交互

## 1\.3 项目适用场景

小型团队内部即时沟通、局域网实时通讯、轻量化IM功能教学演示、嵌入式设备简易通讯交互、中小型轻量化商用即时通讯场景。

# 二、技术选型方案

## 2\.1 服务端技术栈（Go）

采用Go语言作为服务端核心开发语言，充分利用Go原生优势适配IM高并发场景，搭配MySQL\+Redis实现数据持久化与高性能缓存，核心技术组件如下：

- **核心语言**：Go 1\.21\+，原生支持高并发、协程（Goroutine）、通道（Channel），单机可稳定支撑千级客户端连接

- **网络协议**：服务端兼容**WebSocket** 协议，基于长连接实现浏览器与服务端实时双向通讯，保证消息、文件传输的可靠性和有序性，适配Web客户端场景

- **并发处理**：Goroutine per connection，每个客户端连接独立协程处理，无连接阻塞

- **数据交互**：自定义轻量化消息协议（JSON序列化），兼容文字消息、文件消息、心跳消息、指令消息

- **日志工具**：Go标准库log，记录客户端连接、消息传输、文件操作、异常报错日志

- **文件处理**：原生os、io包，实现文件读取、分片传输、本地缓存、断点续传校验

- **数据存储**：**MySQL 8\.0 \+ Redis 6\.0\+**，持久化核心业务数据、缓存高并发热点数据，兼顾数据安全与响应速度

## 2\.2 客户端技术栈（WEB\+PC双端适配）

系统采用**一套前端代码、双端部署**方案，同时支持**WEB浏览器端**和**PC桌面客户端**，无需分别开发两套业务逻辑，两端功能完全一致、数据实时互通，适配全场景使用需求。WEB端采用原生HTML\+CSS\+JavaScript开发，PC端基于Electron打包Web页面实现桌面客户端能力，零额外开发成本、跨平台、可打包exe安装程序，完美兼容原有WebSocket通信、数据库交互逻辑。

摒弃传统桌面客户端，采用**原生HTML\+CSS\+JavaScript**开发纯Web客户端，零安装、跨全平台、交互体验更佳，适配电脑/平板浏览器，无需编译打包，打开网页即可使用，选型如下：

- **页面结构（HTML5）**：搭建登录页、聊天主页面、用户列表模块、文件传输弹窗，语义化标签构建清晰页面结构，适配不同浏览器窗口尺寸

- **样式美化（CSS3）**：实现现代化IM界面、气泡聊天样式、滚动美化、进度条动画、弹窗过渡效果，适配深色/浅色基础样式，界面简洁美观

- **核心交互（原生JS）**：处理网络通信、消息渲染、用户列表刷新、文件上传下载、进度实时更新、断线重连逻辑，无需框架，轻量化无冗余

- **网络通信（WebSocket）**：替换传统Socket TCP，采用WebSocket长连接，基于HTTP握手后持久化双向通信，完美适配浏览器环境，兼容Go服务端双向数据推送

- **辅助能力**：异步非阻塞渲染、页面无刷新更新数据、文件分片前端处理、本地聊天缓存、浏览器状态栏提示

- **双端架构适配**：Electron打包适配PC桌面端，保留全部Web端功能，支持窗口置顶、桌面通知、离线后台运行、exe安装部署，与WEB端共用同一套服务端接口与消息协议，实现多端账号同步、消息互通

## 2\.3 数据库选型论证（MySQL\+Redis）

**结论：MySQL\+Redis 组合完全可行，是中小型IM系统的黄金搭配**，解决纯内存数据易丢失、持久化数据库并发低的痛点，适配IM高并发、热数据高频读写、冷数据持久留存的核心特性。

### 2\.3\.1 分工策略（读写分离、冷热分离）

- **Redis（热点缓存、高性能读写）**：内存数据库，负责存储高频读写的临时数据，支撑IM实时交互高并发场景，读写毫秒级响应。主要存储：在线用户列表、用户WebSocket连接状态、心跳缓存、临时文件分片进度、当前会话缓存、用户在线权限缓存。

- **Redis（热点缓存、高性能读写）**：内存数据库，负责存储高频读写的临时数据，支撑IM实时交互高并发场景，读写毫秒级响应。主要存储：在线用户列表、用户WebSocket连接状态、心跳缓存、临时文件分片进度、当前会话缓存、用户在线权限缓存、**离线消息队列缓存**。

- **MySQL（持久化存储、数据落地）**：关系型数据库，负责存储需要永久留存的核心业务数据，保证数据不丢失、可追溯。主要存储：用户账号信息、**用户头像资源信息**、历史聊天记录、离线消息记录、文件传输记录、用户基础配置、系统操作日志。

### 2\.3\.2 选型优势

1. **解决核心痛点**：纯内存架构服务端重启后所有用户数据、会话数据全部丢失，搭配MySQL持久化、Redis缓存，实现重启数据不丢失、在线状态快速恢复。

2. **高并发适配**：IM系统在线状态、心跳检测、用户列表刷新为超高频操作，Redis内存读写性能远超MySQL，避免数据库频繁读写导致卡顿。

3. **数据可靠**：聊天记录、文件记录核心数据通过MySQL落地，支持历史记录查询、数据回溯、故障恢复，满足基础业务合规性。

4. **成本极低、适配性强**：双组件部署简单、资源占用低，适配轻量化IM项目，同时支持后续功能迭代扩展。

5. **Go完美适配**：Go拥有成熟的MySQL（gorm）、Redis（go\-redis）第三方库，连接池稳定、并发处理安全，无协程冲突问题。

### 2\.3\.3 缓存一致性策略

- 新增/更新数据：先更新MySQL，再更新Redis缓存，保证热数据实时同步

- 用户下线/连接断开：主动删除Redis对应在线状态缓存，留存离线消息队列缓存

- 服务启动初始化：从MySQL加载用户基础信息、头像配置，预热Redis在线缓存与离线消息缓存

- 过期清理：Redis设置键值过期时间，自动清理超时无效的心跳、分片缓存；**离线消息缓存设置合理过期周期，避免资源堆积**

## 2\.4 整体架构优势

1. **高并发低延迟**：Go协程轻量化\+Redis内存缓存，百万级协程开销极低，完美适配IM多连接、高刷屏场景

2. **数据高可用**：冷热数据分离，缓存保速度、数据库保安全，杜绝数据丢失问题

3. **部署极简**：Go服务端可编译为单可执行文件，MySQL、Redis单机即可部署，无复杂集群依赖

4. **稳定性强**：WebSocket长连接\+自定义心跳机制，规避死连接、无效缓存占用资源

5. **扩展性高**：前后端完全解耦，一套代码适配WEB浏览器、PC桌面端，可快速拓展移动端、小程序，数据库架构支持后续功能无缝迭代

# 三、系统整体架构设计

## 3\.1 架构模式

采用**服务端中转C/S架构 \+ 冷热数据分离存储架构**，所有客户端不直接点对点通信，统一通过Go服务端中转消息和文件数据；热数据缓存至Redis、冷数据持久化至MySQL，架构简洁、易管控、无端口穿透问题，适配局域网/公网部署。

架构层级：Web客户端层 → WebSocket网络传输层 → Go服务端调度层 → Redis缓存层 → MySQL持久化层

## 3\.2 核心模块拆分

### 3\.2\.1 服务端核心模块

- **连接管理模块**：监听WebSocket端口、接受客户端连接、维护在线客户端列表、处理断线/重连、清理无效连接

- **消息调度模块**：解析客户端消息、区分群聊/私聊消息、广播消息、消息格式校验、非法消息过滤

- **文件传输模块**：接收客户端文件分片、缓存文件数据、中转文件至目标客户端、校验文件完整性、断点续传处理

- **心跳检测模块**：定时检测客户端存活状态，自动离线超时无响应客户端，释放服务端资源

- **日志管理模块**：记录所有连接、消息、文件操作、异常信息，支持日志持久化

- **数据存储模块**：MySQL数据增删改查、用户头像资源管理、离线消息持久化、Redis缓存读写、数据一致性维护、初始化缓存预热

### 3\.2\.2 客户端核心模块

- **连接模块**：主动连接服务端、断线自动重连、心跳发送、连接状态展示

- **聊天交互模块**：用户输入文字、发送群聊/私聊消息、展示聊天记录、在线用户列表刷新、历史记录加载

- **文件操作模块**：本地文件选择、文件分片发送、接收服务端中转文件、进度展示、文件保存

- **界面UI模块**：Web端登录页面、聊天窗口、在线用户侧边栏、个人中心头像编辑\&资料设置面板、主题切换面板、文件传输进度弹窗、系统消息提示、聊天记录滚动渲染、会话列表模块、消息搜索面板；PC端适配桌面窗口布局、系统通知、快捷键操作、主题全局同步、托盘后台运行、系统级消息弹窗

## 3\.4 Redis缓存键值设计

- **在线用户缓存**：key=im:online:username，value=连接状态，过期时间120s，配合心跳自动续期

- **文件分片缓存**：key=im:file:chunk:fileid，value=已传输分片集合，用于断点续传校验

- **用户会话缓存**：key=im:session:username，value=最近会话信息，提升页面加载速度

# 四、核心功能详细设计

## 4\.1 用户连接与状态管理

1. **连接流程**：服务端启动预热Redis缓存、加载MySQL用户数据 → 客户端输入用户名\+服务端IP端口发起连接 → 服务端校验用户名（MySQL查重） → 连接成功，写入Redis在线缓存、加入在线用户列表 → 广播全员【用户上线】通知

2. **心跳检测机制**：客户端每30秒发送一次心跳包，服务端更新Redis用户在线缓存过期时间；超过90秒未接收心跳则判定客户端离线，删除Redis缓存、断开连接、广播下线通知、更新在线列表

3. **断线重连**：客户端检测连接断开后，自动发起重连请求，重连成功后读取MySQL历史会话数据、恢复Redis在线缓存，**服务端批量推送离线消息**，同步在线状态与聊天记录

4. **登录失败提示保障（阶段三十四）**：密码错误等登录失败场景，服务端**同步写**错误消息送达客户端后再关闭连接（绕过发送队列，消除异步队列与立即关连接的竞态丢消息），前端 Toast 展示"用户名或密码错误"；用户名不存在与密码错误区分判定（ErrUserNotFound/ErrInvalidLogin），仅用户不存在时触发"首次登录自动注册"，避免密码错误被误导提示"用户名已存在"；前端仅在登录成功后断线才自动重连（携带真实密码），登录失败不重连，杜绝"失败→重连→失败"无限循环

5. **登录链路稳定性加固（阶段三十四·回归检查）**：连接写互斥锁串行化 writePump 队列写与登录失败同步写，杜绝 gorilla 并发写 panic；MySQL 连接池配置连接寿命上限（ConnMaxLifetime/ConnMaxIdleTime）+ 后台 30 秒定时 Ping 保活，消除"MySQL 断开空闲连接后首次查询报 invalid connection"问题；登录错误分级下发——业务校验错误（用户名或密码错误等）原样展示，底层依赖错误统一下发"登录服务暂不可用，请稍后重试"并记日志，保证客户端只见中文提示

## 4\.2 文字聊天功能设计

### 4\.2\.1 群聊功能

客户端发送msg\_type=1的消息，to\_user为空，服务端接收后先写入MySQL消息表持久化，再遍历Redis在线用户缓存，将消息广播至全员，所有客户端展示群聊内容、发送人、发送时间。

### 4\.2\.2 私聊功能

客户端选择指定在线用户，发送msg\_type=2的消息，携带目标to\_user，服务端先持久化至MySQL，再精准转发消息至指定用户，其他用户无法接收，实现私密聊天。

### 4\.2\.3 历史消息分页加载与串窗归属校验（阶段二十七）

1. **向上滚动加载更多（对齐微信体验）**：切换会话时加载最近20条历史（PAGE_SIZE统一常量）；消息列表监听scroll事件——滚动到顶部附近（scrollTop≤60）且无翻页请求进行中、还有更多历史时，自动请求下一页（page=historyPage+1）。服务端按ID倒序返回，前端将更早消息prepend插入列表最前（复用renderHistoryRecord的beforeEl能力，文字/图片/文件/撤回提示统一支持），并以scrollHeight差值补偿scrollTop保持视口不跳动；返回条数不足一页判定已到最早记录，停止向上加载。

2. **切换会话分页状态重置**：openConversation切换会话时重置historyPage=1、historyHasMore=true、loadingMore=false，从第1页重新加载；翻页请求响应沿用historyTarget/currentChatUser双重归属校验，会话切换期间的过期响应自动丢弃。修复背景：原实现切换会话仅加载最近20条且无向上翻页机制，实时消息与登录离线补发累积超过20条后，切换会话再切回窗口按"最近20条"重渲染，更早内容从窗口消失且无法再查看（用户感知为"之前的聊天记录没了"）。

3. **定位翻页与滚动翻页状态归口**：置顶条/搜索定位（locateState）向前翻页加载的页数同步计入historyPage（取最大值），翻到最早记录时同步置historyHasMore=false，防止定位加载过早期数后向上滚动从旧页码重复请求造成消息重复渲染。

4. **实时消息串窗归属校验**：GROUP_CHAT群聊消息处理器补currentChatUser拦截（群聊消息仅在群聊视图渲染，与GROUP_IMAGE口径一致）；ONLINE上下线提示补归属校验（群聊视图显示全部成员上下线，私聊视图仅显示会话对方）。原实现无校验，私聊视图打开时收到的群聊消息/他人上下线提示被串入当前窗口，切换会话后"消失"，造成内容丢失的错觉。

## 4\.3 文件传输功能设计

采用**分片传输\+服务端中转\+数据落地**方案，解决大文件传输卡顿、丢包、记录丢失问题，支持任意格式文件（图片、文档、压缩包等）。

1. **文件分片**：客户端将本地文件按4KB固定大小分片，生成分片序号和总分片数

2. **消息通知**：发送方先发送文件头消息（文件名、文件大小、总分片数、目标用户），服务端写入MySQL文件记录表，初始化Redis分片缓存

3. **分片中转**：客户端逐片发送文件二进制数据，服务端接收后实时中转至目标客户端，同步更新Redis已传输分片记录

4. **文件拼接**：接收方按分片序号有序拼接数据，传输完成后校验文件大小，确认文件完整性

## 4\.4 新增核心功能详细设计

### 4\.4\.1 离线消息功能设计

系统完整支持**用户离线消息缓存、持久化、上线自动推送**，用户下线期间他人发送的私聊、群聊消息不会丢失，上线后一次性批量接收，完全贴合主流IM使用逻辑。

1. **离线判定逻辑**：服务端通过Redis在线缓存判定用户状态，若目标用户无在线缓存、连接已断开，判定为离线状态。

2. **消息存储逻辑**：发送方发送消息后，服务端正常写入MySQL消息表持久化，同时将消息加入**目标用户专属Redis离线消息队列**，按时间顺序排序，避免消息乱序。

3. **上线推送逻辑**：离线用户重新连接登录成功后，服务端优先读取该用户Redis离线消息队列，批量推送所有未读离线消息至客户端；推送完成后清空对应Redis离线缓存，保证消息不重复、不遗漏。

4. **过期兜底策略**：离线消息缓存设置7天有效期，过期未上线的消息保留MySQL持久化记录，用户后续可通过历史记录查询加载，彻底杜绝消息丢失。

5. **消息唯一性保障**：每条离线消息绑定唯一时间戳与消息ID，推送时客户端自动去重，规避重连重复推送问题。

### 4\.4\.2 用户头像自定义上传与修改功能

系统原生支持**用户头像上传、在线修改、持久化存储、全局展示更新**，前端提供可视化头像编辑入口，服务端完成文件校验、存储、数据库更新，所有聊天场景实时展示最新头像。

1. **前端交互逻辑**：Web客户端新增个人中心模块，支持点击头像、选择本地图片上传，实时预览裁剪，提交后发起头像更新请求；支持随时重复修改、替换原有头像。

2. **服务端校验逻辑**：接收头像图片文件，校验文件格式（仅支持jpg、png、gif）、文件大小（限制最大5MB），过滤非法文件，保证系统安全。

3. **资源存储逻辑**：头像文件统一存储在服务端专属静态资源目录，生成唯一文件名防止覆盖；旧头像资源可保留或按需清理，避免资源冗余。

4. **数据更新逻辑**：头像上传成功后，服务端更新MySQL用户表avatar字段，写入最新头像访问路径，同步更新用户缓存信息。

5. **全局同步逻辑**：头像修改成功后，服务端广播用户信息更新通知，所有在线客户端刷新对应用户头像展示，私聊、群聊消息气泡同步更新最新头像。

6. **双端加载优化**：两端统一缓存用户头像、会话信息资源与主题配置，避免重复请求加载，提升页面渲染速度；PC端额外支持本地缓存持久化，重启应用保留用户主题偏好、快速恢复聊天界面。

7. **无头像降级策略（阶段三十三）**：新注册账号 avatar 为空，全部头像展示位统一降级为**账号首字母占位**（跟随主题色，禁止出现破图碎图标）——会话列表/消息气泡走 buildAvatarPlaceholder，导航栏左上角与个人资料面板大头像走 setNavAvatar/setProfileAvatar 统一入口；头像图片加载失败（文件被清理/路径变更）时 img 挂 error 监听自动降级占位。img 元素不允许携带空 src 属性（浏览器会渲染为破图并误触发 error）。

### 4\.4\.3 个人资料面板与好友资料卡（阶段三十，微信式）

系统支持微信同款**个人资料编辑**与**好友资料卡查看**，资料数据服务端归口（昵称/性别/地区/签名存储于 im\_user 表，好友关系与备注由 im\_friend 表服务端判定），多端实时同步。

1. **个人资料面板**：点击左上角头像从右侧滑出资料面板（微信"我的个人资料"同款布局：头像大图 hover 相机角标、昵称、微信号=用户名只读、性别三段选择、地区、签名）；面板内点击大头像触发换图（复用 /upload/avatar 通道，导航栏/消息气泡/面板大头像三处同步更新）；保存经 PROFILE\_UPDATE（msg\_type=37）提交，服务端校验性别合法性与字段长度后落库，并向本人全部在线连接回推 PROFILE\_RESP（msg\_type=39）实现多端同步。

2. **登录资料恢复**：LOGIN\_RESP（msg\_type=8）content JSON 追加 profile 完整资料字段，登录即恢复面板状态，无需二次查询。

3. **好友资料卡**：点击消息气泡头像/好友列表头像（点自己则打开资料面板）弹出微信式居中资料卡——先占位"加载中"，PROFILE\_QUERY（msg\_type=38）响应后填充：名称按"备注 > 昵称 > 用户名"优先级展示（括号补充用户名）、性别图标（♂蓝/♀粉）、微信号、地区、签名；好友关系与备注由服务端归口判定（is\_friend/remark），非好友可见基本资料但不显示"设置备注"按钮；卡片附"发消息"（切换会话）与"设置备注"（复用自定义输入弹窗 + FRIEND\_UPDATE 通道）按钮。

4. **交互细节**：资料面板遮罩点击/Esc/× 均可关闭，层级资料面板 1600/1650 < 资料卡 1700 < 确认弹窗 2000 < Toast 3000；样式全部跟随主题色变量，小屏内容区滚动复用全局自定义滚动条。

1. **数据模型**：新增`im_msg_pin`置顶消息表（id、conv\_key、msg\_id、pin\_user、create\_time），`conv_key`为会话唯一键：群聊固定`group`，私聊按双方用户名字典序拼接`userA|userB`，同一会话双方计算结果一致；每会话仅保留一条置顶消息，新置顶自动替换旧置顶。

2. **置顶校验**：服务端校验被置顶消息存在且未撤回、消息归属当前会话（群聊消息或双方互发的私聊消息），非法请求直接拒绝。

3. **多端同步**：置顶/取消后服务端按会话键推送最新状态（msg\_type=30，content为JSON）：群聊广播全体成员，私聊按双方各自视角推送（target为对方用户名，msg\_id=0表示无置顶）；用户登录时批量补发全部相关会话的置顶状态，重连/重登自动还原。

4. **撤回联动**：被置顶消息撤回时，服务端自动删除置顶记录并推送取消状态，避免置顶条展示已撤回内容。

5. **前端交互**：聊天窗口顶部置顶消息条（发送者+消息内容+取消置顶按钮），消息右键菜单动态显示「置顶/取消置顶」，样式跟随三套主题。

6. **置顶幂等（阶段十三深化增强）**：服务端归口去重——重复置顶同一消息时跳过写库与同步（提示"消息已在置顶中"），无置顶记录时取消置顶跳过删库与同步，防止重复操作引起的冗余写库与双方全部设备的重复推送；前端 MSG\_PIN\_SYNC 处理增加兜底去重，同步内容与现有状态完全一致时跳过更新与重渲染，防重复同步引起置顶条闪烁。

7. **置顶联动清理（阶段十五二次深化增强）**：置顶者侧数据变更时服务端自动联动取消置顶并同步双方全部设备——置顶者删除置顶消息（`handleDelete` 校验删除者=`pin_user` 且消息=`pin.MsgID`）、置顶者清空会话（`handleConvClear`）、置顶者删除会话（`handleConvDelete`）均联动删除 `im_msg_pin` 记录并经 `syncPinByKey` 推送取消状态；非置顶人执行删除/清空/删除会话不联动（置顶保留）。配合撤回联动与登录补发以数据库为真值来源，彻底杜绝孤儿置顶（置顶条悬空指向已删除/已清空内容）。

8. **置顶条点击定位原消息（阶段十五前端体验增强）**：置顶条内容区（`pin-bar-main`）增加点击事件与手型光标提示，复用会话内搜索的定位高亮机制——目标消息已加载时直接滚动居中并高亮（2 秒主题色渐隐动画）；未加载时经 `locateState` 从第 2 页起向前翻页查找，直至定位到目标消息，原消息不可见时由翻页上限兜底提示。点击「×」取消置顶与点击定位互不干扰。阶段十六增强：`locateState` 增加 `src` 来源标记（pin=置顶条/search=搜索结果），定位失败时按来源提示精确原因——置顶条场景提示"原消息已删除或不可见"（历史接口排除已删除与已撤回消息）或"原消息超出可加载范围，未能定位"，搜索场景保持原提示。

9. **关系终止联动清理（阶段十六三次深化增强）**：删除好友（`handleFriendDelete`）与拉黑（`handleBlacklist` block，先解除好友关系）时调用 `clearPinForConv` 整条清理该会话置顶记录并经 `syncPinByKey` 同步双方全部设备——关系终止属会话级事件，无论置顶人是谁均清理；取消拉黑不恢复置顶（一次性清理，不逆）。配合登录补发以数据库为真值来源，关系终止后重登不再还原置顶条，孤儿置顶场景闭环。

### 4\.9\.2 会话内消息搜索与定位高亮（msg\_type=31/32）

1. **搜索范围**：仅在当前聊天窗口对应会话内检索（私聊为双方互发消息，群聊为全体群消息），排除已撤回与自己删除的消息，关键词LIKE通配符转义防注入，按消息ID倒序最多返回50条。

2. **搜索浮层**：聊天头部搜索按钮唤起覆盖式搜索浮层，回车发起搜索，结果列表展示发送者、时间、内容摘要，支持空结果提示「暂无匹配的聊天记录」、Esc快捷关闭、切换会话自动清空。

3. **定位高亮**：点击搜索结果后，若消息已在窗口内直接滚动居中并高亮；若消息未加载则复用历史消息分页接口向前翻页加载（prepend渲染保持时间正序），直至定位到目标消息；高亮采用主题色2秒渐隐动画，定位过程对用户无感。

4. **数据归口**：搜索与定位全部基于服务端`im_message`表统一检索，客户端仅展示服务端返回数据，保证多端搜索结果一致。

## 4\.10 多端同时在线与消息同步架构设计（新增商用级拓展功能）

支撑同一账号 WEB、PC 多设备同时在线，消息、已读状态、未读数、置顶、会话、撤回全部实时同步，服务端统一归口。

### 4\.10\.1 连接层：多连接 Hub 架构

1. **连接集合管理**：Hub 由"用户名->单一连接"升级为"用户名->连接集合"（`map[string]map[*Client]bool`），同一账号新设备接入不踢旧连接，多端共存。

2. **连接级注销**：连接断开按连接对象移除（`Remove(c)` 返回剩余连接数），彻底消除旧连接断开误删新连接的竞态问题；仅最后一个连接断开时才判定离线（删除 Redis 在线缓存、广播下线通知），其余设备断开不影响在线状态。

3. **上线通知去重**：仅首个设备上线时广播上线通知（`hub.Count==1` 判断），多端重复登录不重复广播；在线用户列表按用户名去重。

### 4\.10\.2 推送层：sendToUser 多端同步归口

所有定向推送统一通过 `sendToUser(用户名, 数据)` 遍历该用户全部在线连接发送：

1. **私聊消息**：接收方全部设备实时收到；发送方全部设备同步回显（多端消息视角一致）。
2. **已读回执（msg\_type=13）**：读取方发送已读水位后，服务端归口更新 `im_message.is_read`，回执转发给对方全部设备（对端任一设备查看气泡均显示"已读"）；同时刷新读取方全部设备的会话列表（未读角标多端同步清零）。服务端基于会话行 `last_read_id` 水位去重，仅水位前进才写库+转发+推送，杜绝多端重复回执风暴（详见4.10.4）。
3. **消息撤回（msg\_type=14）**：撤回通知推送双方全部设备；群聊撤回广播天然多端。通知携带原始消息接收方 `to_user`（群聊为空）供前端归属校验；服务端撤回幂等（已撤回消息拒绝重复撤回），杜绝重复通知。撤回时间窗口由服务端配置 `recall_window` 归口判定，登录响应下发该参数供前端菜单动态显隐。
4. **撤回摘要联动**：撤回后服务端重算相关会话行摘要（撤回最后一条可见消息时显示"[消息已撤回]"，撤回中间消息时重算为最新可见消息内容），修正后推送双方全部设备多端同步；离线期间被撤回的消息以数据库 `recalled` 状态为准不再补发，撤回提示由历史加载统一渲染。
5. **消息置顶（msg\_type=30）**：置顶状态同步推送双方全部设备，登录时批量补发。
6. **会话列表（msg\_type=18）**：会话新增/未读/摘要变更推送用户全部设备。
7. **好友与申请**：好友列表刷新、好友申请实时推送全部设备；申请同意/拒绝结果同步推送申请方全部设备（阶段二十九，详见4.10.7）。
8. **文件传输**：文件头与分片中转接收方全部设备（每设备独立拼装下载）；输入状态提示推送全部设备。
9. **AI 回复**：私聊 AI 问答回复推送用户全部设备。

### 4\.10\.3 离线与在线判定

1. **在线判定**：依据 Redis 在线缓存（120s 心跳续期），任一设备心跳维持即判定在线；多端在线期间消息实时推送、不入离线队列。
2. **离线队列**：最后一个设备离线后消息入 Redis 离线队列（7 天），下次任一设备登录时批量补发并清空；后登录设备可通过会话云端历史查看全部消息。

### 4\.10\.4 已读回执水位与未读数服务端归口（阶段十一深化增强）

1. **回执水位去重**：`im_conversation` 表新增 `last_read_id` 字段（该用户在其会话中已读到的对方最大消息 ID）。服务端处理已读回执（msg\_type=13）时仅当新回执 ID 大于当前水位才执行：落水位 → 批量更新 `is_read` → 转发回执对方全部设备 → 推送读取者全部设备会话列表；水位未前进（重复回执/水位回退）直接跳过，彻底杜绝多端同时打开同一会话重复发送回执造成的回执风暴（重复写库、重复转发、重复推送）。
2. **会话清空/删除联动回执**：会话清空（msg\_type=27）、会话删除（msg\_type=28）时未读清零同步提升 `last_read_id` 至对方消息最大 ID（水位仅前进不回退），并转发回执对方全部设备，发送方实时看到"已读"；重复清空因水位不再前进不会重复转发。
3. **未读数单一归口**：前端删除本地 `unreadCount` 计数，会话列表角标与好友列表角标统一渲染服务端 `CONV_LIST` 推送的 `unread` 字段（同源数据），任一设备读取后服务端推送即同步清零全部设备角标；前端打开会话时本地乐观清零提升体验，服务端归口推送随后确认。文件消息不入 `im_message` 表（服务端未读统计不覆盖），前端仅在本地会话列表乐观 +1 提示，服务端推送到达时归口覆盖。
4. **已读水位客户端双保险**：前端维护 `sentReadId`（已发送回执水位，仅水位前进才发送回执）与 `readWatermark`（对方已读水位，任一连接收到的回执都记录、跨会话保留），历史渲染时叠加本地水位即时显示"已读"，解决回执先于会话打开到达被丢弃、重开会话需等服务端 `is_read` 才能显示的体验问题。

5. **未读数排除已删除消息（阶段十四深化增强）**：私聊未读数统计排除接收方已删除的消息（子查询 `im_msg_delete` 过滤），删除消息"仅对自己生效"的语义与未读角标保持一致，重登后角标不虚高；服务端单一归口，多端渲染一致。

6. **删除未读消息联动角标（阶段十四深化增强）**：`handleDelete` 判定被删除消息为对方发来的未读私聊消息时，主动推送会话列表（`notifyConvUpdate`）到删除者全部在线连接，未读角标实时递减；删除已读消息不推送，避免无意义的会话列表刷新。

7. **登录补发对端已读水位（阶段十四深化增强）**：登录时服务端遍历用户全部私聊会话，以 MSG.READ（from\_user=对端、content=对端已读我方最大消息 ID）形式补发已读水位，复用前端现有已读处理（幂等，水位前进才更新）；重连/重登后本地 `readWatermark` 即时恢复，历史渲染叠加水位即时显示"已读"，不再依赖实时回执到达。

### 4\.10\.5 消息撤回深化增强：撤回幂等、归属校验与窗口配置修复（阶段十二）

1. **撤回幂等（服务端归口）**：`handleRecall` 在时间窗口校验后增加 `recalled` 状态校验，已撤回消息拒绝重复撤回（返回"该消息已撤回，请勿重复操作"错误提示），防止重复撤回通知（多端重复系统提示）、重复摘要刷新与重复置顶清理；前端按 `msg_id` 维护 `processedRecalls` 已处理表兜底去重，同一撤回通知到达两次不追加重复提示。

2. **撤回通知归属字段与会话校验**：撤回通知增加 `to_user` 字段（原始消息接收方，群聊为空），前端据此校验消息归属——私聊撤回归属对端会话（自己撤回则为接收方，否则为发送方），群聊撤回归属群聊；非当前查看会话的撤回通知不渲染（仅服务端落库与 CONV_LIST 同步），彻底杜绝撤回提示误渲染进当前打开的无关会话窗口（跨会话串窗）。

3. **撤回窗口配置生效修复**：`socket.js` 的 `recallWindow` 原未声明（隐式全局）且未暴露 `getRecallWindow`，服务端登录响应下发的 `recall_window` 配置从未被前端使用（撤回菜单恒用 120 秒兜底）；修复为声明变量并暴露 `getRecallWindow()`，撤回菜单显隐与配置文件 `recall_window` 参数保持一致（前端预留 10 秒网络余量）。

4. **撤回链路多端一致性**：撤回幂等保证同一消息仅产生一次通知与一次摘要联动；摘要联动（撤回最后一条可见消息显示"[消息已撤回]"、撤回中间消息重算为最新可见内容）推送双方全部设备；未读数随撤回经 CONV_LIST 归口重算（已撤回消息不计入未读），全部设备角标同步。

5. **撤回摘要联动判断修复（阶段二十四验证发现）**：`refreshConvSummaryAfterRecall` 原以 `latest.ID != record.ID` 判断"存在更新的可见消息"，但被撤回消息已先标记 recalled（查询条件 recalled=false 必不返回自身），条件恒为真，导致撤回"最后一条可见消息"时误用更早的历史消息重算摘要（如显示旧消息内容/\[图片\]）而非"\[消息已撤回\]"；修正为 `latest.ID > record.ID`——仅当存在比被撤回消息更新的可见消息（即撤回的是中间消息）才重算摘要；私聊摘要查询同步纳入图片(4)/文件(5)消息类型并按类型转换摘要文本（\[图片\]/\[文件\]）。

6. **实时图片/文件气泡撤回能力补全（阶段二十四遗留边界闭环）**：①`appendImageMsg`/`appendFileMsg` 补设 `data-from`/`data-ts` 属性（原缺失导致撤回菜单"本人发送"判断恒为 false，实时图片/文件气泡回填 msg\_id 后右键仍无撤回项）；②新增协议 **33\-文件持久化同步（FILE_PERSISTED）**：服务端持久化落库成功后向双方全部在线连接推送 file\_id+msg\_id，双方实时气泡按 file\_id 精确回填 msg\_id（发送方气泡在文件头回执时记录 data-file-id，接收方 blob 组装渲染时同样记录），撤回/删除/置顶能力与撤回提示替换原气泡随之可用；③HTTP 上传响应回填逻辑废弃（注释保留），msg\_id 回填统一归口 WS 通知，杜绝并发发送多文件时"最后一条无 msg\_id 气泡"推测错位，对齐服务端统一归口原则。

7. **验证记录（双账号 uitestA/uitestB 实测）**：文字撤回最后一条可见消息→双方会话摘要"\[消息已撤回\]"；撤回中间消息→摘要重算为最新可见"撤回验证三"；图片撤回→A端"你撤回了一条消息"、B端"uitestA 撤回了一条消息"（原图片气泡替换无残留，双端 bubble-image 数量一致）、摘要"\[消息已撤回\]"；窗口外撤回已撤回消息→"超过撤回时间限制的消息无法撤回"（窗口校验先于幂等校验）；窗口内重复撤回→"该消息已撤回，请勿重复操作"；非本人消息右键无撤回项（删除项可见）；全程无 JS 报错；数据库核对 fileID→msg\_id 落库、recalled=1、摘要归口均正确。

### 4\.10\.7 好友申请微信式"新的朋友"归口（阶段二十九）

1. **背景与根因**：好友申请的服务端链路（在线实时推送 + 离线登录补发）本身正常，但前端通知仅为一个临时确认弹窗——可被随手关闭或被后续申请覆盖，关闭后申请无处可寻，接收方感知为"没收到加好友消息"；且无微信式入口/红点/申请列表，错过即失联。

2. **申请列表归口查询（msg\_type=35/36）**：前端点击"新的朋友"入口或收到新申请（防抖合并）时请求申请列表，服务端 `handleFriendReqList` 查询本人收到的全部申请记录（含已同意/已拒绝历史，微信同款）并附申请方头像，返回 JSON `list + pending`（待处理数量），角标数据服务端统一归口。

3. **微信式通知链路**：①接收方收到申请（实时或登录补发）→ Toast"X 请求添加你为好友"+ 通讯录导航图标与"新的朋友"入口条双红点角标（服务端 pending 数，99+ 封顶）；②申请列表浮层（覆盖式，样式跟随主题色）逐条展示头像/用户名/验证消息/时间，待处理行带"同意/拒绝"按钮，处理后服务端归口刷新列表与角标（pending 递减、行内状态更新为"已同意/已拒绝"）；③处理结果同步：服务端向申请方全部在线连接推送 FRIEND\_REQUEST\_RESP（from\_user=处理人），申请方 Toast"X 已同意/拒绝你的好友申请"，好友列表经 FRIEND\_LIST 刷新随之出现新好友。

4. **多端一致性**：申请推送、列表归口、结果同步均经 `sendToUser` 覆盖用户全部在线连接；登录补发沿用 `pushPendingRequests`（status=0 且 create\_time 早于本次登录），重复申请按申请记录 ID 去重；已结为好友或存在拉黑关系时申请被服务端拦截（"对方已是你的好友"）。

5. **验证记录（Go 双端探针 5/5 + 浏览器双账号 5/5）**：探针覆盖在线实时推送、列表归口 pending 数量、同意后申请方同步、pending 递减、离线登录补发；浏览器覆盖 Toast+角标实时显示、列表同意操作与角标联动消失、申请方结果同步与好友列表更新、连续多申请不覆盖、离线补发，全程无 JS 错误。

## 5\.2 核心配置参数

- 服务WebSocket监听端口：8888

- 心跳超时时间：90s

- 文件分片大小（chunk_size）：65536Byte（64KB），服务端归口，登录响应（msg\_type=8）JSON 下发 chunk\_size 字段供前端自适应；原 4096Byte（4KB）在大文件场景产生海量 WS 消息与 Redis 操作（20MB 文件需 5120 片），64KB 后消息数降 16 倍

- 最大在线连接数（max\_connections）：10000，服务端 HandleWS 升级握手前实际校验，达到上限拒绝新连接

- 单连接发送队列缓冲（send\_queue\_size）：1024 条，文件分片与聊天消息共用队列，过小会溢出丢消息

- 大文件直传阈值（http\_upload\_threshold）：1048576Byte（1MB），超过该值前端自动分流 HTTP 直传链路（服务端流式落盘），WebSocket 仅传信令

- 单请求直传上限（max\_file\_size）：20971520Byte（20MB），阶段三十二起语义调整为"单请求 HTTP 直传的上限"；超过该值走分片直传链路

- 分片直传单片大小（upload\_chunk\_size）：4194304Byte（4MB），分片直传链路单片大小，服务端归口下发（LOGIN_RESP 携带 upload\_chunk\_size），单片请求体超限（含 1KB 容差）即拒绝

- 分片直传文件上限（max\_direct\_size）：2147483648Byte（2GB），超过直接拒绝发送；服务端归口下发（LOGIN_RESP 携带 max\_direct\_size）

- 消息撤回时间窗口（recall_window）：120s，仅该窗口内自己发送的消息可撤回；服务端从bin/config.yaml读取，缺省自动回退默认值，登录响应（msg_type=8）以JSON形式下发该参数供前端撤回菜单动态适配

- MySQL配置：单机本地连接、默认端口3306、支持连接池复用

- Redis配置：单机本地连接、默认端口6379、缓存过期自动清理

## 5\.3 核心代码逻辑说明

### 5\.3\.1 服务启动与数据库初始化

程序启动优先初始化MySQL、Redis连接池，校验数据库连通性，自动创建数据表（首次启动）；从MySQL加载所有用户基础信息，预热Redis在线缓存，初始化WebSocket监听服务。

### 5\.3\.2 消息处理与持久化逻辑

服务端接收客户端消息后，先完成参数校验，合法文字/文件消息同步写入MySQL持久化存储，再根据消息类型执行广播/私聊中转逻辑；所有消息操作日志落地数据库，支持后续追溯查询。

### 5\.3\.3 缓存调度逻辑

用户上下线、连接状态变更实时同步Redis缓存；高频查询的在线用户列表、会话信息优先从Redis读取，规避频繁查询MySQL造成的性能损耗；超时无效缓存自动过期清理，释放内存资源。

# 七、系统运行流程全梳理

## 7\.1 系统启动流程

1. 启动MySQL、Redis服务，保证数据库正常运行

2. 运行Go服务端程序，初始化数据库连接、创建数据表、预热缓存、监听8888端口

3. 多客户端启动，输入自定义用户名和服务端IP:端口，发起连接

4. 服务端MySQL校验用户合法性，写入Redis在线缓存，客户端上线，全员同步在线用户列表

**状态测试**：用户上下线通知、在线列表实时更新、心跳超时离线测试、头像全局同步展示测试、双端同时在线状态同步测试、三套主题切换生效与持久化测试、跟随系统实时同步测试、消息已读状态、输入状态、未读角标、会话置顶功能测试

## 7\.2 文字聊天流程

1. 客户端输入文字，选择群聊/私聊模式，发送消息

2. 服务端接收消息，写入MySQL完成持久化

3. 根据消息类型，通过读取Redis在线用户列表执行广播/定向转发

4. 接收方客户端实时渲染消息，展示发送人、内容、时间，支持后续加载历史记录

## 7\.3 文件传输流程（阶段三十一/三十二：三层分流）

文件传输按服务端下发的 http\_upload\_threshold（默认 1MB）、max\_file\_size（默认 20MB）与 max\_direct\_size（默认 2GB）自动分流，**小文件走 WebSocket 分片中转、中等文件走 HTTP 单请求直传落库、超大文件走分片直传（进度回显可取消）**：

**链路A：小文件 WS 分片（≤1MB，协议不变）**

1. 发送方选择本地文件、选择接收用户，发起文件传输

2. 服务端初始化MySQL文件记录、Redis分片缓存

3. 客户端按服务端下发的 chunk\_size（64KB）分片封装文件数据，依次发送文件头\+分片数据，发送前检查 websocket.bufferedAmount 背压限速（积压超 8 片量级暂停 10ms 重试）

4. 服务端实时中转数据（sendBlock 阻塞写接收方队列形成背压，接收方消费不及时节流发送方），更新Redis分片进度

5. 接收方拼接文件分片，校验完整性并保存至本地

6. 最后一片到达时服务端执行一次 SCard 齐片判定，更新MySQL文件传输状态为已完成

**链路B：大文件 HTTP 直传（\>1MB，WS 仅传信令）**

1. 前端本地 blob 立即渲染（nonce 标识）→ `POST /upload/file?username=xxx&to_user=yyy&nonce=zzz` 流式上传（不经 WebSocket，不产生分片）

2. 服务端流式落盘（不占内存）→ 建档 im\_file → 落库 im\_message → 会话摘要更新 → 推送 FILE\_PERSISTED（携带 content 与 nonce）

3. 发送端按 nonce 回填 msg\_id，接收端按 content 直接渲染 URL；大文件海量分片不再挤占连接队列与 Redis

**链路C：超大文件分片直传（\>20MB 至 2GB，阶段三十二：进度回显可取消）**

1. 发送方逐片 `POST /upload/chunk`（raw body，片间独立请求，xhr.upload.onprogress 本地回显"上传中 xx%"，气泡可随时 × 取消）

2. 服务端按片流式落盘临时目录，节流推送 FILE\_PROGRESS（最快 500ms 一条），接收方渲染"接收中 xx%"进度气泡

3. 收齐后顺序合并落盘 → 建档/落库 → 推送 FILE\_PERSISTED → 双端进度气泡替换为正式文件卡片；取消则双方移除气泡并清理临时分片（详见 7.3.4）

## 7\.3\.1 图片/文件消息持久化（阶段二十四：历史可重现）

原文件传输仅服务端中转（不存二进制、不写消息表），图片/文件消息刷新即丢失。持久化改造在**协议零改动**前提下补齐"发送方回传→服务端存储→消息落库→历史直出"链路：

1. **触发时机**：发送方分片全部发送完成后，通过 HTTP `POST /upload/file?file_id=xxx&username=yyy` 回传原文件；上传失败仅告警降级（实时显示不受影响）

2. **服务端处理**（server/uploadfile.go）：校验请求者为 im_file 记录收发双方（403 拦截）→ 幂等检查（im_file.msg\_id\>0 直接返回已有消息，杜绝多端重复落库）→ 大小限制（max\_file\_size 配置，默认 20MB）与危险文件拦截 → 保存至 upload\_dir 配置目录（默认前端静态目录 static/upload，URL 直出零路由）→ 落库 im\_message → 回写 im\_file（status=3/msg\_id/file\_path）→ 双方会话摘要更新为 \[图片\]/\[文件\]

3. **存储类型**：im\_message.msg\_type 新增 **4=图片消息、5=文件消息**（存储命名空间，与 1群聊/2私聊 同表），content 为 JSON {url,name,size}

4. **历史与未读**：handleHistory 私聊条件扩展为 msg\_type IN (2,4,5)；私聊未读统计同步扩展，图片/文件计入角标

5. **竞态防护**：分片完成判定（写 status=1）与上传落库（写 status=3）并发时序，完成判定改为条件更新 `WHERE status < 3`，幂等以 msg\_id 为权威依据

6. **前端渲染**（chat.js ?v=1.18）：历史加载按 msg\_type 分支，图片 URL 直出（点击大图）、文件卡片（名称+大小+点击下载），元数据（msg\_id/时间戳/已读状态）与文字消息一致，气泡对齐规则复用

7. **持久化同步通知（协议 33\-FILE_PERSISTED）**：落库成功后服务端向双方全部在线连接推送 file\_id+msg\_id，双方实时气泡按 file\_id 精确回填 msg\_id（实时图片/文件气泡补设 data-from/data-ts 后撤回/删除/置顶能力齐备），HTTP 上传响应仅作确认不再承担回填（统一归口 WS 通知）

8. **边界闭环**：阶段二十四"实时气泡无 msg\_id 不支持实时撤回"的遗留边界已在本轮闭环（见 4.10.5 第 6/7 条）；持久化仍仅私聊（分片协议现状）

## 7.3.2 群聊图片消息（阶段二十六：HTTP 上传 + 服务端广播）

群聊图片不走点对点分片协议（该协议强制单一 ToUser、im\_file 为收发双方模型），改走独立 HTTP 上传链路，**私聊分片协议与持久化链路零改动**：

1. **前端发送**（chat.js ?v=1.19）：群聊视图选择图片后新增 `sendGroupImage` 流程——生成 nonce 标识 → 本地 blob 立即渲染（data-nonce 挂载）→ `POST /upload/group/image?username=xxx&nonce=yyy`；上传失败仅告警降级（本地预览保留，刷新后消失属预期）。私聊视图仍走私片协议 sendFile，截图在群聊视图同样走此链路（截图即图片）

2. **服务端处理**（server/uploadfile.go 新增 `HandleGroupImageUpload`）：校验图片扩展名（非图片 400）+ 危险文件拦截 + 大小限制（max\_file\_size 配置）→ 保存至 upload\_dir（唯一文件名）→ 落库 im\_message（**msg\_type=4，to\_user 为空表示群聊**，content 为 JSON {url,name,size,nonce}）→ `hub.Broadcast` 广播协议 **34\-GROUP_IMAGE**（含 msg\_id）→ 离线注册用户入队（与群聊文字一致）→ 全部在线用户群聊会话摘要更新为 \[图片\] 并推送

3. **msg_id 回填归口**：发送端收到自己的 GROUP_IMAGE 广播后按 nonce 精确匹配本地气泡回填 msg\_id/ts（并发发送多图不错位；多端场景无本地气泡走通用渲染分支）；其余用户实时渲染图片气泡携带 msg\_id，撤回/删除/置顶能力齐备

4. **群聊链路纳入**：三处群聊查询统一改为 `msg_type IN (1,4) AND to_user = ''`（to\_user='' 守卫防止私聊图片混入群聊范围）——handleHistory 群聊历史、convMessageQuery（会话清空）、refreshConvSummaryAfterRecall（撤回摘要联动重算，case 4 摘要 \[图片\]）；历史渲染复用 createMediaMessageEl 零改动

## 7.3.3 大文件传输瓶颈改造（阶段三十一：双链路分流 + 背压 + 配置归口）

面向 10000 用户同时在线、个别用户传输大文件的商用场景，五处瓶颈逐层改造：

1. **发送队列背压**（server/client.go）：新增 sendBlock 阻塞写入（带超时），文件分片中转改用阻塞语义——接收方消费不及时天然节流发送方读循环，杜绝"队列满直接丢弃导致接收方永远收不齐文件"；普通聊天消息保持非阻塞丢弃语义（宁可丢一条聊天不可阻塞广播）。队列缓冲 send\_queue\_size 配置化（原固定 256，现 1024）

2. **连接上限生效**（server/hub.go + server.go）：hub 新增 TotalConns() 按连接数（非用户数，多端模型）统计在线总数，HandleWS 升级握手前校验 max\_connections（1000→10000），达到上限拒绝新连接

3. **齐片判定 O(1) 化**（server.go handleFileChunk）：每片均 SCard 统计改为仅最后一片判定，20MB 文件 Redis 往返从 5120 次降为 1 次；齐片后条件更新 `WHERE status < 3` 防与持久化落库竞态

4. **chunk\_size 64KB**：4096→65536，消息数与 Redis 操作降 16 倍；登录响应 JSON 归口下发 chunk\_size/upload\_threshold，前端零硬编码自适应（socket.js 暴露 getChunkSize/getUploadThreshold/getBufferedAmount）

5. **大文件 HTTP 直传分流**：超过 http\_upload\_threshold（1MB）的文件前端 sendFileDirect 走 `POST /upload/file`（无 file\_id 参数即直传模式，服务端 handleDirectUpload 流式落盘不占内存），WebSocket 仅承担 FILE\_PERSISTED 信令；海量分片不再占用 WS 连接队列与 Redis；发送端 nonce 回填、接收端 content 直渲染（复用阶段二十四/二十六归口模式，协议零新增）

6. **前端背压限速**（chat.js）：WS 分片发送前检查 websocket.bufferedAmount，积压超 8 片量级暂停 10ms 重试，弱网时分片不在浏览器/服务端堆积挤掉普通聊天消息

## 7.3.4 超大文件分片直传（阶段三十二：GB 级进度回显 + 取消同步）

单请求直传在 GB 级文件下受内存、超时与"fetch 无上传进度"约束，新增第三层分流链路（**\>max\_file\_size 20MB 至 max\_direct\_size 2GB**），微信同款"发送中/接收中 xx%"进度体验：

1. **协议扩展**：新增 **40\-FILE_PROGRESS**（content 为 JSON：upload\_id/nonce/received/total/file\_name/file\_size）与 **41\-FILE_CANCEL**（下行 content 为 JSON：upload\_id/nonce）

2. **服务端分片接收**（server/uploadchunk.go，main.go 注册 /upload/chunk）：逐片 `POST /upload/chunk?username=&to_user=&nonce=&upload_id=&seq=&total_chunks=&file_name=&file_size=`，raw body（application/octet-stream）流式落盘临时目录 upload\_dir/tmp\_chunks/\<upload_id\>/\<seq\>.part（不经 multipart 解析省内存省 CPU）；上传会话仅内存存储（重启丢失即重传，不落库不进 Redis 避免超大文件高频写），超时 30 分钟懒清理；首片创建会话（重复 upload\_id 幂等复用）

3. **安全校验链**：在线校验（401）→ 黑名单拦截（403）→ 总大小上限 max\_direct\_size（400）→ 危险文件拦截（400）→ 分片序号合法性（400）→ 会话归属校验（403）→ 取消后分片拒绝（410）→ 单片大小 MaxBytesReader 限制（upload\_chunk\_size+1KB 容差）

4. **进度推送节流**：单会话最快 500ms 一条 FILE\_PROGRESS（LastPush 时间戳在锁内先记后推，并发分片不超发）；私聊推接收方全部在线连接、群聊广播全部在线用户；发送方本端进度由 xhr.upload.onprogress 本地计算回显，不经服务端信令

5. **收齐合并归口**：收齐后顺序合并各分片（流式拷贝不经内存全量缓冲）→ 建档 im\_file（status=3）→ 落库 im\_message（图片 4/文件 5，content 含 nonce）→ 会话摘要 [图片]/[文件] → 推送 FILE\_PERSISTED（复用阶段二十四/三十一归口模式，双端按 nonce 回填/替换）→ 清理会话与临时目录

6. **取消链路**：发送方 WS 上行 41\-FILE\_CANCEL（file\_id 复用携带 upload\_id）→ 校验会话归属（仅发送方可取消）→ 打取消标记（在途分片竞态请求被 410 拒绝）→ 清理会话与临时分片 → 推送双方全部连接移除进度气泡（发送方多端同步），接收方 Toast"对方取消了文件发送"

7. **前端发送侧**（chat.js ?v=1.29 sendFileChunked）：sendFile 四层分流（超 max\_direct\_size 拒绝 → 超 max\_file\_size 走分片直传 → 超 upload\_threshold 走单请求直传 → 小文件走 WS 分片）；逐片 XHR 顺序上传，进度气泡带 × 取消按钮（abort 在途 XHR + 移除本地气泡 + 上行取消信令）

8. **前端接收侧**（chat.js ?v=1.29）：FILE\_PROGRESS 渲染"接收中 xx%"气泡（仅对应会话视图渲染，upload\_id 精确匹配/nonce 兜底）；FILE\_PERSISTED 到达后替换为正式文件卡片（msg\_id 回填，撤回/删除/置顶齐备）；FILE\_CANCEL 移除双端气泡

9. **配置归口**：upload\_chunk\_size（4MB）与 max\_direct\_size（2GB）服务端配置、LOGIN\_RESP 下发、前端零硬编码自适应（socket.js ?v=1.16 暴露 getUploadChunkSize/getMaxDirectSize）

10. **进度条样式**（style.css ?v=1.10）：.file-progress 进度条与 .file-progress-text 进度文本均使用主题变量（\-\-primary/\-\-border），取消按钮 hover 红色，上传失败态红色文本，跟随明暗主题切换

## 7.3.5 微信式截图发送（阶段三十五：Ctrl+V 粘贴编辑器 + 伪冻结遮罩选区）

截图即图片，复用既有图片上传链路（服务端零改动），前端独立模块实现双模式截图编辑器：

1. **模块结构**（web/js/screenshot.js，chat.js 之前加载）：window.ScreenshotEditor 对外暴露 open/freeze/close/isOpen；底图层/标注层/遮罩层三画布均保持原图分辨率（CSS 缩放适配视口，输出不损失清晰度）；标注仅落在选区内（clip）；笔触随图尺寸自适应；撤销栈上限 10；马赛克采用降采样 1/8 关平滑放大重贴；文字工具使用自定义浮动输入框（禁止系统弹窗）；快捷键 Esc 取消 / Enter 发送 / 选区工具双击快捷发送

2. **编辑器模式 open**（Ctrl+V 粘贴入口 + 截图按钮默认入口）：contain 居中缩放窗口式展示，默认全图选区（粘贴/截帧后可直接发送或标注）；chat.js paste 监听仅拦截剪贴板图片项（已登录且聊天视图可见时），文本粘贴不受影响

3. **伪冻结遮罩模式 freeze**（第二期，备选入口，ScreenshotEditor.freeze 接口保留）：抓帧后画面 cover 铺满视口（居中、溢出裁剪，贴近"屏幕被冻结"观感）、空选区（必须拖拽框选，微信 Alt+A 同款）、顶部自绘操作提示条引导框选（框选开始即收起）、拖拽期间右下角实时显示宽×高尺寸标签、框选完成后底部居中工具栏才出现（重新框选时自动隐藏）；经实测反馈截图按钮默认走 open 模式（freeze 调用注释保留在 chat.js），需要全屏冻结体验时换回即可。**事件归口**：三画布绝对定位同位层叠且遮罩层在最上层，mousedown/dblclick 统一绑容器 wrapEl 冒泡接收（绑画布会被 maskCanvas 拦截导致冻结态无法框选），不依赖层叠顺序

4. **确认输出**：按选区裁剪 底图层+标注层 合成 PNG blob，经 sendScreenshotFile 统一入口分流（群聊走 sendGroupImage HTTP 上传链路，私聊走 sendFile），双模式共用同一套标注/撤销/输出核心

## 7.3.6 图片消息滚动贴底修复（阶段三十六：异步加载撑高跟随）

图片气泡插入时 img 高度为 0，插入后立即滚底滚的是"未撑高"的列表，图片加载完成撑高（.chat-image 最高 200px）后滚动位置停在原处，导致新图片只显示一半：

1. **贴底快照判定**（chat.js）：插入前采样 stick=isNearBottom()（scrollHeight \- scrollTop \- clientHeight < 80 视为贴底），img 挂 load 监听，加载撑高后按快照决定是否再次滚底。**快照必须在插入前采样**——load 回调内实时判定会被图片撑高干扰（gap 瞬间≈图片高度突破容差，误判为翻历史而放弃滚底）；发送/接收新消息场景贴底生效，用户正在翻看历史时（不在底部）不强行拉底打断浏览

2. **两处渲染点统一接入**：appendImageMsg（实时发送/接收，函数首行快照）与 createMediaMessageEl（历史图片分支，renderHistoryRecord 传入 stickBottom=!beforeEl && isNearBottom()，向上补插历史不参与滚底）；原插入后立即滚底逻辑保留

## 7.3.11 知识库与自动向量化（阶段五十一：RAG 检索增强问答）

1. **向量库选型**：chromem-go 内嵌向量数据库（纯 Go 实现、磁盘持久化、零外部依赖，维持单二进制部署模型）；向量库根目录 `ai.kb.data_dir`（默认 kb_data，相对 exe 目录解析），每知识库一个 collection（kb_<id>）；chromem-go `QueryEmbedding` 要求 nResults ≤ 集合文档数，检索前按 `col.Count()` 钳制 topK（空集合跳过）

**进入路径**：后台管理 → 左侧导航「量化数据管理」。打开后默认展示全部知识库的已向量化切片（每页 20 条，按库分组排序），顶部状态行显示总条数。

**表格列说明**：

| 列 | 含义 | 健康参考值 |
|---|---|---|
| 知识库 | 切片所属库名（同一文件所有切片归属同一库） | — |
| 文件 | 切片来源文件名（超长省略显示） | — |
| 切片 | 切片序号（同一文件内从 #0 连续编号） | — |
| 字数 | 切片正文字符数（rune 计） | ≤ 切片参数 500 字 |
| 维度 | 向量维度（等于当前向量模型输出维度） | 同库内应完全一致（如 768/128） |
| 范数 | 向量 L2 范数 | ≈1.0000（明显偏离说明 embedding 服务异常） |
| 内容 | 正文前 60 字预览（鼠标悬浮显示全文），下方为向量前 8 维数值 | 前 8 维不应全为 0 |
| 操作 | 编辑 / 删除 / 源文（源文仅 txt/md/csv 显示） | — |

**搜索与筛选**：
- 库筛选下拉：切到某个库只看该库切片，选项带切片数（如「测试知识库（121 片）」）；切换即时生效
- 关键词搜索：输入切片内容中的任意连续文字（如"预警准确率"），回车或点「搜索」；搜索作用于全库或当前筛选库
- 组合使用：先选库再搜索 = 库内搜索；「刷新」按钮重新拉取库下拉与列表（其他管理员刚上传的文件会出现）

**编辑切片（微调量化数据）**：
1. 找到目标行点「编辑」，弹窗内回显当前切片全文
2. 修改文字后点「保存」——服务端用新文字重新调用 embedding 生成新向量，同 ID 写回，来源标注（文件名+切片号）不变
3. 表格自动刷新，字数列变化即保存成功；范数应仍≈1.0000（重嵌后自动归一化）
4. 验证效果：到「知识库 → 检索调试」用相关问题测试，命中内容应为编辑后文字
- **注意**：编辑只改向量库，源文件不动；日后对该文件点「重建」会用源文件重新切片，覆盖手工编辑

**删除切片**：点「删除」→ 二次确认 → 该切片从向量库移除，AI 检索不再命中它；用于清理 OCR 错误片段、重复内容等坏数据。删除后其他切片编号不变。

**编辑源文（整篇修改）**：仅文本类文件（txt/md/csv）行内显示「源文」按钮——弹窗回显源文件全文，保存后服务端覆写源文件并**自动重新切片+重向量化**（全文件所有切片会更新）。docx/xlsx 等二进制文件无此入口，需修改内容请重新上传。

**分页**：底部「上一页 / 下一页」，显示"共 N 条 · 第 X / Y 页"；数据增删后若当前页超界自动回退最后一页。

**常见问题排查**：
- 范数明显不是 1.0000 → embedding 服务返回异常，检查 config.yaml 的 ai.embedding 配置与本地模型状态
- 同库内维度不一致 → 该库混入了不同模型的向量，须整库「重建」（管理后台知识库视图）
- 搜索无结果显示「暂无数据」→ 关键词未命中任何切片，换词或清空搜索
- 列表为空但文件列表有文件 → 文件状态非 ready（向量化处理中或失败），到知识库视图查看文件状态
- 编辑保存报 embedding 错误 → ai.embedding 未配置（降级态），先在 config.yaml 配置并重启服务端

**推荐工作流**：上传文件 → 检索调试面板实测命中率与阈值 → 本页搜索定位坏切片 → 编辑/删除修正 → 检索调试复测确认 → （必要时）调 config.yaml 阈值并重启。

## 7.3.15 表格向量化数据标准化（阶段五十五：xlsx/csv 切片格式归一）

1. **问题根因（三层叠加）**：①提取层 aiSpreadsheetText 逐行 join 不清理空单元格 → xlsx 排版空白列产生 "| | | |" 空管道污染；②切片层 kbSplitChunks 对超长表格行按字符硬切 → 列被拦腰切断出孤立碎片（切片以 "| | |" 开头无表头）；③切片无工作表名/表头 → 数据行缺语义，"有的标准有的不标准"。

2. **提取标准化（aidoc.go aiSpreadsheetText 重写）**：单元格 TrimSpace + 内部连续空白（含制表符/换行）压缩为单空格（strings.Fields+Join）；裁剪行首尾连续空单元格；行内连续空单元格压缩为 1 个空段（保留列间隔感避免错误合并相邻列）；全空行剔除。同时惠及 AI 文档问答链路（同一提取归口）。

3. **切片表格感知（kb.go kbSplitChunks 重构）**：表格行判定 = Contains " | "；①超长表格行按 **列边界聚合切分**（单元格完整不切断，列语义连续不带 overlap）；②**表头继承**——表格连续块首行为表头，块内数据行切出的每个切片自动带表头前缀（新片起始/落盘后再入都注入，表头占片预算，表头行自身不注入）；③**工作表边界**（"## 工作表："标题行）强制起新片并重置表头；普通行打断表格块后表头失效；④普通超长段维持字符硬切+overlap 原逻辑（回归保护）。

4. **验证（临时单测 5/5 + 实测）**：单测覆盖表头继承/长行列边界/工作表边界/普通文本回归/提取标准化；实测重建「梗阳IP信息表V2.xlsx」（file_id=20）切片 105→144，旧乱片 "| | | | | | HA带外GE10..." 变为「工作表名+完整表头+完整数据行」，切片 #2 起自动带表头前缀；全库空管道残留 0 条；临时测试文件已删除。

10. **真实对话实测（浏览器全流程，专用账号）**：告知个人信息→AI 确认→约 15s 后记忆弹窗自动出现 3 条 source=auto 记忆（用户名叫王小明/住在杭州西湖区/最喜欢的食物是东坡肉，提取质量符合提示词要求）；同账号 WS 多端发 10 轮算术对话挤出 aiContextWindow=20 条历史窗口后提问"我叫什么/住哪里/爱吃什么"，AI 精准答出三者——此时历史上下文已无该信息，证明回答纯靠记忆向量召回注入；重复告知不产生重复记忆（去重环生效）；第 11 轮触发 AI 提问限频（服务端 msg_type=9 拦截，保护链路正常）。
11. **去重阈值实测校准（12 对样本，nomic-embed-text）**：同义改写句相似度 0.74~0.98（"最喜欢的食物是/喜欢吃"仅 0.74、"名叫/名字是"达 0.98）、不同记忆相似度 0.59~0.86（"工作是程序员/喜欢吃东坡肉"高达 0.86、"最喜欢吃东坡肉/擅长钓鱼"竟 0.98——nomic 对短中文句区分度不足，区间交叠无完美分界）；dedup_threshold 定 0.88 零误杀（宁少量冗余不丢真实记忆），0.74 级轻微改写漏存为冗余条目属已知局限（可弹窗手删）；原 0.85/0.68 均有误杀实测。
12. **实测教训（GORM 通用坑）**：bool 字段带 default:true 标签时，GORM 建行对零值（false）会从 INSERT 剔除交由数据库默认值填充——导致"新建偏好行且要求关闭"永远落库为 true（FirstOrCreate+Assign(map) 只修好"行已存在"分支，此为"行不存在"分支的独立坑）；修复=移除 default 标签，缺行默认开启语义由代码层（memUserEnabled 查无行返回 true）保证。

6. **工具集**：todo_write（建/更新任务清单全量推送 todo 事件+done/total 进度）、run_command（命令白名单外强制审批）、write_file（默认审批，auto_write=true 免审批）、read_file（免审批）；文件操作经 agentSafePath 严格限制在用户工作区内（../ 盘符 绝对路径穿越全拦截）。
7. **权限审批**：agentNeedsApproval 风险分级——白名单命中（run_command 前缀匹配）与免审配置直通执行；高危操作挂起任务（status=waiting_approval）+step key=toolCall.ID 防跨任务/跨步骤错投，等待 AGENT_APPROVE：approve（可带改参 params 覆盖）/reject（"用户拒绝了该操作"结果回传模型自纠）/cancel（整任务取消）/超时（任务失败）。

9. **前端**（chat.js v=1.90 / style.css v=1.54）：AI 智能体会话输入工具栏出现 Agent 模式开关（active 态主题色高亮，切换会话自动退出任务模式）；开启后发送内容作为任务目标本地回显+AGENT_RUN 上行；任务卡片容器（头部：目标+状态标签+停止按钮；自绘进度条 todo 驱动 done/total；任务清单全量重绘 done 划线；事件流子块：💭思考/⚙️工具执行(含耗时)/审批卡片）；审批卡片参数 JSON 可编辑（改参放行），同意/拒绝后 settle 置灰；事件不落库仅当前会话实时渲染，切换会话不重放；done 最终答复以正常 AI 消息气泡展示（Markdown 渲染）。

## 7\.3.22 Agent 执行轨迹留痕（阶段六十五：每步工具调用即时落库，任务详情可回看完整执行轨迹）

## 7\.3.23 Agent 任务完成通知（阶段六十六：完结消息落库留档+会话未读归口+系统级提醒）

1. **服务端落库归口**（agentrun.go agentFinish）：任务完结时统一落一条通知消息进会话流——completed 落最终答复原文（修复事件流不落库、重登后最终答复丢失）、cancelled 落"任务已取消"（is_read=true，本人现场操作触发不产生未读）、failed 落"任务执行失败：+原因"；消息为私聊形态（MsgType 2，from=智能体、to=发起人），落库成功后 done/error/cancelled 事件携带 msg_id 回传前端（气泡关联库记录，撤回/引用/操作栏正常）；联动 touchConversation（会话摘要刷新）+ notifyConvUpdate（CONV_LIST 推送，托盘角标/闪动自动生效），切走会话/最小化/离线后经历史与角标可靠感知。
2. **摘要截断修复**（conversation.go / msgstate.go）：touchConversation 原实现 lastMsg[:200] 按字节截断，中文多字节字符被拦腰切断产生无效 UTF-8，MySQL 静默拒绝写入且错误被吞（会话行创建/更新失败、完结通知无角标），改为按字符 []rune 截取 200 字并补错误日志；消息撤回同步会话摘要的同源字节截断一并修复。
3. **前端事件分发**（chat.js）：done/error 完结事件不再依赖当前会话——切走会话/最小化时先拦截触发系统级提醒再 return（原实现非当前会话直接丢弃事件）；当前会话内 done 渲染最终答复气泡（关联 msg_id，Markdown+操作栏齐全）并发已读回执（正查看时完结消息视为已读，不留假未读角标）；error 实时渲染失败通知气泡（内容与服务端落库留档一致）+已读归口；cancelled 渲染"任务已取消"留档气泡保持双端一致。
4. **系统级提醒归口**（chat.js agentTaskNotify）：窗口隐藏（document.hidden）或已切走会话时触发——PC 端经 preload notify IPC 弹系统桌面通知，Web 端 showToast 轻提示兜底；正盯着该会话时不打扰（任务卡片进度即通知）；通知正文=任务状态+目标前 20 字截断。
5. **PC 端桥接**（preload.js / main.js）：preload notify 由占位实现补真（ipcRenderer.send 'notify'），主进程 ipcMain.on('notify') → showNotification（Electron Notification，isSupported 校验），任务完结提醒在窗口最小化/失焦时仍可送达。

## 7\.3.24 Agent 任务队列排队（阶段六十七：单用户并发任务从"直接拒绝"升级为"FIFO 排队等待"）

1. **配置归口**（config.go / config.yaml）：ai.agent 新增 concurrency（每用户同时运行任务数上限，0=1）与 queue\_size（每用户排队任务数上限，0=5），InitAgent 加载并兜底默认值；超出并发数的新任务自动排队，排队已满时新任务直接拒绝（错误回执提示"已有任务在执行中且排队已满"，不落库不建卡）。
2. **入队与派发归口**（agentrun.go）：handleAgentRun 统计用户活动任务数（running/waiting\_approval，等待审批占并发槽）与排队列表——低于并发上限直接启动，超出生成 EnqueueSeq（全局原子自增保证 FIFO 严格递增）入队；agentDispatchNext 为唯一派发归口，任务完结（completed/failed/cancelled）与取消排队后统一调用，队首最早入队任务自动启动（status 事件 from\_queue=true，前端卡片转"执行中"），落库状态同步刷写。
3. **排队位次广播**：agentDispatchNext 无论是否发生派发，均向全部排队任务广播当前位次（queued 事件携带 position）——队首被派发取走或中段任务被取消后，后续任务位次自动前移（未变化时幂等刷新），前端卡片实时显示"排队中 · 第 N 位"。
4. **取消排队**：排队任务尚未启动、无状态机协程可唤醒，取消分支直接收尾（cancelled 事件 + 落库留档）并触发派发归口；运行中任务的既有取消路径回归不变。
5. **重启遗留态清理**（InitAgent）：内存任务注册表随进程消失，落库的 queued/running 记录已不可能恢复（queued 从未启动、running 执行中断），启动时统一标记 failed（"服务重启，任务中断"），防任务历史出现幻影进行态。
6. **前端渲染**（chat.js / style.css）：排队任务同样实时建卡（含目标与位次），queued 状态徽标为主题色低饱和中性态与"执行中"区分，卡片按钮转"取消排队"，自队列派发后复位"停止"；任务历史弹窗与管理端 Agent 任务审计视图状态标签/筛选/徽标同步支持 queued（排队中），落库记录全口径可追溯。
7. **验证**：E2E（tools/agent\_queue\_test\_main.go，验证后已清理）9 项断言全通过——任务1直接运行、任务2/3入队位次1/2、取消任务3后任务2位次前移、任务1完成后任务2自动派发（from\_queue）、派发后取消回归、队列打满（并发1+排队5）第7个被拒不落库、落库状态归口（1 completed + 8 cancelled 共 9 条）；浏览器实测（真实流程：任务1执行 run\_command 触发"等待审批"占住并发槽→任务2入队）——排队卡片"排队中 · 第 1 位"与"取消排队"按钮正确显示、取消后转"已取消"、任务1可停止收尾、任务历史"排队中/已取消"筛选正常。

## 7\.3.28 文件工具补全（阶段七十四：list_dir/grep/edit_file/delete_file + read_file 分段与二进制防护）

## 7\.3.29 命令实时控制台 + 长命令转后台（阶段七十五：Trae 同款执行反馈）

1. **背景**：run_command 执行期间前端仅显示"执行中"跳动点，长命令（编译/打包/安装依赖）用户无从得知进展，误以为卡死。本阶段对齐 Trae：输出实时控制台 + 超时转后台不阻塞对话。
2. **协议帧**：AGENT\_TOOL\_OUTPUT(60) 上行 PC 渲染进程 → 服务端（content 为 JSON：{task\_id,step,chunk,total\_bytes,over,final,exit\_code,duration\_ms}，final=true 为进程结束帧）；AGENT\_BG(61) 双向（上行前端 → 服务端请求转后台 {task\_id,step}，服务端执行时直接生效，PC 本地执行时服务端原样下行转发给渲染层桥接执行器）。
3. **服务端**（agentrun.go）：agentToolRunCommand 改为 StdoutPipe/StderrPipe 流式泵——行级聚合 200ms 节流下发 tool\_output 事件（累计 64KB 停增量，over 标记；模型结果仍 head 8KB+tail 56KB 环形保留、上限 8000 字符），tool\_start 事件补 call\_id（toolCall ID，前端归属键）；"转后台"由 handleAgentBg(61) 校验步骤后 close runBgCh 广播——前台立即返回"命令已转入后台执行"（不阻塞模型循环），进程换 30 分钟兜底强杀继续跑完，结束后 tool\_exit 事件（退出码/耗时仅前端控制台展示，不进模型上下文）。PC 本地执行同语义：agentWaitLocalExec 挂起中收到转后台请求原样下行转发（msg 61），输出帧经 handleAgentToolOutput(60) 转任务事件流。

8. **联调修复（readPump 同步阻塞死锁）**：实测 PC 在线时面板恒报"空目录/服务器工作区"，全链 trace（渲染层 send62→recv64→IPC→send65 经 preload fileopTrace 经 IPC 落盘 + 前端 recv63 打点）显示 64 下行 38ms 即达、本地执行 1ms 完成、65 上行渲染层即时发出，但服务端 15s 后才读到 65——根因：handleWsFileReq 在 readPump 内同步调用 wsFileWaitPC（select 等回传最长 15s），阻塞期间本连接的 65 回传滞留 TCP 缓冲读不进来，超时删挂起表后才读到 65，必然"超时→回退→迟到丢弃"死循环，且顺带阻塞该用户全部上行消息。修复：等待逻辑移入独立 goroutine，readPump 立即返回继续读帧（agentfiles.go）。修复后实测全链 41ms 闭环（send62→recv63），PC 回传 ok=true root=本地工作区 条目正常。另 writePump 增加慢写观测（>200ms 打 Warn，帧字节与用户名随日志输出）辅助定位连接级写出卡顿。

## 7\.3.31 Git 克隆仓库 + SSH 远程主机（阶段八十一：TRAE CN 同款克隆体验）

1. **背景**：Agent 工作区面板已具备项目切换（proj\_open/proj\_list），但新项目只能手动放入工作区。本阶段对齐 TRAE CN：面板内直接克隆 Git 仓库——实时进度条、可取消、Token 记忆、最近克隆历史；随阶段补齐 SSH 远程主机连接（终端托管会话 + 本地快连簿），为远程开发场景铺路。
2. **协议帧**：复用 WS\_FILE\_REQ(62)/WS\_FILE\_RESP(63)，新增 op：proj\_clone（content=JSON{url,name,token}）、proj\_clone\_cancel（content=JSON{target:克隆请求的 req\_id}）、proj\_list（归口返回 list+recents 两段）。克隆进度走 63 多帧模式：{type:"progress",req\_id,pct,stage,speed,sent}（同 req\_id 多帧、不结束前端 Promise，最终结果仍以常规 63 帧收尾）；PC 本地执行时进度经 PC\_FILE\_RESP(65) 多帧上行服务端转发（type=progress 同构）。
3. **服务端**（agentfiles.go）：wsProjClone——git clone \-\-progress 流式执行，StderrPipe 挂 wsCloneProgressPump 泵（\\r 单行刷写按 \\r/\\n 双分隔切行；正则提取四阶段百分比 Receiving objects/Resolving deltas/Updating files/Checking out files、速度、已接收量；500ms 节流推 63 进度帧；stderr 尾段 8KB 环形保留供错误提取；recover 兜底解析异常绝不带崩服务端）；context.WithTimeout 600s 兜底强杀；运行句柄登记 wsCloneRunning（key=username|req\_id）支持精确取消——ctx 取消杀进程、半成品目录 os.RemoveAll（git 被杀不自清理）；失败路径统一清理并按错误特征追加提示（Authentication failed→引导填 Token、not found→引导查地址）。凭据安全：Token 仅内存拼接 URL（://token@ 形式）不落盘不进日志；克隆历史 wsProjRecentAdd 剥凭证后按 URL 去重置顶（上限 10）。**凭据弹窗三重禁用**：\-c credential.helper= 置空 + GIT\_TERMINAL\_PROMPT=0 + GIT\_ASKPASS=echo（无人值守服务端必须禁交互，见联调修复 1）。wsCloneProgressPump 首个非空 stderr 行即推"连接远端中"帧、remote: 统计阶段（Enumerating/Counting/Compressing objects）透出阶段文字，避免远端枚举静默期前端无反馈。
4. **PC 执行器**（agent-executor.js）：projCloneLevel 与服务端同构实现（spawn 流式解析、500ms 节流经 65 多帧回传、600s 兜底 taskkill /T /F 杀树——git\-remote\-https 等传输子进程 child.kill 杀不干净、取消/失败均清 dest）；projRecentAdd 同构剥凭证去重，PC 本地元数据一份（与 projList 归口合并返回）。main.js/preload.js：tokenGet/tokenSet 按 host 走 Electron safeStorage 加密存储本机（浏览器端无此能力自动隐藏记忆选项）；SSH 快连簿 agent:ssh\-list/save/del（userData/agent\_ssh.json，仅存 host/port/user/备注无密码，按 host|port|user 去重置顶上限 10）。
5. **SSH 远程主机**（阶段八十一同步）：终端页签栏新增 SSH 入口（仅 PC 本地终端可用时显示）→ 快连弹窗（host/port/user + 快连簿列表点击回填、长按删除）→ 新建 ssh 终端标签。执行器 termSsh 无 PTY 依赖方案：spawn ssh \-tt 强制分配远端伪终端（stdin 管道不回显，远端 TTY 负责回显/行编辑/密码提示），本地仅字节流转发 + ANSI 控制序列清洗（CSI/OSC 转义清除，textContent 渲染兼容）；input 直写远端 stdin（sync 标记无 exit 帧）；会话复用终端标签基础设施（term\_id 独立命名空间 ssh 前缀），退出/断开自动恢复就绪态。认证由 ssh 自身机制处理（密码/密钥均走远端 TTY 交互，快连簿不存密码）。
6. **前端**（chat.js/style.css）：wsPanelProjCloneDlg 自绘弹窗——仓库地址（https:// /git@ /ssh:// 前缀校验）、目录名（留空自动取地址尾段；路径分隔符/../: 拒绝）、Token（password 型，仅私有仓库选填）三字段；最近克隆列表（proj\_list 归口 recents，点击回填地址与目录名）；进度区主题色进度条 + 阶段/速度/已接收量状态行（63/65 progress 多帧统一经 wsPanel.onCloneProgress 更新）；克隆中按钮切换为"取消克隆"（按 req\_id 精确取消，迟到错误按已取消处理）；失败复开弹窗回填原值与错误便于修正重试；克隆成功自动切换到新项目（TRAE 同款体验）。Token 记忆（仅 PC）：勾选后 safeStorage 按 host 加密保存，地址 blur 时自动回填（urlFillSeq 竞态序号防过期回填）。SSH 弹窗样式与克隆弹窗同套（主题色跟随）。
7. **验证**：服务端 go build/go vet 通过产出 bin/im-server.exe；新增真实链路测试 ws\_proj\_clone\_real\_test.go（TestWsProjCloneReal 真实克隆成功+进度回调多次、TestWsProjCloneCancelReal 取消后半成品清理、TestWsProjCloneAuthFailFast 需认证仓库快速失败不挂进程）全部 PASS；浏览器全流程验证（克隆弹窗→进度→完成自动切换→最近历史→取消克隆→无残留项目）通过；chat.js 版本号 2.48、style.css 1.92 强制刷新缓存。
8. **联调修复（实测发现的 4 个问题）**：
   - **GCM 凭据弹窗挂死克隆（最关键）**：需认证仓库（如 gitee linux.git 匿名 401）克隆时触发 Git Credential Manager 交互弹窗，克隆挂死直至 600s 超时（实测 22s 仍停在弹窗）。先试 GCM\_INTERACTIVE=never 无效（GCM 2.7.3 对 gitee 等未知主机无视该变量，实测 git credential fill 仍挂起）；最终 \-c credential.helper=（空值重置助手链）+ GIT\_TERMINAL\_PROMPT=0 + GIT\_ASKPASS=echo 三重禁用，实测认证失败 22s 干净返回（22s 为 gitee 服务端枚举耗时）。URL 内嵌 Token 的私有仓库不受影响（凭证随 URL 传递不经 helper）。
   - **cloneSentBytes 单位解析错误**（PC 执行器）：charAt(length\-4) 恒取到单位前空格（"1.23 MiB"→' '），已接收量单位换算失效；改为按空格分组（\["1.23","MiB"\]）取单位首字符。
   - **远端枚举阶段零反馈**：大仓库 Enumerating/Counting 阶段 git 无输出、且这些阶段不在原四阶段正则内，前端长时间停留"正在连接仓库…"。补 remote: 阶段正则透出阶段文字 + stderr 首行即推帧（pct 置 0、阶段"连接远端中"），服务端与 PC 执行器同步。
   - **tail 重声明编译错误**：wsCloneProgressPump 签名命名返回值 (tail string) 与局部 var tail strings.Builder 冲突，改非命名返回值。
9. **测试仓库选择注意**：取消/进度类真实测试须用可匿名访问的大仓库（如 gitee.com/mirrors/go.git）；勿用需认证仓库（克隆进程被凭据弹窗/认证失败提前终结，测不到真实传输窗口）。

## 7\.3.32 历史对话压缩（阶段八十四：TRAE 同款上下文瘦身，AI 问答 + Agent 任务双链路）

1. **背景**：长上下文两大痛点——AI 问答固定窗口（context\_window=20）外历史"滑走即丢"；Agent 任务循环 msgs 无界追加且每轮全量重发，token 消耗随步数近似平方级膨胀（超长工具结果尤其恶化），后期响应变慢、费用变高甚至"上下文超长"直接压死任务。本阶段对齐 TRAE"历史对话压缩中"：估算 token 超阈值时把较旧历史 LLM 摘要成一条摘要消息注入，最近若干条保留原文（混合策略，压缩有损但最近上下文无损）。
2. **配置归口**（config.yaml ai 节点，均兜底默认）：compress\_threshold\_tokens（触发阈值，估算 token，0=默认 12000，负数=禁用，AI 问答与 Agent 任务共用）、compress\_keep\_messages（压缩时保留最近原文条数，0=默认 6）；agent 节点新增 tool\_result\_max\_chars（工具结果入模型上下文的字符上限，0=默认 8000，负数=不截断；前端执行控制台与留痕仍全量）。token 估算归口 aiEstimateTokens：CJK/全角约 1 字 1 token、其余约 4 字 1 token（粗估，误差由阈值余量吸收）。
3. **AI 问答压缩**（ai.go aiCompressHistory）：压缩启用时历史查询回溯量扩展至 context\_window+60（窗口外更早历史可进摘要，不再丢失）；估算未达阈值时行为与原窗口逐条一致（零额外开销）。触发后：较旧段（剔除最近 keep 条）按 id ASC 转录（用户/AI 角色标注、messageSummary 取正文），LLM 合并上一摘要生成新摘要（aiCompressSummarize，system 压缩器提示词：保留事实/结论/数字/路径/命令结果/未解决问题，输出≤4000 字符），按 "sid|user|agent" 内存缓存增量合并（缓存覆盖 uptoID，只摘要新增段，缓存全覆盖零 LLM 调用；服务重启首问重压缩一次，可接受）。注入顺序：system 系列 → \[历史对话摘要\] → 最近原文 → 本轮提问。摘要失败（无模型/网络异常/用户停止）回退原窗口不注入。提示帧 aiPushCompressFrame 复用 AI\_STREAM 通道 remark=compress，摘要调用挂接停止句柄 askCtx（压缩阶段点停止即时生效）；会话清空（AI\_SESSION\_DEL clear=true）时摘要缓存同步失效。
4. **Agent 任务压缩**（agentrun.go agentCompressTaskHistory，每轮模型调用前执行）：agentCompressBoundary 扫描完整工具轮（assistant 含 tool\_calls 起 + 其全部 tool 结果），在最近第 3 轮起处切割——保证 tool\_call\_id 配对永不拆分（OpenAI 兼容格式要求）。超阈值时把 msgs\[1:边界\]（含 goal 与旧摘要，天然增量合并）转录为文本交 LLM 摘要，重建 msgs = system + goal + \[前序执行历史摘要\] + 保留轮原文；事件流推 history\_compress（phase=start 前端显示"历史对话压缩中"，phase=done 静默）。摘要失败时未超 3 倍阈值则本轮跳过下轮重试；超 3 倍阈值紧急截断（弃旧轮+省略声明）防任务死亡。工具结果截断归口 agentTruncateToolResult（头 2/3+尾 1/3，尾段含最终状态对决策更关键；256 字符余量防对 run_command 既有截断二次截坏标注）。
5. **前端**（chat.js v2.53）：AI 问答 AI\_STREAM 处理新增 remark=compress 分支——hideAIThinking 后建流式气泡并在正文上方插「历史对话压缩中…」状态行（复用联网搜索行 .ai-search-row 主题样式类，跟随主题色；每次回复至多一条，压缩完成后保留作过程留痕，不落库）。Agent 事件 switch 新增 history\_compress 分支（phase=start 时思考过程区显示"历史对话压缩中…"，done 不重复上屏）。
6. **验证**：go build / go vet 通过；浏览器实测——短会话行为与原版一致（无压缩帧）；超长会话（粘贴大量文本超阈值）提问可见「历史对话压缩中…」状态行、回复正常、日志打印"AI 历史压缩触发"；Agent 长任务执行中思考过程区出现压缩提示、任务正常完成；压缩后再次提问复用缓存摘要（服务端日志无第二次摘要调用）。

# 十一、MCP 能力（TRAE CN 同款，阶段八十八～九十）

## 11\.1 架构总览

系统在两处提供 MCP（Model Context Protocol）能力，命名空间隔离互不干扰：

- **服务端归口 MCP（阶段八十八/八十九）**：Go 服务端作为 MCP Host 统一管理所有公共 MCP 服务器连接（stdio 在服务端本机拉起子进程 / sse / http 远程端点），配置以 im\_mcp\_server 表为唯一数据源，后台管理增删改热生效；发现的工具以命名空间 key `mcp_<服务器名>_<工具名>` 注入 AI 智能体 schema，调用经服务端连接会话执行。
- **用户本机自定义 MCP（阶段九十，仅 PC 端）**：用户在 PC 端"我的 MCP 服务器"面板配置自己电脑上的 stdio MCP 服务器（TRAE 同款本地执行），命令/参数/环境变量等凭据仅存用户本机（userData/agent\_mcp\.json），服务端只接收工具元数据清单；注入名带 `mcp_pc_` 前缀命名空间，调用经 PC 本地执行器在用户电脑上执行。

注入名规整算法（非法字符→下划线，超长截断+fnv1a 8位十六进制后缀，≤64 字符）在服务端 mcpToolKey 与 PC 端 mcp\-manager\.js pcToolKey 两端逐字节一致，保证路由反查不错位；后台管理员服务器名禁止 `pc_`/`pc-` 前缀防撞名，服务端路由遇到 `mcp_pc_` key 一律不匹配（本机工具绝不走服务端连接执行）。

## 11\.2 服务端归口 MCP（阶段八十八/八十九）

- **配置归口**：config\.yaml `mcp` 节点（enabled 总开关 / user\_enabled 用户自建开关 / stdio\_whitelist 用户自建 stdio 命令白名单 / connect\_timeout\_seconds / tool\_timeout\_seconds / servers 种子示例——仅首次启动表空时导入，之后以后台管理配置为准）。
- **管理后台**：admin\.html「MCP 服务器」页，支持新增/编辑/删除/重连/测试连接/导入 mcp\.json（兼容 TRAE/Claude/Cursor 格式）/单工具启停（per\-tool disabled\_tools）/免审批（auto\_approve）开关；新增弹窗内置生产模板一键填充（filesystem/fetch/memory/github 官方实例）。
- **Agent 注入**：已连接且启用服务器的未禁用工具动态进入 OpenAI function calling schema；默认逐次人工审批，auto\_approve 服务器免审批。

## 11\.3 用户本机自定义 MCP（阶段九十，PC 端专属）

**用户流程**：PC 端聊天输入栏「我的 MCP 服务器」按钮 → 面板内新增服务器（名称/启动命令/参数/环境变量，与 TRAE mcp\.json 同构）→ 保存即在本机拉起 stdio 子进程并做工具发现 → 工具清单经消息类型 67（AGENT\_PC\_TOOLS）全量上报服务端 → 服务端回执 \{ok,count\} 前端 toast 确认 → Agent 任务中模型可调用 `mcp_pc_<服务器>_<工具>`，审批确认后经本地执行器（msg 50/51 链路）在用户电脑执行。

**技术要点**：

- 配置存储：Electron 主进程 userData/agent\_mcp\.json 按用户名分桶，凭据不出本机；登录后首次 sync 自动拉起常驻会话，无需手工启动。
- 工具清单上报：主进程快照指纹变化才上报（服务端 sync\.Map 全量覆盖，空清单=清除注入）；建连/保存后窗口期内每秒快照一次直到清单稳定。
- 服务端清洗归口（handleAgentPcTools）：仅接受 platform=pc 连接；服务器数 ≤10、工具总数 ≤64、名称 ≤128、描述按字符截断 512、schema ≤8KB（超长丢弃走空对象兜底）、server\+tool 去重；仅内存保存不落库（源头在用户本机，重启后等 PC 重新上报）。
- 注入闸门：mcp\.enabled 与 mcp\.user\_enabled 双开关，且仅发起人 PC 端在线时注入（离线时调用必失败，schema 反而误导模型）。
- 审批与执行：本机工具默认逐次人工审批（模型可借工具在用户电脑执行任意逻辑）；执行分派归口 agentToolExecDispatch——PC 在线走本地执行器，PC 离线/回传超时明确报错不回退服务端（服务端无进程可调，无法等价执行）。
- 提示词：系统提示词动态追加本机 MCP 工具纪律说明（mcp\_pc\_ 前缀、经用户电脑本地执行）；tool\_start 事件 label 下发「MCP · 服务器 / 工具（本机）」展示名。

# 十二、内置浏览区与浏览器工具（阶段九十一，PC 端专属）

## 12\.1 功能总览

TRAE CN 同款内置浏览区：PC 客户端（Electron）内置多标签页浏览器（WebContentsView 内核），用户可从聊天输入栏「内置浏览器」按钮打开浏览网页；AI Agent 任务中可调用 browser\_\* 工具族直接在用户可见的浏览区里打开网页、读取可交互元素、点击/输入/截图/执行 JS——相比服务端 http\_request 抓静态 HTML，本机浏览可操作 JS 渲染页面与登录态。另提供 CDP（Chrome DevTools Protocol）远程调试端口开关（默认关闭），开启后任何本机 CDP 客户端可附加窗口读页/执行 JS（OpenClaw/TraeClaw 控制 Trae 同款机制）。

## 12\.2 架构与调用链

- **服务端归口**：config\.yaml `agent.pc_browser` 总开关（默认开启）；开启且发起人 PC 在线时向 OpenAI function calling schema 注入 browser\_\* 工具定义（agenttools\_browser\.go）；审批分级归口 agentBrowserNeedsApproval（见 12\.3）；执行分派走 msg 50/51 本地执行器链路（PC 离线明确报错不回退服务端）。tool\_start 事件 label 下发「浏览器 · xxx」展示名，系统提示词动态追加工序纪律（先 snapshot 拿 ref 再操作）。
- **PC 主进程**：agent\-executor\.js 按 `browser_` 前缀分派 → browser\-manager\.js（与主进程同上下文免二次 IPC）；多标签页管理、导航/快照/点击/输入/截图/eval 实现、状态推送（browser:state 单向数据流）。
- **渲染层 UI**：index\.html 浏览区面板（标签栏/工具栏/内容占位）+ chat\.js 能力检测启用（Web/手机端无 desktop 桥自动旁路）；渲染层自绘面板并承载标签内容元素（file iframe/web webview），显隐/tab/地址栏/导航态全部以主进程推送状态为准。

## 12\.3 工具清单与审批分级

| 工具 | 作用 | 审批 |
| --- | --- | --- |
| browser\_navigate | 打开网页（自动展开浏览区，用户实时可见） | 免审批 |
| browser\_snapshot | 可交互元素清单（带 ref 编号）+ 文本概要 | 免审批 |

快照防膨胀：可交互元素采集上限 120 个、回传字符上限 12000（超长截断并提示用 browser\_eval 精确读取）；ref 写入页面 data\-agent\-ref 属性供 click/input 反查，页面变化后 ref 失效自动提示重新 snapshot。

## 12\.4 安全边界

- **协议白名单**：URL 仅放行 http/https（服务端与客户端双重拦截，javascript:/file:/data: 一律拒绝）。
- **会话隔离**：标签页共用 persist:agent\-browser 持久分区（登录态跨会话保留），与主窗口会话完全隔离——浏览区站点无法触碰客户端自身登录凭据。
- **能力封禁**：页面不注入 preload、contextIsolation+sandbox 开启、无 node 能力；权限请求（定位/通知/摄像头/麦克风等）默认拒绝；window\.open/target=\_blank 一律转应用内新标签页（防弹窗劫持外跳）；UA 去 Electron 标记降低站点反爬误拦截。
- **CDP 端口风险**：userData/agent\_browser\.json 配置 \{cdp\_port: 9222\} 开启（app ready 前注入 remote\-debugging\-port 启动参数，运行中改配置需重启）；端口绑 127\.0\.0\.1，开启后等同任何本机进程可完全控制客户端，仅建议开发调试场景开启。

## 12\.5 浏览区面板 UI（渲染层）

- 入口：聊天输入栏「内置浏览器」按钮（能力检测 window\.desktop\.browserPanel 存在才显示；Web/手机端永不显示）。
- 结构：标签栏（tab chip + 新建 + 收起）+ 工具栏（后退/前进/刷新 + 地址栏回车 + 前往按钮）+ 内容区（占位背景，内容由渲染层 DOM 元素承载：file 标签 iframe、web 标签 webview，见 12\.7）。
- 几何同步：阶段九十三起原生层已移除，iframe/webview 以 CSS inset:0 铺满内容区自动跟随布局（分栏拖拽/侧栏折叠/窗口缩放），无需 bounds 上报。
- 状态同步：显隐/标签列表/地址栏/导航可用态全部由主进程 browser:state 推送归口，渲染层单向应用；用户正在地址栏输入时不覆盖输入内容。

## 12.6 文件查看归一浏览区（阶段九十二，PC 端专属）

TRAE CN 归一语义：PC 端所有文件查看/预览/编辑、git diff、提交详情、审查报告**统一在浏览区标签打开**，不再出现"工作区预览面板 + 浏览区"两个浏览区并存；Web/手机端（无 desktop 桥）自动走 wsPanel 原路，行为完全不变。

- **file 标签类型**：browser-manager 新增 `kind: 'file'` 标签，独享 `persist:agent-fileviewer` 持久分区 + 窄 preload（viewer-preload.js 仅暴露 save/setDirty）；页面恒为服务端同源 file-viewer.html（will-navigate 锁死导航，外部网页进不了本分区）。
- **渲染能力**：file-viewer.html 多格式归一渲染——docx(mammoth)/xlsx(SheetJS)/pptx(PPTXjs)/图片/PDF/代码(hljs)/Markdown/diff/提交详情（元信息头+diff）；文本文件可编辑保存（脏标记圆点，保存经 browser:file-save 主进程归口写盘，路径只认 tab.filePath 杜绝任意路径写）。
- **打开归口**：渲染层 chat.js `wsOpenFile`/`wsOpenData` 双 helper 归口——`browser:open-file`（磁盘文件，主进程 safePath 校验读盘，同文件复用标签刷新）/`browser:open-data`（diff/提交/审查报告等直传内容，payload.key 相同复用标签）。
- **改道入口（PC 判定 wsPcViewer）**：文件树点击/右键打开、Agent 文件变更卡点击、git 变更列表 diff（含仓库无提交时的"整文件新增"伪基线）、提交详情/提交单文件、智能体审查报告、Agent write_file/edit_file 工具写入后自动打开/刷新标签（TRAE 同款）、delete_file 联动关闭对应标签、撤销变更后已开标签重读还原内容。
- **状态扩展**：browser:state 的 tabs 携带 kind/file_name（工作区相对路径）/ext（小写扩展名）/data\_kind（diff/commit/md/text）/favicon（web 标签站点图标）/dirty，渲染层据此渲染标签与已开判定（browserHasFileTab，撤销刷新仅刷已开不强行打开）。
- **标签呈现（TRAE CN 同款）**：标题主进程归口（file 标签恒为文件名/diff 标题，did\-stop\-loading 不再被页面 title"文件预览"覆盖）；file 标签按扩展名显示 VSCode 通行配色徽标（GO/JS/MD/CPP…）、diff/commit/审查报告显示 ±/⎇/MD 徽标，web 标签显示站点 favicon（page\-favicon\-updated 采集，无则地球兜底）；标签条为 TRAE 平底矩形样式（\-\-chat\-bg 底色+细竖分隔线，激活项 panel\-bg 背景盖住底线与内容区无缝融合+顶部主题色亮条），关闭钮默认半透明悬停高亮；未保存标签显示主题色圆点、悬停切回 ×。
- **file 标签 DOM 化（iframe 承载，原生层退场）**：file/内容标签不再创建 BrowserView——主进程只维护标签状态（createTab 对 file 直接 view=null），payload 经 browser:file\-load IPC 推给渲染层；渲染层（chat.js）按 tab\_id 维护同源 iframe 池（src=file\-viewer.html，与主页面同源可直调 contentWindow），跟随活动态显隐、标签关闭即移除、未就绪 payload 暂存补投。保存/脏标记经宿主 window.\_\_imViewerHost（preload 新增 browserFileSave/browserViewerDirty）转发主进程，viewer 页桥解析回退 parent（viewerBridge\(\)）。收益：file 标签场景下悬停提示/弹窗遮罩/分隔线等页面 DOM 恢复最高层级，不再被原生层遮挡（此前整类"被盖住"问题的根除）；缩放刻度/bounds 错位问题对 file 标签自然消失。网页标签仍走原生层（跨站网页无法内嵌主页面 DOM），其遮罩联动（browser:modal 隐藏视图）保留。
- **多标签打开语义（一个文件/内容一个标签）**：点击工作区不同文件/git diff/提交详情各开各的浏览区标签（标签数=打开数，文件名/diff 标题独立显示）；同一文件（同用户同相对路径）或同一 key 的直传内容复用原标签并重推 payload 刷新。注：曾实现过 TRAE/VSCode 预览复用（唯一预览位被后续点击替换），但复用路径只换 payload 不触发重载导致"内容不变+永远一个标签"，且不符合多标签预期，已整体移除（preview 字段/pinTab/browser:pin\-tab 均废弃）。
- **居中分栏布局（TRAE CN 同款）**：浏览区贴 .main\-chat 左缘（会话侧栏与聊天区之间的"中间区"），聊天列压缩到右侧——padding\-left 压缩（基准宽剔除已加 padding 防两种 box\-sizing 下反馈环路；窗口过窄保聊天最少 320px），消息/输入框保持可见可用，用户可边浏览边向 AI 提问；#list\-toggle\-btn/.emoji\-panel/conv\-search 等经 \-\-browser\-w 变量避让；窗口 resize 重算。
- **控制台停靠浏览区底部（TRAE CN 同款）**：控制台抽屉（任务输出/终端多标签）在 PC 端停靠进 #browser\-panel 作为底部子块（flex 纵排排到内容区之下，通栏贴底仅顶部黑色分隔线），开合改变内容元素尺寸→ResizeObserver 自动重报原生视图 bounds；"打开控制台"浮标仍固定聊天区输入框上方，控制台展开时若浏览区隐藏则一并唤起（browserPanel\(true\)），收起不动面板；窄屏/旧布局回退工作区预览列下方，Web/手机回退输入框上方。
- **bounds 同步（含侧栏折叠位移）**：ResizeObserver 同时观察内容区与主区（.main\-chat）——侧栏折叠是 #list\-panel 宽度动画，主区宽度逐帧变化而浏览区面板为固定像素宽（内容元素尺寸不变），仅观察内容区会漏掉这类整体位移导致原生视图错位（内容渲染到聊天区上方）；观察主区后逐帧重算分栏+重报 bounds，动画全程跟随。分栏宽度持久化去抖（宽度真变化才写 localStorage）。
- **缩放刻度对齐（防原生视图越界）**：getBoundingClientRect 返回 CSS px 而 setBounds 按 DIP 应用，页面被缩放（Ctrl+滚轮，Chromium 还会持久化缩放值）时原生视图会比内容区偏宽/偏移，盖住分隔线、边缘按钮与悬停提示。三层修复：主进程 browser:bounds 按 event.sender.getZoomFactor\(\) 折算；main.js 启动 setZoomFactor\(1\) 归一历史持久化值；渲染层禁用缩放入口（wheel ctrlKey preventDefault + Ctrl ±0 拦截，仅 PC 桥存在时）。
- **分栏拖拽调宽**：浏览区右缘 7px 把手（browser\-splitter，悬停/拖拽中主题色提示线），左右拖动水平调整宽度（浏览区最小 280px、聊天列最少保留 320px），宽度 localStorage 持久化跨会话保留；拖拽期间主进程对全部 BrowserView setIgnoreMouseEvents(true) 放行鼠标（否则鼠标划过原生视图时渲染层收不到 mousemove 拖拽中断），mouseup/窗口失焦复位。
- **地址栏/面包屑按标签类型切换**：file 标签显示只读路径面包屑（bc\-seg 路径段 + › 分隔 + 末段文件名高亮，TRAE 同款），网址输入栏与前往按钮隐藏；web 标签才显示网址输入栏。
- **弹窗遮罩与原生视图联动（防遮罩/弹窗被盖）**：遮罩与弹窗（ws\-proj\-mask 系，SSH 快连、工作区弹窗等）属主页面 DOM，会被浏览区原生 BrowserView 盖住（Electron 层级行为，原生层恒在页面 DOM 之上，z\-index 无法穿透）。方案：chat.js 用 body childList MutationObserver 归口观测遮罩加入/移除，经 preload browserModal IPC 通知主进程；主进程按计数在遮罩期间 setVisible\(false\) 隐藏全部浏览区视图（遮罩本就半透明压暗全屏，观感自然），关闭后恢复，layout 后重申可见态。悬停提示仍用原生 title 气泡（保持既有样式，未改自绘气泡）。
- **安全边界**：file 标签与网页标签分区完全隔离；保存仅限 tab.filePath（safePath 复验防工作区切换后写穿旧路径）；二进制只读；文本超 1MB 只读截断。

## 12.7 Web 标签 DOM 化（阶段九十三，PC 端专属）

阶段九十二已将 file 标签 DOM 化（iframe 承载），但 web 标签仍走原生 BrowserView，网页区域依旧遮挡页面 DOM（工具提示/弹窗遮罩/分隔线/控制台），且需 modal 联动隐藏、拖拽放行鼠标、bounds 缩放折算三类专项补偿。阶段九十三将 web 标签改由主页面 `<webview>` 标签承载，**浏览区彻底告别原生视图层**，全部"被盖住"问题从根因消除，此前三类补偿机制整体移除。

- **webview 承载（真内核但是 DOM）**：main.js 主窗口 webPreferences 开启 `webviewTag: true`；chat.js 按 tab_id 维护 webview 池（仅活动 web 标签建框，首次激活按当前 url 设 src 首载），跟随活动态显隐、标签关闭即移除（元素移除即销毁 guest）；属性锁定 `partition=persist:agent-browser`（登录态跨会话保留，与主窗口会话隔离）+ `webpreferences="contextIsolation=yes, sandbox=yes, nodeIntegration=no"` + `allowpopups`（仅为让 window.open/target=_blank 能进主进程 setWindowOpenHandler 归口转应用内标签）。webview 是页面 DOM 元素（与 file iframe 同层级），标签栏/地址栏/工具提示/弹窗遮罩/分隔线/控制台等恒在其上。
- **主进程归口（wcId 直达）**：webview dom-ready 时渲染层经 preload `browserWvReady` 上报宿主 webContents id；主进程 `webContents.fromId(tab.wcId)` 直达宿主——挂接 page-title-updated/did-start-loading/did-stop-loading/did-navigate(-in-page)/page-favicon-updated 事件（幂等，guest 崩溃重建后按新 id 重挂）+ setWindowOpenHandler（deny 弹窗 + urlAllowed 放行转应用内新标签）；导航操作（back/forward/reload/stop/goto）与 Agent 工具（snapshot/click/input/screenshot/eval）全部经 fromId 执行。webview 未就绪时 goto 暂存 tab.queuedNav，wv-ready 后补发；browser_navigate 新标签由渲染层按 src 自动首载，主进程 wcFor 轮询就绪后 waitLoaded/settleAfterLoad（语义与旧 BrowserView 时代一致）。
- **专项补偿机制整体移除**：browser:modal 弹窗遮罩联动（MutationObserver+setVisible）删除——遮罩本就是 DOM，天然盖在 webview 上；browser:split-drag 拖拽放行鼠标（setIgnoreMouseEvents）删除——改为 CSS `body.browser-resizing .browser-file-frame/.browser-web-frame { pointer-events: none }`；browser:bounds 上报/setBounds/DIP 折算/ResizeObserver 观察主区整套删除——iframe/webview 尺寸由 CSS inset:0 布局驱动自动跟随；缩放锁定（Ctrl+滚轮拦截）保留为视觉一致性行为。
- **createTab 状态化**：主进程不再创建任何原生视图（旧版 web 标签 new BrowserView），标签仅状态归口（title/url/loading/favicon/dirty/wcId），渲染层按 browser:state 建/删/显隐 DOM 元素；面板显隐/标签切换/文件打开归口相应简化（无 attachTab/layout）。
- **样式**：`.browser-web-frame` 与 `.browser-file-frame` 同款（absolute inset:0 铺满 #browser-content，主题 panel-bg 底色），标签/工具栏样式不变（TRAE CN 同款延续）。

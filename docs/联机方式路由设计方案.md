# 联机方式路由设计方案（应用级 supernode / 隧道 分流）

> 状态：设计评审稿（未实施）
> 关联文档：`docs/虚拟IP池设计方案.md`（虚拟网卡 IP/社区/密钥分配）、`docs/局域网公网联机开发文档.md`（隧道链路现状）、`docs/联机原生SDK设计.md`
> 关联代码：`im-server/server/gamenet.go`（建房 mode 收敛）、`im-client/web/js/gn-room.js`（建房/房间页）、`im-client/web/js/admin.js`（应用表单）

## 一、背景与目标

现状：联机接入形态由**全局配置** `game_net.mode`（lane/tunnel/both）收敛，所有应用共用同一条链路。虚拟网卡路线（p2p-host.exe 组网，见虚拟 IP 池设计方案）落地后，需要**应用级**区分：

- 管理员给应用上架时选择「联机方式」：
  - **虚拟网卡（supernode）**→ 创建房间默认走 p2p-host.exe 组网（老游戏广播发现类，如需要真·局域网的应用）
  - **端口隧道（tunnel）**→ 默认走既有隧道链路（War3 等已适配端口隧道的方式）
- 房主创建房间时**只读跟随**应用配置（不可改，配置归口管理员），选「联机应用」后自动带出
- 服务端按房间 mode 分流：supernode 房间下发组网参数（虚拟 IP/社区/密钥/supernodes），tunnel 房间维持既有隧道链路

## 二、存储设计

`im_game` 新增一列（AutoMigrate 自动加列，存量应用默认空零回归）：

```go
// NetMode 联机方式（建房房间跟随；空=跟随全局 game_net.mode 现状，存量应用零回归）
// "supernode"=虚拟网卡（p2p-host.exe 组网）/ "tunnel"=端口隧道（既有方式）
NetMode string `gorm:"column:net_mode;type:varchar(16);default:''" json:"net_mode"`
```

- 值域白名单：`""` / `"supernode"` / `"tunnel"`（服务端保存校验，非法值拒绝）
- 与既有 `Supernodes` 列的关系：`NetMode="supernode"` 时 `Supernodes` 必填（≥1 条，保存拦截）；`NetMode="tunnel"` 时 `Supernodes` 强制清空（隧道方式不消费，防脏数据）

## 三、服务端收敛规则（建房时，gnHandleCreate）

现有 mode 收敛（全局 `game_net.mode` 收敛客户端声明）之前插入**应用级覆盖**：

```
优先级（高 → 低）：
1. 游戏 NetMode="supernode"
   前置校验（全部满足才生效）：
   a) vip_pool.enabled=true（虚拟 IP 池启用）
   b) 游戏 Supernodes 非空
   c) 本连接登录回执已分配 vip_ip（可选校验，未满足时房间日志警告）
   通过 → mode="supernode"
   不满足 → 降级 mode="tunnel" + WARN 日志（"应用 %s 配置虚拟网卡方式但前置条件不满足，已降级隧道"）
2. 游戏 NetMode="tunnel" → mode="tunnel"（强制隧道，忽略全局与客户端声明）
3. 游戏 NetMode=""（空/未配置）→ 现有收敛链不变（全局 game_net.mode 收敛客户端 p.Mode 声明）
```

- 收敛结果写入房间 meta `mode` 字段（既有逻辑）→ 随房间态广播自动下发，**下行链路零改动**
- supernode 房间额外携带组网字段（comm/comm_key/supernodes）——虚拟 IP 池方案已实现，随 `gnStateEnv` 自动下发，本方案零改动
- mode 值域扩展 `"supernode"`：`gnEnvelope.Mode` 为透传字符串，旧客户端收到未知值按既有降级逻辑处理（走隧道），不会崩

## 四、admin 应用表单设计

「联机 supernode」多选上方新增**联机方式**三态胶囊单选（游戏管理表单通用样式）：

```
联机方式： (○ 跟随全局   ○ 虚拟网卡   ○ 端口隧道)
```

| 选中 | 行为 |
|---|---|
| 跟随全局（默认） | supernode 多选隐藏；保存 NetMode=""；建房走现状收敛 |
| 虚拟网卡 | supernode 多选**展开**；保存校验：未选任何 supernode → 拦截"虚拟网卡方式需至少选择一个 supernode"；NetMode="supernode" |
| 端口隧道 | supernode 多选隐藏 + 提示"已保存的 supernode 配置将保留但不再下发"；NetMode="tunnel" |

- 提示文案引导：跟随全局="由服务端全局联机配置决定（当前 tunnel 形态）"；虚拟网卡="适合只认局域网广播的老应用，创建房间即组虚拟网（需用户端安装 TAP 驱动）"

## 五、建房页设计方案（gn-room.js 建房弹窗）

「联机应用」选中后**自动带出**该应用联机方式，只读展示：

```
┌─ 创建房间 ─────────────────────────────────┐
│ 房间名称  [________________________]       │
│ 联机应用  [魔兽争霸3 ▼]                    │
│ 联机方式  (⬤ 虚拟网卡)   ← 随应用带出，只读  │
│           ├ ✓ TAP 驱动已安装               │
│           ├ ✓ 虚拟 IP 已分配 (10.28.1.5)   │
│           └ ✓ supernode 可达 (1/1)         │
│ 对战模式  [1v1 ▼]                          │
│ 房间人数  [4 ▼]                            │
│ 游戏端口  [6112]   ← 仅 tunnel 模式显示     │
│ 房间口令  [______]                         │
│                [取消]  [创建房间]           │
└───────────────────────────────────────────┘
```

交互分支：

| 应用 NetMode | 建房弹窗行为 |
|---|---|
| supernode | 隐藏「游戏端口」行（虚拟网卡无需端口）；显示联机方式行 + 前置条件检查清单（TAP 驱动安装态 / vip_ip 分配态 / supernode 在线态，实时检查）；条件不满足 → 创建按钮置灰 + 提示原因（"请先在设置中启用虚拟网卡"） |
| tunnel | 显示端口行（现状），联机方式行显示"端口隧道"徽标 |
| 空（跟随全局） | 联机方式行显示"跟随全局配置"；其余现状 |

数据源：应用列表接口（游戏摘要）需带 `net_mode` 字段（`gameSummary` 增加该键——管理端详情已有，用户端摘要为公开接口，net_mode 非敏感可直接下发）。

## 六、房间页设计方案

标题区（房间名/房号旁）加**联机方式徽标**：

- `mode="tunnel"` → 「端口隧道」灰徽标（现状视觉，成员无感知变化）
- `mode="supernode"` → 「虚拟网卡」绿徽标 + 可展开状态区：
  - 本机虚拟 IP / MAC（p2p-host 启动后显示"组网中"）
  - 社区号（-c 值，供排查）
  - supernode 连接状态
- 成员开局行为分支（客户端侧）：
  - supernode 房间开局 → 启动 p2p-host.exe（-a/-s/-c/-k/-l 参数见虚拟 IP 池方案附录 A）→ 虚拟网卡就绪后提示"可进入游戏"
  - tunnel 房间开局 → 既有 110 连接层隧道流程（现状不变）

## 七、客户端联动架构

```
开局（房主点开始，status=playing）
  └─ 客户端按房间 mode 分支：
      ├─ tunnel → 既有链路：GameNet.hostStart/connect（110 连接层端口隧道）
      └─ supernode → 新链路（另案：p2p-host 启动器）
            1. 校验 TAP 驱动（设置页已装？未装引导）
            2. 启动 p2p-host.exe sidecar（-a vip_ip -s vip_mac -c comm -k comm_key -l supernodes...）
            3. 虚拟网卡就绪探测（IP 配置成功）
            4. 房间页显示"组网就绪"；对局结束/退房 → 停止 p2p-host
```

**边界声明**：p2p-host 启动器（sidecar 生命周期/就绪探测/游戏内组网验证）为独立另案——本方案落地后 supernode 房间的 UI 与服务端信令全部就绪，启动器未落地前 supernode 房间开局时客户端提示"虚拟网卡启动器即将支持，暂走隧道链路"并降级 tunnel 行为。

## 八、兼容性矩阵

| 场景 | 行为 |
|---|---|
| 存量应用（NetMode 空） | 建房收敛走现状，War3 等隧道联机**零回归** |
| 老客户端收 `mode="supernode"` 新房间 | 未知 mode 按既有降级逻辑走隧道 |
| vip_pool 未启用但应用配了 supernode | 建房自动降级 tunnel + 服务端 WARN |
| 新客户端开 tunnel 房间 | 行为与现状完全一致 |
| 房间创建后应用配置变更 | 房间沿用创建时刻快照（与 supernodes 同语义，对局稳定优先） |

## 九、测试与验收清单

1. **收敛规则**：三态 NetMode × vip_pool 启用/关闭 × 客户端声明 → mode 结果矩阵正确
2. **降级**：supernode 应用在 vip_pool 关闭时建房自动降级 tunnel + WARN 日志
3. **表单校验**：supernode 方式未选节点被拦截；tunnel 方式保存后 Supernodes 列清空；存量应用编辑保存 NetMode 不被意外清空
4. **建房页**：选应用带出方式徽标；supernode 隐藏端口行；前置条件清单实时刷新；不满足时置灰
5. **房间页**：徽标正确；supernode 房间信令携带 comm/comm_key/supernodes
6. **兼容**：老客户端（未升级）建房/加入 supernode 房间不崩、走隧道
7. **回归**：既有隧道联机全流程（建房/端口探测/连接/对局）不受影响

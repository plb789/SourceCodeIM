# 一、背景与目标

## 1.1 背景

项目 PC 客户端当前启动商户游戏客户端时存在以下限制：

1. **单实例限制**：同一游戏只能启动一个客户端进程，想多开必须手动复制整个游戏目录或用第三方工具；
2. **账号锁定**：启动游戏时传入的账号密码固定为平台登录账号派生（`{0}`=登录账号，`{1}`=HMAC 派生 16 位密码），无法自定义；
3. **SmartSteamEmu 锁死**：`SmartSteamEmu.ini` 全局单份，并发启动会互相覆盖导致联机身份错乱；
4. **端口转发冲突**：每次启动游戏都重新绑定端口转发，多实例会导致端口占用冲突。

## 1.2 目标

1. **管理后台增加多开开关**：每个游戏独立配置是否允许多实例、最多实例数量；
2. **PC 客户端支持多开**：已配置允许多开的游戏，可同时启动多个客户端进程；
3. **启动参数支持自定义账号密码**：占位符扩展为 `{0}` 平台账号、`{1}` 平台派生密码、`{2}` 自定义账号、`{3}` 自定义密码；
4. **自定义账号持久化**：用户在游戏属性里可增删改多组账号，密码用 DPAPI 加密存储；
5. **启动按钮下拉选择账号**：有多个自定义账号时，启动按钮右侧显小三角，下拉菜单选择账号启动；
6. **端口转发复用**：同一游戏多实例共享第一个实例的端口转发，引用计数管理，最后一个实例退出才关闭转发；
7. **SmartSteamEmu 维持单实例**：SSE 游戏锁定不支持多开（配置文件冲突），与现有 `sseBusy` 检查保持一致。

## 1.3 非目标（功能一期不做）

- 手机端多开（Android/iOS 系统限制单实例 APK 进程）；
- Overlay 多实例切换面板（P2 阶段，一期多实例只对首个生效的实例注入热键）；
- SmartSteamEmu 多实例独立运行目录（一期维持 SSE 单实例限制）；
- 游戏本身有互斥锁导致启动失败的兼容（这是游戏自身限制，客户端无法绕过）；
- 云存档多实例同时写冲突处理（一期仅启动前 pull、退出后 push，运行时冲突由后续迭代处理）。

# 二、现状分析

## 2.1 启动链路

```
前端 launchGame(gid)
  → DESKTOP.gameGetLaunchOptions(gid)     // 读 userData/game-launch.json
  → buildLaunchArgs(tpl, gid)              // {0}=账号, {1}=密码 替换
  → DESKTOP.gameLaunch(payload)            // IPC
    → main.js game:launch handler
      → spawnGameChild / spawnSteamEmuGame
      → runningGames.set(gameId, info)     // ← 单实例 Map<gameId>
      → gameForward.start(pfTag, rules)    // ← 每次重新绑定端口
```

## 2.2 当前单实例限制点

| 限制点 | 位置 | 原因 |
|--------|------|------|
| `runningGames` 用 `gameId` 作 key | `main.js:2890` | 同一游戏只存一个进程引用 |
| `state.running[gid]` 单实例状态 | `game-store.js:4522` | 检测到运行中就拒绝启动 |
| `state.launching[gid]` 防重复启动 | `game-store.js:4523` | 启动中也拒绝再次启动 |
| SmartSteamEmu `sseBusy` 硬拦截 | `main.js:2850-2854` | ini 全局单份，并发互相覆盖 |
| Overlay 热键按 gameId 注册 | `main.js:2891` | 多实例热键冲突 |

## 2.3 账号密码传入链路

```
平台登录账号 (im_auth.username)
  → {0} 占位符 → buildLaunchArgs 替换
  → 服务端 HMAC-SHA256(secret, "im-game-launch:"+username+":"+gameID)
    → {1} 占位符 → 16 位数字字符串
    → SmartSteamEmu 映射为 SteamID64
```

关键点：当前 `{0}` 和 `{1}` 都是平台账号派生的，无法自定义。

## 2.4 端口转发链路

```js
// game-forward.js
fwMap = Map<tag, { forwards, rules }>  // tag = "game:" + gameId

function start(tag, rules, gwPack) {
    // 绑定本机监听端口 → 远端转发
    // 同一 tag 再次 start → 已存在返回失败（端口已绑）
}
function stop(tag) {
    // 关闭 socket → 删除 fwMap entry
}
```

## 3.2 instanceId 格式

```
{gameId}_{timestamp}_{random6}
示例：12345_1700000000000_abcdef
```

每次 spawn 前端生成，唯一标识一次启动会话。

## 3.3 端口转发引用计数

```js
// game-forward.js 改造
fwMap = Map<tag, { forwards, rules, refCount }>

start(tag, rules, gwPack):
  entry = fwMap.get(tag)
  if entry && entry.refCount > 0:
    entry.refCount++
    return Promise.resolve({ ok:true, reused:true })  // 跳过绑定
  // 原有绑定逻辑...
  fwMap.set(tag, { forwards, rules, refCount:1 })

stop(tag):
  entry = fwMap.get(tag)
  if !entry return 0
  entry.refCount--
  if entry.refCount > 0: return 0  // 还有其他实例在用
  // 原有 close socket 逻辑...
  fwMap.delete(tag)
```

```js
onGameLaunching: function (info) {
    if (!state.launching[info.gameId]) state.launching[info.gameId] = {};
    state.launching[info.gameId][info.instanceId] = Date.now();
    scheduleRefresh();
},
onGameStart: function (info) {
    if (!state.running[info.gameId]) state.running[info.gameId] = {};
    state.running[info.gameId][info.instanceId] = true;
    if (state.launching[info.gameId]) delete state.launching[info.gameId][info.instanceId];
    scheduleRefresh();
},
onGameExit: function (info) {
    if (state.running[info.gameId]) delete state.running[info.gameId][info.instanceId];
    if (state.launching[info.gameId]) delete state.launching[info.gameId][info.instanceId];
    scheduleRefresh();
},
onGameLaunchError: function (info) {
    if (state.launching[info.gameId]) delete state.launching[info.gameId][info.instanceId];
    scheduleRefresh();
}
```

### 4.6.3 launchGame 改造

```js
function launchGame(gid, opts, onResult) {
    // opts = { accountId, instanceId, customUsername, customPassword, accountLabel }
    if (!username) { toast('请先登录'); return; }
    if (!DESKTOP || !DESKTOP.gameLaunch) { toast('请在 PC 客户端中启动游戏'); return; }

    // 多开数量校验
    var gameInfo = state.games[gid] || {};
    var max = gameInfo.max_instances || 1;
    var allowMulti = !!gameInfo.allow_multi_instance;
    var count = runningCount(gid);

    if (!allowMulti && count >= 1) {
        toast('游戏正在运行中'); return;
    }
    if (count >= max) {
        toast('已达最大实例数（' + max + '）'); return;
    }
    if (isLaunching(gid)) {
        toast('游戏正在启动，请稍候…'); return;
    }

    // 生成 instanceId
    var instanceId = (opts && opts.instanceId) ||
        (gid + '_' + Date.now() + '_' + Math.random().toString(36).slice(2, 8));

    // 标记 launching
    if (!state.launching[gid]) state.launching[gid] = {};
    state.launching[gid][instanceId] = Date.now();
    scheduleRefresh();

    // 后续流程与现有一致，在 payload 里加新字段...
}
```

# 五、兼容性

| 场景 | 处理 |
|------|------|
| 旧版本 game-launch.json 无 accounts 字段 | `JSON.parse` 后 accounts 为 undefined → 安全跳过，走原逻辑 |
| 不支持多开的游戏（allow_multi_instance=false） | UI 上不显示 caret、启动按钮按原样单实例；服务端 max_instances=1 |
| SmartSteamEmu 游戏 | 维持原单实例 sseBusy 检查，UI 上也不显示多开入口 |
| WEB 端（无 desktop bridge） | 所有多开/自定义账号 UI 隐藏或禁用，提示同现有「请在 PC 客户端中启动游戏」 |
| Win7 客户端（无游戏启动能力） | 本来就无 game:launch handler，无需额外适配 |
| 已有 runningGames 条目（应用重启后） | game-running-list 返回时 main.js 里 Map 已空，重启后实例状态清空，客户端重新 spawn |

# 六、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 端口转发监听端口被游戏占用 | 第一个实例绑定失败 | 现有 fwEnsureForLaunch 异步不阻塞启动，绑定失败游戏仍能启动（不走网络联机）；端口转发本身已有错误处理 |
| Overlay 多实例热键冲突 | 多个实例都响应 Shift+Tab | P0 阶段屏蔽非首个实例的 Overlay 热键；P2 做多实例切换面板 |
| 游戏本身有互斥锁 | 多开启动失败（游戏进程秒退） | 这是游戏自身限制；客户端已尽力，启动失败走现有 game:launch-error 广播提示用户 |
| SmartSteamEmu 并发 | 维持不支持（sseBusy 检查保留） | UI 上 SSE 游戏不显示多开入口；硬编码拦截兜底 |
| 自定义账号密码明文内存 | 安全风险 | 密码用 DPAPI 加密存，启动完 main.js 内一次性解密用完即置空（置 null 后 GC 回收） |
| 云存档多实例同时写 | 存档文件损坏 | 云存档仅启动前 pull、退出后 push；运行时游戏自己写存档，多实例同时写是游戏行为 → P2 加文件锁 |
| max_instances 配得过大 | 用户误启动数十实例导致资源耗尽 | 服务端校验上限 100；客户端启动前弹确认「要启动 N 个实例？」 |
| instanceId 生成重复 | 理论上 Date.now()+6位随机 碰撞概率 ~1/1600 万 | 已足够；极端重复时 runningGames.set 覆盖旧条目，旧实例 exit 自然清理 |

# 九、已确认决策

| 编号 | 决策 | 理由 |
|------|------|------|
| D1 | SmartSteamEmu 维持不支持多开 | 全局单一 ini 文件并发互相覆盖，改造复杂且用户基数小 |
| D2 | 端口转发用引用计数复用 | 首个实例绑定端口，后续实例复用；最后一个退出才真关 |
| D3 | instanceId 前端生成 | 避免主进程与前端竞态；格式 `gid_ts_随机` |
| D4 | 账号密码持久化复用 game-launch.json | 不新增配置文件，沿用现有 userData 路径 + DPAPI 加密 |
| D5 | 启动按钮 caret 仅当 allow_multi_instance 且有自定义账号时显示 | 普通单开游戏不增加 UI 复杂度 |
| D6 | Overlay 多实例 P0 屏蔽非首个实例热键 | 简化实现，P2 做多实例切换面板 |
| D7 | max_instances 服务端上限 100 | 防误配过大导致资源耗尽 |
| D8 | 账号至少保留 1 个默认 | 保证启动时总有可用账号 |

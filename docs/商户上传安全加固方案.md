# 商户上传安全加固方案（可行性 + 影响面评估）

> 关联背景：商户上传功能（图片 `handleAdminGameImage` / 游戏版本分片 `handleAdminGameChunk` +
> 版本登记 `gameVersionCreateCore`）上传病毒文件本身**不会执行、不会感染 Linux 服务器文件**
> （全链路 Go 落盘、无 exec 调用、路径穿越已双重防护）。本方案解决的是间接风险：
> 磁盘耗尽、恶意软件经平台分发、浏览器渲染上传内容（存储型 XSS）。

---

## 一、方案 1：静态托管 nosniff + 聊天文件强制 attachment（本次落实）

### 1.1 现状

- 静态托管入口：`main.go` `http.FileServer(http.Dir(cfg.WebDir))` 挂载 `/`，响应无
  `X-Content-Type-Options`；`/static/upload/**` 按扩展名下发 Content-Type（Go 内置 mime 表）。
- 聊天上传 `isDangerousFile` 黑名单拦截 `.exe/.bat/.cmd/.sh/.msi/.com/.scr/.js/.vbs/.ps1/.jar`，
  但 `.html/.htm/.svg/.xml` 等可被浏览器渲染的扩展名未拦——攻击者上传恶意 HTML/SVG 后，
  同域打开 `/static/upload/xxx.html` 即可窃取同源 Cookie/LocalStorage（存储型 XSS）。
- 游戏文件下载 `HandleGameFileDownload` 已强制 `application/octet-stream`（无此问题）；
  本方案只覆盖静态托管路径 `/static/upload/**`。

### 1.2 实现方案（改动最小化，仅动 main.go 一处 handler）

1. **全站静态响应加 `X-Content-Type-Options: nosniff`**：在 `/` handler 内
   `fileServer.ServeHTTP` 之前统一 `w.Header().Set(...)`。
   浏览器此后拒绝"声明类型与内容不符"的嗅探执行（恶意 HTML 改名 .png 也无法被嗅探执行）。
2. **`/static/upload/**` 非内联白名单文件强制 `Content-Disposition: attachment`**：
   - 内联白名单（浏览器可安全渲染、业务必须内联展示的）：
     - 图片：`.png .jpg .jpeg .gif .webp .bmp`（聊天气泡 `<img>`、头像级封面/截图/公告图、admin 附件预览）
     - 视频：`.mp4 .webm .mkv`（商店详情页 `<video>` 宣传视频）
     - 音频：`.mp3 .wav .amr .aac .ogg .m4a`（语音消息/音频文件播放）
   - 白名单之外（pdf/docx/zip/exe……）：下发 `Content-Disposition: attachment; filename="<服务端生成名>"`
     ——浏览器导航打开即触发下载而不是渲染/执行。
   - 文件名安全性：落盘名统一为服务端生成的 `前缀_纳秒_16位hex.扩展`（uploadfile.go /
     announcement.go 归口），纯 ASCII 白字符集，无需 RFC5987 编码，无头注入面。

### 1.3 影响面评估（逐项实测口径）

| 消费方 | 路径/形式 | 影响 | 结论 |
|---|---|---|---|
| 聊天图片气泡（私聊/群聊） | `<img src="/static/upload/xx.png">` | 扩展名在白名单，仍 inline | ✅ 无影响 |
| 聊天语音条 | `<audio>`/fetch blob | 音频扩展名在白名单 | ✅ 无影响 |
| 聊天文件下载（点击气泡/另存为） | 前端 `fetch → Blob → <a download>`（chat.js downloadWithProgress） | fetch 忽略 Content-Disposition，下载名由前端 `a.download` 决定；直链导航场景 attachment 恰好是期望行为 | ✅ 无影响（更安全） |
| 商店封面/截图/详情视频 | `/static/upload/games/**` | 图/视频扩展名在白名单，`<img>/<video>` 内联正常 | ✅ 无影响 |
| 群公告图片/附件（ann_ 前缀） | 图片内联显示；附件点击下载 | 同上分治 | ✅ 无影响 |
| 工作台文件（wb_ 前缀） | 预览用 fetch；下载用 <a download> | fetch 忽略 attachment | ✅ 无影响 |
| OnlyOffice 在线编辑 | DocumentServer **服务端到服务端**回源拉文档 | Content-Disposition 仅约束浏览器，服务端 HTTP 客户端忽略该头 | ✅ 无影响 |
| 管理后台聊天附件预览 | admin.js `img.src=/static/upload/...` | 图片白名单 inline | ✅ 无影响 |
| AI 文件（知识库/文档问答） | 服务端读取本地文件解析，不经浏览器 | 无关 | ✅ 无影响 |
| PC（Electron）/APP 客户端 | 同一 fetch/blob 链路 + `will-download` | 同 WEB 端 | ✅ 无影响 |
| 头像 `/static/avatar/**` | 不在 upload 前缀内，且均为图片 | 不涉及 | ✅ 无影响 |
| 前端 HTML/JS/CSS 本体 | `/`、`/js/**` | Go mime 按扩展名返回正确 Content-Type，nosniff 不拦截类型正确的资源 | ✅ 无影响（唯需保证无"错误扩展名承载 JS/CSS"的遗留约定——现网无此用法） |
| Agent 工作区预览 `/agent/preview`、`/agent/site/**` | 独立路由，不经 `/` fileServer | 本次仅收窄 `/` 静态托管，不波及 | ✅ 无影响 |

**已知取舍**：直链打开 pdf/docx 的行为从"浏览器内预览"变为"触发下载"——这是本方案的目的
（杜绝同域渲染上传内容），与微信网页版行为一致。

## 二、方案 2：磁盘水位监控告警（本次落实）

### 2.1 现状与缺口

- 管理后台已有 30s 周期告警评估器（`server/alerts.go`，告警随 `/admin/api/metrics` 下发、
  仪表盘横幅展示、触发/恢复自动记日志），但**没有任何磁盘空间规则**。
- 聊天文件、游戏包、网盘均可持续增长，磁盘写满会导致 MySQL/日志写失败、整个服务异常。

### 2.2 实现方案

- 新增 `server/diskusage_windows.go` / `server/diskusage_unix.go`（build tag 分平台）：
  用 `golang.org/x/sys/windows` GetDiskFreeSpaceEx 与 `golang.org/x/sys/unix` Statfs
  实现 `dirDiskUsage(dir)`——**零新增第三方依赖**（x/sys 已在 go.mod）。
- 新增 `server/diskmonitor.go`：
  - 监控目录集合 = 聊天上传目录（UploadDir）+ 游戏数据根目录（Game.LocalDir）+
    网盘本地根目录（Drive.LocalDir，仅本地后端），按绝对路径去重；
  - 60s TTL 缓存 statfs 结果（告警评估 30s 周期与指标接口共用缓存，避免高频 syscall）；
  - 挂入既有 `evaluateAlerts`：使用率 ≥warn 水位触发 `warn` 告警、≥error 水位升级 `error`
    （按目录分键，恢复自动清除）；
  - `/admin/api/metrics` system 节新增 `disk` 数组（目录/总量/剩余/使用率）供仪表盘后续展示。
- 配置节 `disk_monitor`（`enabled` / `warn_percent` 默认 80 / `error_percent` 默认 90），
  enabled=false 时完全旁路。

### 2.3 影响面

纯增量：不改任何上传/下载链路；告警仅读磁盘，开销为每目录每分钟一次 statfs。
唯一行为变化 = 管理后台仪表盘可能出现磁盘告警横幅（这正是需求）。

## 三、方案 3：商户存储总量配额（本次落实）

### 3.1 现状与缺口

- 商户版本上架 `gameVersionCreateCore` 有单文件上限（game.max_file_size）与 ZIP 解压后
  总量上限（game.max_unpack_size），但**商户累计上传无总量约束**——可反复上传新版本
  （旧版本不自动删除）把磁盘吃满。

### 3.2 实现方案

- 配置 `game.merchant_quota_bytes`（字节，默认 50GB，`-1` 不限）。
- **管理员按商户分配专属配额**（管理后台→商户管理）：`im_merchant.storage_quota_bytes`
  （0=跟随全局默认，-1=不限，>0=专属字节），解析归口 `merchantQuotaLimit`——专属优先、
  全局兜底；商户端进度条与上架校验同源即时跟随（列由 AutoMigrate 自动加列）。
- 口径 = 该商户名下全部游戏全部版本的 `im_game_version.size_bytes` 之和（SQL SUM，
  归属隔离复用 owner_username），**不含官方游戏**。
- 校验双保险（均在 `gameVersionCreateCore`，商户名下游戏才生效，管理员上架不受限）：
  1. **合并落位前预检**（快）：已用 + 本次申报大小之和 > 配额 → 直接拒绝（大版本合并耗时
     分钟级，提前拦截不浪费 IO）；
  2. **合并落位后复检**（准）：实际 totalSize 入库前再校验一次，超限整版回滚删除目录
     （申报与实算不一致时以此为准）。
- 错误信息带上"已用/配额"，商户可自助判断需先删旧版本。

### 3.3 影响面

- 仅商户路径生效（`g.OwnerUsername != ""`），官方游戏零感知；配额 `-1` 时全量零开销。
- 对既有测试：gamepack_test 等商户版本用例数据量远小于配额，不受影响；
  配额校验函数对空库/0 值均安全。

## 四、方案 4：ClamAV 病毒扫描接入（本次落实）

### 4.1 现状与缺口

- 商户游戏包天然允许 .exe（这是分发通道），病毒包会经版本下载下发到玩家 Windows 机器。
- 现有防线只有人工审核（audit=1 待审核，管理员审核对外字段），文件本体无自动检测。

### 4.2 实现方案

- 部署形态：**独立 clamd 服务**（Linux `apt install clamav-daemon`，TCP 3310），
  服务端经 clamd INSTREAM 协议流式送扫——不依赖本机安装 clamscan 命令，Windows 开发机
  不受影响，扫描在大病毒库进程进行不拖垮 im-server。
- 新增 `server/clamav.go`：INSTREAM 客户端（`zINSTREAM\0` + 分块 4 字节长度前缀 + 零块结束），
  返回 `OK` / `<签名> FOUND` / 错误。`clamScanDir` 为统一扫描核心，三条链路共用：
- **挂点一·新版本扫描（双模式）**：
  - **异步模式（默认，`clamav.sync=false`）**：`gameVersionCreateCore` 成功登记后，仅商户名下
    游戏（OwnerUsername 非空）异步 goroutine 逐文件扫描落位文件（不阻塞上架响应——大包扫描
    分钟级）。**检出病毒** → 游戏整体自动驳回（audit_status=3 + audit_remark 携带病毒签名与
    文件名），玩家侧过滤墙（audit IN (official, approved)）立即下架隐藏，记 error 日志；病毒
    文件本体保留（供管理员取证）。已知取舍：登记到驳回之间存在分钟级下发窗口。
  - **同步模式（`clamav.sync=true`）**：版本登记**前**同步扫描落位文件——检出即整版回滚拒绝
    （病毒文件不落库存、不可被下载，报错带签名与检出数）；大包扫描分钟级会阻塞商户上架响应，
    由部署方按安全/可用性权衡选择。
- **挂点二·存量回溯扫描（管理端入口）**：管理后台「游戏管理 → 游戏审核 → 病毒扫描（存量回溯）」
  卡片（`POST /admin/api/security/clamav/rescan` 启动 + `GET .../rescan/status` 进度轮询）。
  后台单飞任务逐版本扫描全部商户名下游戏的落位目录，检出自动驳回（同游戏去重），命中明细
  （slug/版本/相对路径/签名）实时展示；任务态纯内存、关闭页面不中断。
- **fail-open 统一语义**：clamd 不可达/超时三种链路均不驳回不删档，仅记 warn 日志（扫描是增益
  不是准入门槛，防扫描服务故障卡死正常上架），人工审核兜底不变；
- 病毒库更新由 clamd 自身 `freshclam` 负责，im-server 无感知。
- 配置节 `clamav`（`enabled` 默认 false / `addr` 默认 127.0.0.1:3310 / `timeout_sec` 默认 600 /
  `sync` 默认 false）。

### 4.3 影响面

- enabled=false（默认）时零开销零行为变化；仅商户路径挂载，管理员上架不扫。
- 异步设计：上架响应时间与不加扫描完全一致；扫描失败不阻断业务（fail-open 已在 4.2 说明）。
- 自动驳回只改 audit 状态（既有状态机语义），不删文件不动版本表——与人工驳回走同一展示/申诉链路。

## 五、配置项汇总（config.yaml 与 config - linux.yaml 同步补齐）

```yaml
# 磁盘水位监控（30s 评估周期，告警展示于管理后台仪表盘横幅）
disk_monitor:
  enabled: true
  warn_percent: 80     # 预警水位（%）：触发 warn 告警
  error_percent: 90    # 严重水位（%）：触发 error 告警

# ClamAV 病毒扫描（clamd INSTREAM；仅扫描商户上架的版本文件）
clamav:
  enabled: false       # 需自建 clamd 服务（Linux: apt install clamav-daemon）后开启
  addr: "127.0.0.1:3310"
  timeout_sec: 600     # 单文件扫描超时秒（0=600）
  sync: false          # true=版本登记前同步扫描（检出即回滚拒绝）；false=登记后异步扫描（检出自动驳回）

game:
  # ...既有项...
  merchant_quota_bytes: 53687091200   # 商户存储总量配额（字节，默认 50GB；-1 不限）
```

## 六、测试与验收

- `go build ./...` 全量编译；`go test ./server -run 'Merchant|Game'` 商户/游戏链路回归。
- 手工验收口径：
  1. 上传 .png 直链浏览器内联显示；上传 .pdf 直链触发下载（响应带 attachment）；
  2. 响应头含 `X-Content-Type-Options: nosniff`；
  3. 商户连续上架超出配额的版本被拒（报已用/配额），管理员上架不受限；
  4. 启用 clamav 后上架含 EICAR 测试串的版本：异步模式游戏自动驳回且 remark 含签名；
     同步模式登记被拒（版本回滚不可下载）；clamd 停机时上架不受影响（仅日志）；
  5. 磁盘使用率超过 warn_percent 时管理后台出现告警横幅，回到水位下自动恢复；
  6. 管理后台「游戏审核」页点「全量重扫」：任务进度实时刷新，检出 EICAR 的存量游戏被自动
     驳回且命中明细（slug/版本/文件/签名）展示；clamd 停机时任务跳过并继续（fail-open）。

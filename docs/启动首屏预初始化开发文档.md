# 启动首屏预初始化开发文档

> 目标：PC 客户端启动时，在首屏闪屏（Splash）阶段就完成所有可提前的初始化操作，进入聊天主页时 AI/MCP/更新检测等已就绪，类似微信体验。
>
> 作者：即时通开发团队
> 版本：v1.0 （2026-11-16 初稿，待评审定稿后实施）

---

## 一、现状分析

### 1.1 当前启动时间线（main.js 实测打点）

```
双击启动 → BOOT_T0
  │
  ├─ require 链（agent-executor / mcp-manager / web-cache / browser-manager / updater ...）     ~150ms
  │
  ├─ app.whenReady() → BOOT_T1                                                                1~3s（Chromium 启动）
  │     │
  │     ├─ createSplash()                  闪屏窗创建 + show                                +~50ms
  │     ├─ webCache.init()                  缓存目录/加密密钥初始化                           +~20ms
  │     ├─ webCache.installInterceptor()   http/https 拦截安装                              +~10ms
  │     ├─ webCache.sync() （不 await）    后台增量同步（60s 总超时）                         后台跑
  │     ├─ createWindow()                  主窗口创建 + loadURL（show:false）                +~100ms
  │     ├─ createTray()                    托盘图标                                           +~30ms
  │     ├─ updater.init()                  自动更新（10s 后异步检查）                        后台跑
  │     ├─ browserManager.init()           内置浏览器管理器 IPC 注册                          +~20ms
  │     ├─ registerShotRecShortcuts()      Alt+A / Ctrl+Alt+R 全局快捷键                     +~50ms
  │     └─ deferEditorWarmup()             主窗口加载完 5s 后预热编辑器窗口                  延迟跑
  │
  ├─ 主窗口 did-finish-load → revealMainWindow()                                              +300~1500ms（取决于缓存命中/网络）
  │     │
  │     └─ 用户首次看到聊天界面
  │
  ├─ 前端 chat.js 初始化 → 连接 WS → 自动登录 autoLogin                                       +500~2000ms
  │     │
  │     └─ 用户看到"已连接"、会话列表
  │
  ├─ 前端登录成功后才触发：
  │     ├─ desktop.mcpSyncState(username)  → mcpManager.setConfig() → 拉起 MCP 子进程      +15~120s（取决于插件握手）
  │     ├─ reportPcMcpTools()             → Agent 工具清单上报服务端
  │     ├─ agentExecutor 工作区扫描       → 本地工具链状态探测
  │     └─ 其他 AI 相关初始化...
```

### 1.2 痛点

| 问题 | 用户体感 | 根因 |
|------|---------|------|
| 首次使用 AI Agent 响应慢 | 点 AI 对话后转圈 15~120s | MCP 子进程在登录后才 spawn + initialize 握手 |
| 更新检测慢 | 启动后 10s 才检查更新 | updater.init() 内部延迟定时器 |
| 页面内 AI/MCP 面板先显示"未连接" | 用户打开 MCP 设置页看到一片空白/连接中 | 会话尚未建立 |
| 启动闪屏只有 logo | 用户不知道是卡死了还是在加载 | 闪屏无进度反馈 |

## 二、可行性结论

### 2.1 可行 ✅

**核心依据**：
1. **启动闪屏存在天然等待窗口** —— Chromium 启动 + 主窗口创建 + 页面加载约 1.5~4s，这段时间主进程基本空闲，可以塞入初始化任务。
2. **本地持久化数据启动即可读** —— `agent_mcp.json`（MCP 配置）存 `userData/`，主进程 `whenReady` 时就可读取，不依赖登录态。
3. **MCP 子进程是独立长驻进程** —— spawn 后走 stdio 握手，不阻塞主进程消息循环。
4. **微信/QQ/VS Code/Trae CN 都这么做** —— 闪屏阶段完成登录恢复 + 后台预热，进入主界面时核心功能已就绪。

### 2.2 需要解决的前提问题

| 问题 | 解决方案 | 复杂度 |
|------|---------|--------|
| 启动时不知道当前用户名 | 读 `agent_mcp.json` 中所有存过的用户配置，全部预热；**或者**主窗口页面加载后通过 IPC 把 autoLogin 恢复的用户名推给主进程 | 低 |
| MCP 握手超时 15s 会不会阻塞启动 | **不 await**。闪屏继续展示 logo + 状态文字，MCP 在后台建连，主窗口 reveal 时不强求 MCP 已 ready | 低 |
| 低性能机器启动高峰叠加 CPU/IO | MCP 预热改为 `setTimeout(deferMs)` 延迟 300ms 启动，错峰 createWindow 的 Chromium 进程创建 | 低 |
| 首次安装没 MCP 配置 | 跳过，不做任何事 | 无 |
| uv/Node 工具链未装时 MCP spawn ENOENT | 拉起 autoInstallNode/autoInstallUv，后台下载，不阻塞启动 | 已有逻辑 |

## 三、具体实施方案

### 3.1 闪屏升级：从"纯 logo"到"带进度状态"

#### 3.1.1 闪屏增加状态文字和进度条

**当前实现**（[main.js#L605-660](file:///e:/SourceCodeIM/im-client/pc/main.js#L605-L660)）：data URL 全内联 HTML，只有 logo + "即时通" 文字。

**改造方案**：
- 闪屏 HTML 增加状态文字 `<div id="splash-status">正在启动…</div>`
- 主进程通过 `splashWin.webContents.executeJavaScript()` 推送状态更新
- 状态序列：`正在加载资源…` → `正在检查更新…` → `正在初始化 AI 助手…` → `正在启动 MCP 服务…` → `正在连接服务器…` → 进入主界面

**示意代码**（伪代码）：
```javascript
// createSplash() 内新增：
splashWin._setStatus = function(text) {
    try {
        splashWin.webContents.executeJavaScript(
            'document.getElementById("splash-status").textContent=' + JSON.stringify(text),
            true
        );
    } catch(e) {}
};
```

#### 3.1.2 闪屏阶段初始化任务编排

在 `whenReady` 回调中，**webCache.sync() 之后、createWindow() 之前**（或 createWindow 之后但不等它），按以下顺序启动异步任务：

```
whenReady
  ├─ createSplash()          ← 闪屏立即显示
  ├─ splashStatus('正在加载资源…')
  ├─ webCache.init() + installInterceptor() + sync()  ← 已有
  ├─ splashStatus('正在检查更新…')
  ├─ updater.init() + updater.check(false)           ← 把更新检查提前到闪屏阶段
  ├─ splashStatus('正在初始化 AI 助手…')
  ├─ bootPreloadMcp()                                ← 新增：预拉起 MCP 子进程
  ├─ splashStatus('正在启动主窗口…')
  ├─ createWindow() + createTray()                    ← 已有
  └─ revealMainWindow 由 did-finish-load 触发         ← 已有
```

### 3.2 MCP 预拉起实现

#### 3.2.1 核心逻辑

新增函数 `bootPreloadMcp()`，在 `whenReady` 中调用：

```javascript
function bootPreloadMcp() {
    // 1. 读本地所有用户的 MCP 配置
    var store = mcpStoreLoad();  // 已有函数，读 userData/agent_mcp.json
    
    // 2. 拉起所有用户的 MCP 会话（让它们在后台建连）
    Object.keys(store).forEach(function(username) {
        if (username === '__builtin' || username === '__browser' || 
            username === '__projMcp') return;  // 跳过内置开关键
        var rec = store[username];
        if (rec && rec.servers && rec.servers.length) {
            // setTimeout 延迟 300ms，错峰 createWindow 的 Chromium 启动高峰
            setTimeout(function() {
                try { mcpManager.setConfig(username, rec.servers); } catch(e) {}
            }, 300);
        }
    });
    
    // 3. 内置 Computer Use 服务器总是预热（enabled=true 时）
    var builtinEnabled = mcpBuiltinEnabledLoad();
    if (builtinEnabled) {
        mcpManager.setBuiltinEnabled(true);
        // 找一个用户名触发内置服务器拉起（用第一个用户或 __preload__ 占位）
        var firstUser = Object.keys(store).find(k => !k.startsWith('__'));
        if (firstUser) {
            setTimeout(function() {
                try { mcpManager.setConfig(firstUser, (store[firstUser] && store[firstUser].servers) || []); } catch(e) {}
            }, 350);
        }
    }
    
    // 4. 工具链预检（uv/Node 是否存在，缺失则后台下载）
    //    不阻塞启动，下载完成后下次 MCP spawn 自动可用
    setTimeout(function() {
        try {
            var store2 = mcpStoreLoad();
            Object.keys(store2).forEach(function(username) {
                // 让 mcp-manager 的 autoInstall 钩子在首次 spawn 时自动触发
                // 这里不主动安装，保持"按需安装"语义
            });
        } catch(e) {}
    }, 1000);
}
```

#### 3.2.2 需要 mcp-manager.js 的小改动

mcp-manager.js 当前的 `createSession()` 在 spawn 时如果工具链缺失（uvx/Node），会自动触发 `autoInstallNode/autoInstallUv`。这个逻辑**已经完整存在**，不需要改。

唯一需要确认的：`setConfig` 调用时，内置 `builtinConfigs()` 会合并进来（[mcp-manager.js#L441-470](file:///e:/SourceCodeIM/im-client/pc/mcp-manager.js#L441-L470)），所以只要调用了 `setConfig`，内置 Computer Use 服务器也会自动拉起 —— 上面代码里的"内置预热"逻辑可以简化。

**简化后的 bootPreloadMcp()：**
```javascript
function bootPreloadMcp() {
    var store = mcpStoreLoad();
    var builtinEnabled = mcpBuiltinEnabledLoad();
    mcpManager.setBuiltinEnabled(builtinEnabled);
    
    Object.keys(store).forEach(function(username) {
        if (username.startsWith('__')) return;  // 跳过 __builtin/__browser/__projMcp
        var rec = store[username];
        if (rec && rec.servers && rec.servers.length) {
            setTimeout(function() {
                try { mcpManager.setConfig(username, rec.servers); } catch(e) {}
            }, 300);
        } else if (builtinEnabled) {
            // 即使用户没有自定义服务器，也拉起内置 Computer Use
            setTimeout(function() {
                try { mcpManager.setConfig(username, []); } catch(e) {}
            }, 300);
        }
    });
}
```

### 3.3 更新检测提前

#### 当前实现（[main.js#L6852-6857](file:///e:/SourceCodeIM/im-client/pc/main.js#L6852-L6857)）

```javascript
try {
    if (codeUpdater) codeUpdater.init({ serverUrl: SERVER_URL, getThemeDark: resolveBootDark });
} catch (e) { }
```

code-updater.js 内部有 `setTimeout(check, 10000)` —— 启动后 10s 才检查。

#### 改造方案

把更新检查前置到闪屏阶段：
```javascript
// webCache.sync() 之后
splashStatus('正在检查更新…');
// 把 updater.init 里的延迟定时器从 10s 改为 1s（或直接 check）
try {
    updater.init({ serverUrl: SERVER_URL, getThemeDark: resolveBootDark, immediateCheck: true });
} catch (e) { }
```

updater.js / code-updater.js 改造：增加 `immediateCheck` 选项，true 时跳过 10s 延迟，立即发起检查（检查本身是纯网络请求，不阻塞）。

### 3.4 闪屏最小显示时间

微信闪屏大约固定显示 2~3s（有动画），无论内部初始化完成与否。这样用户看到的是"启动流畅"，不会因为 MCP 慢就一直卡在闪屏。

**方案**：闪屏最小显示 1.5s（足够用户看到 logo + 至少一条状态文字），之后无论 MCP/更新等初始化完成与否，直接 revealMainWindow。主窗口内继续后台完成剩余初始化。

```javascript
// revealMainWindow 增加最小显示时间守卫
var splashShownAt = Date.now();
var MIN_SPLASH_MS = 1500;

var revealMainWindow = function () {
    if (splashClosed) return;
    var elapsed = Date.now() - splashShownAt;
    if (elapsed < MIN_SPLASH_MS) {
        setTimeout(revealMainWindow, MIN_SPLASH_MS - elapsed);
        return;
    }
    splashClosed = true;
    if (splashWin) { try { splashWin.close(); } catch(e) {} splashWin = null; }
    if (mainWindow && !mainWindow.isVisible()) mainWindow.show();
};
```

## 四、不做的事（边界范围）

| 项目 | 原因 |
|------|------|
| 闪屏阶段等待 MCP 握手完成 | 有些 MCP 插件握手超时 120s（uvx 首次下载 Python 包），不能卡启动 |
| 闪屏阶段阻塞等待 webCache.sync 完成 | 当前 sync 已经不 await，保持不变 |
| 闪屏阶段做 Agent 工作区扫描/工具链安装 | 这些需要登录态 + 用户工作区路径，登录前不知道；且耗时可能很长 |
| 闪屏阶段读取 localStorage 登录态自动登录 | WS 连接建立本身需要 500ms+，放闪屏里收益不明显；前端 autoLogin 已经很快 |
| 闪屏期间显示进度条百分比 | 各模块耗时不可预估，显示"阶段状态文字"更准确 |

## 六、风险评估与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 低性能机器启动高峰 CPU 叠加 | Chromium + MCP 子进程同时 spawn 让启动更慢 | MCP 预热 setTimeout 延迟 300ms，错峰 Chromium 创建 |
| 杀毒软件拦截多个子进程同时 spawn | 误报/延迟 | MCP 已在正常登录后就 spawn，数量没变，只是时机提前；杀软行为不变 |
| agent_mcp.json 含已删除的旧用户 | 预热无效子进程 | 读取后过滤：该用户不在好友列表/最近登录，跳过（可选优化） |
| 更新检查提前后弹窗打断启动 | 用户看到更新弹窗盖在登录界面上 | 更新弹窗显示判断：主窗口 isVisible 且 isFocused 才弹 |
| 闪屏状态文字 executeJavaScript 在某些环境报错 | 状态不更新但不影响主流程 | try-catch 包裹，失败静默 |

## 九、结论

**完全可行，推荐实施。**

核心思路：
1. **闪屏不空等** —— 利用天然的 1.5~4s 等待窗口在后台预热 MCP 子进程和更新检测
2. **不阻塞 reveal** —— 闪屏最小显示 1.5s 后立即进入主界面，MCP 等继续后台建连
3. **改动面极小** —— 主要是 main.js 增加约 80 行，现有模块的公开 API 已全部满足需求
4. **用户体验收益明显** —— 首次 AI 对话响应时间缩短 50%~80%，启动流畅感提升

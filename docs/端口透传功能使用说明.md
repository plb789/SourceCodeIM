# 端口透传转发功能使用说明

> 适用版本：2026-10-22 之后编译的 im-client（PC 端）、im-server、im-gateway
> 涉及代码：`im-client/pc/game-forward.js`（客户端转发器）、`im-server/server/game.go`（token 签发/下发）、`im-server/server/gameadmin.go`（规则清洗）、`im-server/gateway/main.go`（远程加密网关）

---

## 1. 功能概述

游戏端口透传转发解决一个问题：**让游戏以为自己在连本机，实际流量被透明转发到远端真实游戏服务器**。

支持两种转发模式，可按游戏/按规则混用：

| 模式 | 规则前缀 | 数据流 | 适用场景 |
|---|---|---|---|
| **直连模式** | `tcp:` / `udp:` | 游戏 → 本机 127.0.0.1 监听 → 明文直连远端地址 | 远端服务器本身可信网络，或游戏服务器在公网正常暴露端口 |
| **网关模式** | `gtcp:` / `gudp:` | 游戏 → 本机 127.0.0.1 监听 → **加密隧道** → 远程 im-gateway → 网关本机 127.0.0.1 的真实游戏服务端 | 真实游戏服务端只监听回环不暴露公网；需要防探测/防劫持/防跳板 |

核心特性：

- **启动游戏自动开启**：客户端启动游戏前自动按该游戏配置的规则开启全部监听；任一端口绑定失败则中止启动并提示（游戏不会起来连空口）。
- **退出自动关闭**：游戏退出、启动失败、客户端退出，三路均自动收口。
- **零配置客户端**：玩家侧无需任何配置，规则由管理端按游戏配置、随游戏库接口自动下发。
- **加密网关全拒机制**：未过 TLS 握手断开、token 非法/过期断开、目标不在白名单拒绝、UDP 未知会话/解密失败/重放**静默丢弃**——外部探测连端口存在性都感知不到。

## 2. 架构与数据流

```
【直连模式】
游戏 ──> 127.0.0.1:7777 (PC客户端监听) ──明文──> 远端游戏服务器 1.2.3.4:7777

【网关模式】
游戏 ──> 127.0.0.1:7777 (PC客户端监听)
           │
           └─加密隧道(TLS1.3/AES-256-GCM)──> 远程服务器上的 im-gateway
                                                │ 校验 token/白名单
                                                └──> 127.0.0.1:18001 (真实游戏服务端，仅回环)
```

### 加密协议摘要（网关模式）

- **TCP**：每条游戏连接一条 TLS 1.3 → 首帧声明 `{token, target}` → 验签 + 白名单校验 → 回 `{ok:true}` 后裸字节双向透传。
- **UDP**：先建 TLS 控制连接注册会话，网关下发 `session + k1 + k2`（双向独立密钥）；之后数据包逐包 `AES-256-GCM` 加密（12B 明文头作 AAD，nonce = 方向前缀 + 8B 计数器，滑动窗口防重放），载荷上限 1200B。
- **token**：服务端按账号 HMAC-SHA256 签发，24 小时有效，格式 `hex(expire).username.hex16(mac)`；密钥只存服务端与网关配置，不下发客户端。
- **证书 pin**：网关使用自签证书，客户端持 SHA256 指纹校验，指纹不符立即断开——防假网关冒充与中间人。

## 3. 角色与文件清单

| 角色 | 位置 | 职责 |
|---|---|---|
| PC 客户端转发器 | `im-client/pc/game-forward.js`（随 im-client.exe 打包） | 本机 127.0.0.1 监听、加密隧道、随游戏启停 |
| im-server | `im-server/bin/im-server.exe` | 管理端规则存储/清洗、token 签发、网关地址簿下发 |
| im-gateway | `im-server/gateway/main.go` 编译，单二进制 + `gateway.yaml` | 部署在远程游戏服务器，收加密流量转本机回环 |
| 管理端 | `im-client/web/admin.html` 游戏管理表单 | 为每个游戏配置转发规则 |
| 服务端配置 | `im-server/bin/config.yaml`（同步 `config - linux.yaml` / `config - 模板.yaml`） | 网关地址簿与 token 密钥 |

## 4. im-server 配置（网关地址簿）

### 4.1 后台热更（推荐）

地址簿支持在管理后台直接维护，**改完立即生效，无需重启服务端**：

**入口：后台 → 游戏管理 → 网关地址簿**（游戏管理二级菜单）：

| 字段 | 说明 |
|---|---|
| 网关名（@名） | 转发规则行尾 `@此名` 引用；小写字母/数字/_/-，全表唯一 |
| 公网地址 | `host:port`（如 `1.2.3.4:30100`），全表唯一（同地址勿重复登记） |
| 证书指纹 | 网关首启日志输出的 64 位 SHA256 hex；网关更换证书后须同步更新 |
| 排序 | 小在前；规则缺省 `@名` 时引用第一个启用条目 |
| 启用 | 停用后不再下发（存量客户端下次拉游戏库收敛） |

生效链路：`后台保存 → 落库 im_gateway_book → 玩家下次打开游戏库拿到新地址簿 → 下次启动游戏生效`。已建立的转发连接不受影响。

#### 操作步骤

**新增网关（新部署一台 im-gateway）**

1. 在远程服务器完成网关部署与启动（步骤见第 5 章）；
2. 后台 → 游戏管理 → 网关地址簿 → **添加网关**；
3. 填网关名（如 `gw-hz`）、公网地址（如 `1.2.3.4:30100`），然后点指纹框旁的 **「从网关获取」** 按钮自动回填（或从首启日志复制指纹手动粘贴）；
4. **专属密钥**：新增时留空 → 服务端自动生成 64hex 随机密钥（也可点 **「重新生成」** 手动生成）——保存后把该值复制到这台网关机 gateway.yaml 的 `token_secret` 并重启网关（两端一致才能通过验签）；
5. 保存前核对 toast 提示的**证书有效期**（应与网关侧证书一致，自签证书约 10 年）——获取语义是"首次信任"（TOFU），请确保获取时刻后台到网关的网络链路可信；
6. 验证：打开「游戏管理 → 新增游戏」，转发规则框下方提示应出现 `gw-hz（1.2.3.4:30100）`；
7. 玩家侧：下次打开游戏库后，游戏的 gw 规则即可经 `@gw-hz` 走新网关。

**更换证书（网关重签/重新生成证书后）**

1. 网关侧更换证书并重启（删除 gateway.crt/key 才会重新生成自签）；
2. 后台编辑对应条目 → 点 **「从网关获取」** 重新回填指纹 → 保存；
3. 存量玩家无需任何操作：下次启动游戏即按新指纹 pin 连接（期间已在游戏中的会话不受影响）。

**轮换某网关的专属密钥（怀疑该网关密钥泄露 / 定期轮换）**

1. 后台编辑该条目 → 点 **「重新生成」** → 保存（仅该网关失效，其他网关与全部玩家 token 不受影响）；
2. 把新密钥同步到该网关机 gateway.yaml 的 `token_secret` → 重启该网关；
3. 该网关的玩家下次拉库/启动游戏即恢复；期间该网关隧道与写库拉取会 401（日志可见，属预期）。

**迁移服务器 / 换公网地址**

直接编辑条目的公网地址保存即可（网关名不变则游戏规则无需改动）。

**下线网关**

1. 先**停用**（观察一段时间确认无玩家再使用该网关）；
2. 确认后再**删除**——删除后引用 `@该名` 的游戏规则在玩家启动时立即报"网关「xxx」未在服务端地址簿中配置"。

#### 注意事项

- **生效时机 = 玩家下次拉游戏库**，不是实时踢连接：正在游戏中的隧道继续走旧地址，退出后下次启动收敛。
- **删除/改名前先查引用**：网关名就是规则的引用名——改名或删除会让所有引用 `@旧名` 的游戏规则失效；先在「新增游戏」页各游戏转发规则里确认引用情况，同步修改后再操作。
- **优先停用而非删除**：停用可随时回滚；删除不可逆（重新添加需重填全部字段）。
- **指纹必须与网关实际证书一致**：不一致客户端 pin 校验直接拒绝连接（提示"证书指纹不匹配"）；这是防冒充/中间人的核心机制，不要为了图省事乱填。
- **专属密钥（逐网关独立）**：地址簿条目可配置本网关专属验签密钥（新增自动生成，64hex）——与该网关机 gateway.yaml `token_secret` 必须一致；**泄露/轮换半径仅该网关**（换密钥后其他网关与玩家 token 不受影响），且写库拉取签名通过即密码学证明网关身份。留空条目回退共享 `gateway_token_secret`（兼容存量部署）。**旧版客户端注意**：条目配置专属密钥后，未升级的旧客户端（内置旧转发器只认顶层共享 token）将无法连接该网关——先完成客户端更新再配置专属密钥。
- **共享密钥不在本页**：`gateway_token_secret` 只能在 config.yaml 修改并重启服务端——改密钥会使所有玩家 token 立即失效（需重新登录），属安全事件级变更，不走后台热更（作为未配专属密钥条目的回退密钥保留）。
- **config 静态条目与后台的关系**：config.yaml 的 `game.gateways` 仅在表为空时作为种子自动导入一次；**导入后修改 config 不再影响下发**（避免"改了 config 没生效"的困惑）——日常调整一律到本页操作。
- **唯一性约束**：网关名、公网地址各自全表唯一（同地址重复登记会被拦截）；条目上限 32 条。
- **本地 dev 环境**：后台改动直接生效；生产环境需同步 web 渲染层（admin.html / admin.js）后本页才可见。

### 4.2 config.yaml 静态配置（兜底/首次部署）

`game:` 节仍支持静态配置（改后重启服务端生效）：

```yaml
game:
  # 共享回退密钥：未配置专属密钥的地址簿条目回退用此密钥验签（强随机，32 位以上；仅存本文件不下发）——
  # 改动会使全部玩家共享 token 失效，属安全事件级变更，不走后台；逐网关独立密钥在后台地址簿维护
  gateway_token_secret: "你的强随机密钥"
  # 网关地址簿：每条目 = 一台部署了 im-gateway 的远程服务器（config 无逐网关密钥——
  # 专属密钥在后台地址簿维护，config 种子导入后条目 secret 为空=回退共享密钥）
  gateways:
    - name: "gw-hz"                              # 引用名（小写字母/数字/_/-，地址簿内唯一）
      addr: "1.2.3.4:30100"                      # 网关公网地址 host:port
      fingerprint: "SHA256指纹"                  # 该网关证书指纹（首启日志输出）
    - name: "gw-bj"
      addr: "5.6.7.8:30100"
      fingerprint: "SHA256指纹"
```

要点：

- **config 条目仅在首次启动时作为种子导入后台地址簿表**（表为空且 config 有条目时自动导入），此后地址簿以后台为准，config 条目不再参与下发。
- **表为空时 config 条目兜底生效**（种子导入失败/DB 异常时仍可用）。
- **旧单网关写法兼容**：`gateway: {addr, token_secret, fingerprint}` 仍可解析（地址簿为空时转 `name=default`）。新部署建议直接在后台维护。
- **启用条件**：`gateway_token_secret` 非空且存在 addr/fingerprint 齐备的启用条目，网关字段才随库接口（`/api/game/library`）下发客户端；否则 `gtcp:/gudp:` 规则启动时被拒绝并提示"未配置加密网关"。
- **修改 config.yaml 后需同步补齐** `config - linux.yaml`。
- 管理端游戏表单会自动拉取地址簿（`/admin/api/game/gateways`），在规则框下方实时提示可用网关名（停用条目标注"已停用"）。

## 5. im-gateway 部署与配置

### 5.1 部署步骤

1. 编译/获取对应平台的 im-gateway 单二进制（Windows：`bin/im-gateway.exe`；Linux 产物按需交叉编译）。
2. 上传到远程游戏服务器，与 `gateway.yaml` 放同一目录，运行 `./im-gateway [gateway.yaml]`（缺省读同目录 gateway.yaml）。
3. **记录首启日志中的证书 SHA256 指纹**，填回 im-server 地址簿对应条目的 `fingerprint`（获取方式详见 5.2）。
4. 防火墙放行网关监听的 TCP+UDP 端口；**真实游戏服务端改为只监听 127.0.0.1，并在防火墙关闭其对外端口**。
5. 网关的 `token_secret` 填**本网关的专属密钥**——在 im-server 后台地址簿添加/编辑该条目时生成（见 4.1），复制到此处（两端一致才能通过验签；留空条目回退共享 `gateway_token_secret`）。

### 5.2 证书指纹的获取

指纹 = 网关证书 **DER 编码的 SHA256**（64 位小写 hex），客户端用它 pin 校验防冒充。三种方式结果相同，任选其一：

**方式一：网关首启日志（最简单）**

im-gateway 首次启动生成证书时会直接在日志打印指纹（`[启动] 证书指纹(SHA256): …`），复制即可。日志已滚动丢失时用方式二/三。

**方式二：从证书文件计算（在网关服务器上）**

Linux（gateway.crt 同目录）：

```bash
openssl x509 -in gateway.crt -outform DER | sha256sum
```

Windows（PowerShell，gateway.crt 同目录）：

```powershell
$c = New-Object System.Security.Cryptography.X509Certificates.X509Certificate2('gateway.crt'); ([System.Security.Cryptography.SHA256]::Create().ComputeHash($c.GetRawCertData()) | ForEach-Object { $_.ToString('x2') }) -join ''
```

**方式三：远程在线提取（在自己电脑上跑，验证 + 取指纹一步到位）**

```bash
openssl s_client -connect 网关IP:30100 </dev/null 2>/dev/null | openssl x509 -outform DER | sha256sum
```

Windows 无 openssl 时的 PowerShell 版：

```powershell
$tcp = New-Object Net.Sockets.TcpClient('网关IP', 30100); $ssl = New-Object Net.Security.SslStream($tcp.GetStream(), $false, { $true }); $ssl.AuthenticateAsClient('gw'); $cert = New-Object System.Security.Cryptography.X509Certificates.X509Certificate2($ssl.RemoteCertificate); ([System.Security.Cryptography.SHA256]::Create().ComputeHash($cert.GetRawCertData()) | ForEach-Object { $_.ToString('x2') }) -join ''; $ssl.Dispose(); $tcp.Dispose()
```

要点：

- **推荐直接用后台「从网关获取」按钮**（见 4.1）：填好公网地址后一键回填，无需登服务器
- 方式三还能顺带验证网关端口可达、TLS 握手正常，**部署验收时最实用**
- 指纹填到后台「网关地址簿」对应条目（见 4.1）；网关以后更换证书指纹会变，须同步更新
- 三种方式输出的都是 64 位小写 hex，与后台校验格式一致（大写字母粘贴后也会被自动归一）

### 5.3 gateway.yaml 全字段说明

模板见 `im-server/bin/gateway.yaml`。

```yaml
# —— 全局 ——
token_secret: "本网关的专属密钥（后台地址簿生成）"   # 必填；须与 im-server 地址簿条目「专属密钥」一致
max_tcp_conns: 512        # TCP 透传连接上限（每组监听独立计数）
max_udp_sessions: 256     # UDP 会话上限（每组监听独立计数）
tls_cert: "gateway.crt"   # 缺省自动生成自签 ECDSA P-256（10 年），日志输出指纹
tls_key: "gateway.key"

# —— 【新格式·推荐】多监听组：单实例监听多个公网端口，每组专属白名单（隔离性等同多实例）——
listens:
  - name: "game-a"               # 组名（日志标识；建议与 im-server 地址簿条目对应）
    listen_tcp: "0.0.0.0:30100"  # 该组 TLS 监听（TCP 数据面 + UDP 控制面同端口）
    listen_udp: "0.0.0.0:30100"  # 该组 UDP 数据面监听（可与 TCP 同号）
    allow_targets: [3054, 3053]  # 该组专属白名单：仅允许转发到本组列出的 127.0.0.1 端口
  - name: "game-b"
    listen_tcp: "0.0.0.0:30101"
    listen_udp: "0.0.0.0:30101"
    allow_targets: [7777]

# —— 【旧格式·仍兼容】单监听（listens 为空时自动按此启用，等价 name=default 一组）——
listen_tcp: "0.0.0.0:30100"
listen_udp: "0.0.0.0:30100"
allow_targets: [7777, 6112]

# —— 【可选】Web 管理后台（两字段齐备才启动；见 5.5）——
admin_listen: "127.0.0.1:30101"
admin_password: "后台登录强密码"

# —— 【可选】游戏账号写库（enabled 才启动拉取器；见 5.6）——
dbwrite:
  enabled: true
  gateway_name: "game-a"                 # 自报网关名（= im-server 地址簿条目名，服务端据此按网关过滤队列）
  im_addr: "http://im服务器地址:2087"
  type: mysql                            # mysql / mssql
  dsn: "user:pass@tcp(127.0.0.1:3306)/gamedb"
  strategy: upsert                       # insert / update / upsert
  poll_sec: 30
  sql_insert: "INSERT INTO members(account, password) VALUES({user}, {password})"
  sql_update: "UPDATE members SET password={password} WHERE account={user}"
```

要点：

- `listens` 与旧格式**二选一**；同时存在时 `listens` 优先。
- 各组 TCP 监听地址不可重复（同机同端口启动即报错）。
- `allow_targets` 为空的组启动报错；白名单外的转发目标一律拒绝（防被当内网跳板）。

### 5.4 网关运行行为

- token 验签失败/过期 → 回 `{"ok":false,"err":"auth"}` 后断开。
- 目标端口不在本组白名单 → 回 `{"ok":false,"err":"target"}` 后断开。
- 非 TLS 明文扫描 → 在握手层直接失败。
- **`探测连接（TLS 握手后未发首帧即断开，正常）`** 日志：后台「从网关获取」指纹的探测连接、端口扫描、健康检查都会产生这类记录——TLS 握手完成取走证书后未发业务首帧即关闭，属正常行为，**每次点「从网关获取」网关日志会出现一条**，无需处理。
- UDP 未知会话/解密失败/计数器重放 → **静默丢弃，不回包不记日志**。
- UDP 控制连接断开或 90 秒无帧 → 会话回收；客户端周期发空行保活。
- TCP/UDP 连接与会话数按组达到上限后拒绝新连接（已建立的不受影响）。

### 5.5 Web 管理后台（可选）

gateway.yaml 配置 `admin_listen` + `admin_password` 后启动网关即自动开启后台。

| 项 | 说明 |
|---|---|
| 访问 | 浏览器打开 `http://<admin_listen>`，输入后台密码登录 |
| 监听范围 | **默认建议仅 `127.0.0.1:30101`**（零公网暴露面）；远程管理用 SSH 隧道 `ssh -L 30101:127.0.0.1:30101 服务器` 后访问本机 30101 |
| 总览 | 各监听组的 TCP 连接数、UDP 会话数、白名单端口 |
| 白名单热更 | 页面内修改端口列表点「保存热更」：**内存即时生效**（不重启不断连接）+ 自动回写 gateway.yaml（保留原注释，重启不丢） |
| **写库配置热更** | 「游戏账号写库」卡片在线编辑全部字段（连接/类型/DSN/策略/周期/INSERT/UPDATE 模板=换库换表换字段直接改模板文本）+ **「测试连接」**按钮现场验证 DSN → 「保存并热生效」即时重建连接池并落盘，无需重启网关 |
| 安全 | 密码登录 + 内存会话（2h 滑动过期，重启即失效）；未登录访问一律拒绝；模板保存经服务端强校验（非法语句拒绝），热更绝不绕过启动期校验 |

### 5.6 游戏账号写库（dbwrite，可选）

老游戏服务端只读库验证、不自建账号——玩家首次联机前须把「IM 账号 + 启动密码」预先写入游戏库。启用 dbwrite 后全自动完成，**PC 客户端零参与零改动**：

```
玩家 IM 登录 ──> im-server 队列 im_gateway_dbwrite（按网关过滤：游戏规则里的 @网关名 决定归属）
                    ▲ 网关每 poll_sec 秒自报 gateway_name 拉取（HMAC 签名 + 响应 AES-256-GCM 加密）
                    ├─> 按 SQL 模板参数化写入网关本机游戏库（占位符 {user}/{password} 强制绑定，注入免疫）
                    └─> 写成功回执 ack（body 纳入签名防篡改）；写失败不回执，下轮自动重试
```

部署步骤（网关侧）：

1. gateway.yaml 启用 `dbwrite` 节：`gateway_name` 填 im-server 地址簿里**本网关的条目名**；`im_addr` 填 im-server 地址（走 2087 现有端口，零新增暴露面）；
2. `type`/`dsn` 按本机游戏库填写（四类型全支持：**mysql / mssql / postgres / sqlite**，均为纯 Go 驱动；后台「测试连接」可现场验证；亦可在后台在线编辑热更，见 5.5）；`strategy` 建议 `upsert`（账号在库则改密、不在则插入）；
3. SQL 模板按游戏库表结构填写。模板规则（启动即校验，非法拒绝启动写库）：
   - 语句白名单：`INSERT` / `UPDATE`（内部可任意复杂——子查询、JOIN、INSERT..SELECT、多表关联更新）/ `MERGE`（MSSQL、PG15+）/ `CALL`·`EXEC` 存储过程（**复杂多表+事务逻辑建议写在游戏库端存储过程里，网关模板只带参调用**；sqlite 无过程不支持）；DELETE/DROP/TRUNCATE/ALTER/CREATE/SELECT 一律拒绝；merge/call/exec 类模板自带全语义，无论策略均单次执行；
   - 禁分号多语句（MERGE 尾分号豁免）、禁 `--` 与 `/*` 注释；
   - 占位符仅 `{user}`（IM 账号）与 `{password}`（16 位启动密码，同账号恒定，与启动参数 `{1}` 同源）；
   - 强制参数绑定执行；若游戏侧密码列存哈希，可写 `MD5({password})` 等数据库函数处理。
4. 重启 im-gateway，日志出现 `[dbwrite] 拉取器已启动` 即生效。

服务端侧（im-server，自动）：重启 im-server 后新表 `im_gateway_dbwrite`/`im_gateway_dbwrite_ack` 自动迁移；玩家登录成功与游戏启动心跳自动入队。入队归属两条路径（并集）：① 游戏配置了网关模式转发规则 → 按规则 `@网关名` 归属；② **游戏不配转发规则时，管理端游戏表单选「仅写库网关」显式声明归属**（玩家客户端直连游戏服务器、无隧道，网关只负责写库）。两者都不配 = 纯游戏不写库。

安全要点：账号与启动密码在 2087 明文链路上**全程密文**（AES-256-GCM）；真实 IM 登录密码绝不参与本链路；网关日志不打印密码；启动密码按**每游戏独立密钥**（im_game.game_secret，上架/启动自动生成）派生——单游戏密码体系泄露/需轮换时只换该游戏密钥，队列自动重写该游戏库，其他游戏零感知。

## 6. 管理端规则配置

游戏管理表单的"端口透传规则"编辑框，**每行一条**，格式：

| 行格式 | 含义 |
|---|---|
| `tcp:本机端口=远端host:远端端口` | 直连 TCP（如 `tcp:7777=1.2.3.4:7777`） |
| `udp:本机端口=远端host:远端端口` | 直连 UDP（如 `udp:27015=5.6.7.8:27015`） |
| `gtcp:本机端口=网关本机端口@网关名` | 经加密网关 TCP（如 `gtcp:7777=18001@gw-hz`） |
| `gudp:本机端口=网关本机端口@网关名` | 经加密网关 UDP（如 `gudp:3053=3053@gw-x`） |

语法规则：

- **网关模式的 `=` 后面是网关那台机器上 127.0.0.1 的端口**（不是公网地址）；真实地址由服务端地址簿的 `addr` 提供。
- `@网关名` 缺省 = 地址簿第一条；同一个游戏的不同规则可引用不同网关。
- 直连规则携带 `@名` 会报错（`@名` 仅网关模式使用）。
- 校验（保存时即拦截，启动时双保险）：本机监听端口 1024~65535、保留端口 3478（TURN/STUN）与 2087（客户端本机服务端口）禁用、远端端口 1~65535、直连 host 须为 IPv4/域名字符集、同批 `协议+本机端口` 去重、每游戏上限 16 条、整串 ≤2048 字符。
- 规则以 JSON 存于 `im_game.port_forwards`，随游戏库/详情接口下发；商店页"本地游戏属性"可编辑，商店游戏属性弹窗只读展示。

### 游戏内配置（双端口游戏客户端配置步骤）

游戏内服务器地址填 `127.0.0.1:本机端口`。客户端会在启动游戏时把本机端口全部监听起来，对游戏完全透明。

单地址游戏（登录即全部连接）只需一处填 `127.0.0.1:端口`。**双端口游戏**（登录口 + 登录后游戏口，如 3053/3054）按游戏类型分三种情形：

**情形 A：客户端/配置文件支持分别设置登录地址与游戏地址（多数网游）**

1. 先在管理端配好该游戏的**两条**转发规则（如 `gtcp:3053=3053@gw-x`、`gtcp:3054=3054@gw-x`）——这两个本机端口要等**从 PC 客户端启动游戏时**才会开启监听，直接双击游戏 exe 是连不上的；
2. 找到游戏客户端的地址配置（常见位置：游戏目录 ini/config 文件、启动器设置页、登录界面"服务器设置"）；
3. **登录地址 / 登录服务器** → `127.0.0.1:3053`；
4. **游戏地址 / 游戏服务器 / 连接服务器** → `127.0.0.1:3054`；
5. 保存，**从 PC 客户端游戏库启动** → 登录 → 验证：网关日志先出现 `target=3053` 会话，登录成功后再出现 `target=3054` 会话，即全链路打通。

**情形 B：客户端只填登录地址，游戏地址由服务端登录响应下发**

登录成功后服务端把"游戏服务器 IP:端口"发给客户端——若下发的不是 `127.0.0.1`，游戏会绕过转发直连公网。处理（按优先级）：

1. **服务端按玩家来源回显**（推荐）：经网关进来的玩家在服务端看到的来源是网关本机，回显 `127.0.0.1:3054` 正好正确——不少服务端框架默认回显来源地址，改配置即可；
2. **服务端固定下发值**：服务端若有"游戏服务器对外地址"配置项，改为 `127.0.0.1:3054`；
3. **都不行则退回直连模式**：按安全部署真实服务端只监听 127.0.0.1 时直连公网会失败（卡"连接游戏服务器中"），该游戏不适合网关模式——管理端规则改为直连（如 `tcp:3053=真实IP:3053`、`tcp:3054=真实IP:3054`）。

**验证与排障**

- 网关日志出现两条会话（登录口 target 与游戏口 target 各一）= 打通；
- **能登录但卡"连接游戏服务器中"** = 第二连接没走到 127.0.0.1（服务端下发了公网 IP）→ 按情形 B 处理；
- 端口对调排查：对照网关日志里 target 端口与游戏实际行为（先连的是登录口）。

## 7. PC 客户端行为说明

| 时机 | 行为 |
|---|---|
| 启动游戏前 | 读取该游戏 `port_forwards`，逐条开监听；网关模式先经地址簿解析 `@网关名` → addr+指纹+token；任一失败 → **中止启动**并 toast 提示原因 |
| 网关 TLS 连接 | 证书指纹 pin 校验，不符立即断开并提示（防冒充/中间人） |
| UDP 会话 | 每个游戏客户端地址独立会话（多socket 互不串线），会话建立期间数据包缓冲，注册完成后续传 |
| 游戏退出/启动失败/客户端退出 | 自动关闭该游戏全部监听与会话（socket 随进程消失，无残留） |
| 重复启动同游戏 | 同 tag 幂等重启；旧实例退出不会误关新实例转发 |

玩家侧无需安装任何东西、无需手动配置——一切随游戏启动自动完成。

## 8. 典型场景配置示例

### 场景 A：一台网关服务多个游戏（多白名单端口）

```
网关 gateway.yaml:  allow_targets: [18001, 18002, 18003]
管理端规则:
  游戏 A:  gtcp:7777=18001@gw-hz
  游戏 B:  gtcp:7778=18002@gw-hz
  游戏 C:  gudp:6112=18003@gw-hz
真实服务端: 都部署在网关机器上，各监听 127.0.0.1:18001/18002/18003
```

### 场景 B：登录口 + 游戏口（如登录 3054、登录后自动连 3053）

```
网关 gateway.yaml:  allow_targets: [3054, 3053]
管理端规则（该游戏两条，同 @网关名）:
  gtcp:3054=3054@gw-x
  gtcp:3053=3053@gw-x        # 3053 若为 UDP 则用 gudp:3053=3053@gw-x
游戏内: 登录地址填 127.0.0.1:3054
前提: 游戏登录后连 3053 的目标也须是 127.0.0.1——客户端双地址配置与服务端回显处理见第 6 章「游戏内配置」
验证: 网关日志先出现 target=3054 会话，登录后再出现 target=3053 会话即打通
```

### 场景 C：不同游戏连不同远端服务器（多网关地址簿）

```
im-server 后台地址簿:  gw-hz(1.2.3.4, 专属密钥 S-hz)，gw-bj(5.6.7.8, 专属密钥 S-bj)
各网关 gateway.yaml:    token_secret 各填自己的专属密钥（gw-hz 机填 S-hz，gw-bj 机填 S-bj）
管理端规则:
  游戏 A:  gtcp:7777=18001@gw-hz     ← 走杭州
  游戏 B:  gtcp:7777=18001@gw-bj     ← 走北京
规则引用了地址簿不存在的网关名 → 启动时报"网关「xxx」未在服务端地址簿中配置"
```

### 场景 D：一台服务器多个接入端口（单实例多监听组）

```
网关 gateway.yaml listens: 两组（30100 白名单 [3054,3053] / 30101 白名单 [7777]）
im-server 地址簿: gw-a → 1.2.3.4:30100，gw-b → 1.2.3.4:30101（同 IP 不同端口）
管理端规则: 游戏 A 用 @gw-a，游戏 B 用 @gw-b —— 组间白名单互相隔离
```

### 场景 E：TCP/UDP 混合游戏

```
管理端规则:
  gtcp:3054=3054@gw-x      # 登录走 TCP
  gudp:3053=3053@gw-x      # 游戏数据走 UDP（逐包 AES-256-GCM）
```

## 9. 运维与排查

### 日志关键字

| 日志 | 位置 | 含义 |
|---|---|---|
| `[启动][组名] 组就绪 TCP=… UDP=… 白名单端口=…` | 网关 | 每组监听就绪（含证书指纹，首启必记） |
| `[tcp][组名] 会话建立 用户=… 目标=127.0.0.1:… 来源=…` | 网关 | 一条 TCP 透传开始 |
| `[udp-ctl][组名] 会话注册 用户=… 会话=xxxx` | 网关 | UDP 会话注册成功 |
| `token 拒绝` | 网关 | token 过期/伪造 → 检查 token_secret 两端一致、客户端重新登录刷新 token |
| `目标端口 N 不在本组白名单` | 网关 | 规则远端端口没加进对应组 allow_targets |
| `网关「xxx」未在服务端地址簿中配置` | 客户端 | 规则 @名 与 im-server gateways 不匹配 |
| `证书指纹不匹配` | 客户端 | 网关换证书后未同步服务端 fingerprint |
| `[admin] Web 后台已启动` | 网关 | 管理后台就绪（admin_listen/admin_password 已配置） |
| `[dbwrite] 拉取器已启动` | 网关 | 写库链路就绪（目标库/策略/周期/网关名） |
| `[dbwrite] 写库失败 username=…` | 网关 | 该条不回执、下轮自动重试 → 检查游戏库 DSN/表结构/模板 |
| `[dbwrite] 拉取失败` | 网关 | im-server 不可达/签名不符 → 检查 im_addr、token_secret 两端一致 |
| `[dbwrite] 未启动：…` | 网关 | 配置/模板非法被启动校验拦截（隧道转发不受影响），按提示修正 dbwrite 节 |
| `网关写库拉取：网关 xxx 取待写条目 N 条` | im-server | 按网关过滤后下发的条目数 |
| `网关写库接口鉴权失败` | im-server | 无签名/过期/篡改 → 核对网关 token_secret 与时钟 |

### 常见问题

| 现象 | 原因与处理 |
|---|---|
| 游戏启动被中止，提示端口占用 | 本机监听端口被其他程序占用 → 换规则的本机端口（避开保留端口 3478/2087） |
| 能登录不能进游戏 | 游戏第二连接的端口没配规则，或服务端下发的不是 127.0.0.1（处理步骤见第 6 章「游戏内配置」情形 B） |
| UDP 语音/数据不通 | 检查网关 UDP 端口防火墙放行；载荷超 1200B 的包会被网关丢弃（游戏正常流量不会触及） |
| token 24h 后全部失效 | 玩家重新登录即刷新；启动游戏取的是库接口最新 token |
| 网关重启后客户端连不上 | 自签证书若重新生成（删除 crt/key 才会），指纹变化 → 同步 im-server 地址簿 |
| 网关日志出现"探测连接（未发首帧即断开）" | 正常：后台「从网关获取」/ 端口扫描 / 健康检查的 TLS 握手后关闭，见 5.4 |

### 安全检查清单（上线前）

- [ ] 真实游戏服务端只监听 127.0.0.1，防火墙关闭其对外端口
- [ ] `token_secret` 为强随机值，且 im-server 与所有网关一致
- [ ] 各网关 `allow_targets` 只包含本机确实存在的服务端口
- [ ] 推荐逐网关独立密钥：后台地址簿每条目配置「专属密钥」并同步到该网关机 gateway.yaml（泄露/轮换半径=单网关）；`gateway_token_secret` 仅作未配条目的回退，保持强随机
- [ ] im-server 地址簿 fingerprint 与各网关首启日志一致
- [ ] `gateway_token_secret` 留空时确认没有游戏配置了 gw 规则（否则玩家启动会被拒）
- [ ] 启用后台时 `admin_listen` 保持 `127.0.0.1:30101`（远程用 SSH 隧道），`admin_password` 为强随机密码
- [ ] 启动密码已按每游戏独立密钥派生（im_game.game_secret 自动生成，无需配置）；`launch_secret` 仅兜底，保持强随机值更佳

## 10. 限制与边界

- 每游戏转发规则上限 16 条；结果串上限 2048 字符。
- 本机监听端口范围 1024~65535，保留端口 3478/2087 不可用。
- UDP 单包载荷上限 1200B（公网 MTU 安全值），网关不缓存不重组——透传语义与直连公网一致。
- UDP 会话空闲 90 秒回收（客户端自动保活，正常游戏流量不会触发）。
- 客户端重启后运行中游戏的转发不恢复（运行态本就不恢复，游戏连不上会自行报错）。

# 虎皮椒个人支付接入开发文档

## 一、背景与目标

### 1.1 为什么需要个人支付

当前项目已具备积分体系（`im_user.points` + `im_points_log`），但用户无法自行充值积分，只能通过注册赠送或管理员调整。引入个人支付后，用户可以：

- 扫码付款 → 自动充值积分余额
- 为后续 VIP 会员、游戏购买、功能订阅等**付费场景**打通资金入口

### 1.2 为什么选虎皮椒（xunhupay.com）

| 对比维度 | 虎皮椒 | PayJS | 自建旁路（PC Hook / 无障碍） |
|---|---|---|---|
| 开发成本 | ⭐ 1 个 HTTP 接口 + 1 个回调 | ⭐ 类似 | ⭐⭐⭐⭐⭐ 逆向/维护成本极高 |
| 封号风险 | 🟢 通道方养号 | 🟢 通道方养号 | 🔴 自建收款号极易封 |
| 手续费 | 1%~2% | 1%~2% | 0（但风险高） |
| 稳定性 | 🟡 聚合通道良莠不齐 | 🟡 同上 | 🔴 微信版本更新常断 |
| 合规性 | 🟡 通道方兜底 | 🟡 同上 | 🔴 个人收款商用违反微信协议 |

**结论**：快速验证阶段选聚合通道（虎皮椒），投入产出比最优。后期若规模上来再评估自建或切换官方商户号。

### 1.3 本文档范围

- ✅ 后端：支付订单创建、签名/验签、回调处理、积分入账
- ✅ 前端：收银台页面（微信/支付宝二维码展示 + 轮询检测）
- ✅ 配置：`config.yaml` 新增支付通道配置节
- ✅ 安全：签名校验、金额校验、幂等处理、防回调伪造

**不在本期范围**：
- 支付宝当面付（虎皮椒接口结构相同，二期扩展即可）
- 退款流程（个人支付通道通常不支持退款 API）
- 商户分账（已有商家分成体系，后续打通）

## 二、虎皮椒 API 对接

### 2.1 前置准备

去 [xunhupay.com](https://www.xunhupay.com) 注册商户账号，获取：

| 参数 | 说明 | 存放位置 |
|---|---|---|
| `appid` | 商户 ID | `config.yaml` |
| `appsecret` | 商户密钥 | `config.yaml`（不下发客户端） |
| 签名方式 | MD5 签名 | 代码硬编码 |

### 2.2 下单接口

**请求**：`POST https://api.xunhupay.com/payment/create`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `appid` | string | ✅ | 商户 ID |
| `out_trade_no` | string | ✅ | 商户订单号（全局唯一，本系统生成） |
| `amount` | string | ✅ | 金额（元，保留 2 位小数，如 "9.90"） |
| `title` | string | ✅ | 商品标题（最长 32 字符） |
| `notify_url` | string | ✅ | 回调地址（必须公网可达，内网调试可配 ngrok 隧道） |
| `return_url` | string | ❌ | H5 支付完成跳转地址（PC 扫码支付场景可留空） |
| `type` | string | ✅ | 支付类型：`WXPAY`=微信扫码 / `ALIPAY`=支付宝扫码 |
| `sign` | string | ✅ | 签名（见 2.4） |

**响应**（JSON）：

```json
{
  "code": 1,           // 1=成功，其他=失败
  "msg": "success",
  "data": {
    "orderid": "1234567890",          // 虎皮椒订单号
    "out_trade_no": "PAY20261119001", // 回传商户订单号
    "qr_code": "https://wx.tenpay.com/...", // 扫码支付链接
    "qrcode_url": "https://..."       // 通道生成的二维码图片 URL（部分通道返回）
  }
}
```

**失败响应**：

```json
{
  "code": 0,
  "msg": "错误描述"
}
```

### 2.3 回调接口（notify_url）

虎皮椒在支付成功后向 `notify_url` 发送 **GET 或 POST** 请求，参数如下：

| 参数 | 说明 |
|---|---|
| `appid` | 商户 ID |
| `out_trade_no` | 商户订单号 |
| `orderid` | 虎皮椒订单号 |
| `amount` | 支付金额（元） |
| `status` | 支付状态：`success` / `failed` |
| `pay_type` | 支付方式：`WXPAY` / `ALIPAY` |
| `pay_time` | 支付时间（YYYY-MM-DD HH:mm:ss） |
| `sign` | 签名 |

**回调处理规则**：
1. 验证签名 → 非法直接丢弃，返回非 200
2. 检查 `status == "success"` → 只处理成功回调
3. 用 `out_trade_no` 查本地订单 → 不存在返回非 200
4. 校验 `amount` 是否与订单金额一致 → 不一致记录告警日志，**不**入账
5. **幂等更新**：`UPDATE SET status='success' WHERE id=? AND status='pending'` → RowsAffected=0 表示已处理过，直接回 `"success"`
6. 积分入账（事务内）+ 写 `points_log`
7. 返回纯文本 `"success"` —— 虎皮椒收到非 success 会重试 3 次，每次间隔 1~5 分钟

### 2.4 签名算法（MD5）

**下单签名**：

```
待签名字符串 = appid=xxx&amount=xxx&notify_url=xxx&out_trade_no=xxx&title=xxx&type=xxx&appsecret=xxx
sign = MD5(待签名字符串).toUpperCase()
```

注意：
- 参数按 **字母顺序** 排列（`amount` → `appid` → `notify_url` → `out_trade_no` → `title` → `type` → `appsecret`）
- `appsecret` 拼在最后
- 中间用 `&` 连接
- MD5 结果取大写（32 位）

**回调签名校验**：

```
待签名字符串 = appid=xxx&amount=xxx&orderid=xxx&out_trade_no=xxx&pay_time=xxx&pay_type=xxx&status=xxx&appsecret=xxx
sign 比对 = MD5(上面字符串).toUpperCase() == 回调传来的 sign
```

## 三、数据库设计

### 3.1 支付订单表 `im_payment_order`

```sql
CREATE TABLE im_payment_order (
  id             BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  order_no       VARCHAR(32)  NOT NULL UNIQUE COMMENT '本系统订单号（PAY + 时间戳 + 随机）',
  channel_no     VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '通道订单号（虎皮椒 orderid）',
  username       VARCHAR(32)  NOT NULL COMMENT '下单用户',
  pay_channel    VARCHAR(16)  NOT NULL COMMENT '支付通道：xunhupay',
  pay_type       VARCHAR(16)  NOT NULL COMMENT '支付方式：WXPAY / ALIPAY',
  amount         DECIMAL(10,2) NOT NULL COMMENT '订单金额（元）',
  points         DOUBLE       NOT NULL COMMENT '充值积分（amount × 汇率）',
  status         TINYINT      NOT NULL DEFAULT 0 COMMENT '0=pending 1=success 2=failed 3=timeout',
  qr_code_url    VARCHAR(512) NOT NULL DEFAULT '' COMMENT '扫码链接/二维码图片',
  title          VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '商品标题',
  ip             VARCHAR(45)  NOT NULL DEFAULT '' COMMENT '下单 IP（风控）',
  paid_at        DATETIME     NULL DEFAULT NULL COMMENT '支付成功时间',
  create_time    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_username (username),
  INDEX idx_status (status),
  INDEX idx_create_time (create_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付订单表';
```

**状态常量**：

| 值 | 含义 |
|---|---|
| 0 | `pending` — 已创建，等待用户扫码 |
| 1 | `success` — 支付成功，积分已入账 |
| 2 | `failed` — 支付失败（用户取消 / 通道返回失败） |
| 3 | `timeout` — 超时未支付（定时任务标记） |

### 3.2 汇率说明

积分充值汇率在 `config.yaml` 配置：

```yaml
payment:
  points_per_yuan: 100   # 1 元 = 100 积分（可按需调整）
```

例：用户付 9.90 元 → 到账 990 积分。

### 3.3 积分入账幂等

支付成功回调触发时：

```sql
-- 原子更新（status=0 才命中，天然防重复回调）
UPDATE im_payment_order
SET status = 1, paid_at = NOW(), update_time = NOW()
WHERE order_no = ? AND status = 0;
-- RowsAffected = 0 → 已处理过，直接回 success 跳过后续

-- 积分入账（已在 aipoints.go 提供 userPointsAdd + recordPointsLog）
UPDATE im_user SET points = ROUND(points + ?, 3) WHERE username = ?;
-- 写流水
INSERT INTO im_points_log (username, change, balance_after, reason, operator, detail)
VALUES (?, ?, ?, 'payment_recharge', 'system', CONCAT('订单 ', ?));
```

## 四、服务端接口设计

### 4.1 路由总览

```
POST   /api/payment/create         创建支付订单（需登录）
GET    /api/payment/order/{no}     查询订单状态（前端轮询）
POST   /api/payment/notify          虎皮椒回调（公开，签名校验）
GET    /api/payment/channels        获取当前可用支付通道（公开）
```

### 4.2 创建支付订单

**请求**：`POST /api/payment/create`
**鉴权**：登录态（走既有 WS/TCP 登录会话 token）

```json
{
  "pay_type": "WXPAY",    // WXPAY 或 ALIPAY
  "amount": 9.90          // 金额（元），精度 0.01
}
```

**响应**：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "order_no": "PAY202611191430258421",
    "amount": 9.90,
    "points": 990,
    "qr_code_url": "https://wx.tenpay.com/...",
    "expire_seconds": 1800,
    "poll_interval": 3
  }
}
```

**校验规则**：

1. `pay_type` 必须是已配置通道支持的类型
2. `amount` 范围：`[最小充值额, 500.00]`（最小充值额在 config 配）
3. 用户必须已登录
4. 同一用户 60 秒内同金额去重（防连击）

### 4.3 查询订单状态

**请求**：`GET /api/payment/order/{order_no}`
**鉴权**：该订单所属用户自己（比对订单 username 和当前登录用户）

**响应**：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "order_no": "PAY202611191430258421",
    "status": 0,           // 0=pending 1=success 2=failed 3=timeout
    "status_text": "等待支付",
    "amount": 9.90,
    "points": 990,
    "paid_at": null
  }
}
```

### 4.4 虎皮椒回调

**请求**：`POST /api/payment/notify`（或 GET，按通道回调方式）
**鉴权**：签名校验（`sign` 字段）

**处理流程**：

```
收到回调
  │
  ├─ 验签失败 → 记录告警日志 → 返回非 success
  │
  ├─ status != "success" → 返回 success（失败状态不处理）
  │
  ├─ 查本地订单（out_trade_no → im_payment_order.order_no）
  │     ├─ 不存在 → 记录告警 → 返回非 success（让通道重试）
  │
  ├─ 校验金额（回调 amount == 订单 amount）
  │     ├─ 不等 → 记录告警 + 风控日志 → 返回 success（通道侧已扣款但金额对不上，需人工介入）
  │
  ├─ 事务：
  │     ├─ UPDATE ... SET status=1 WHERE order_no=? AND status=0
  │     │     ├─ RowsAffected=0 → 已处理过 → 回 success
  │     │
  │     ├─ 加积分（userPointsAdd）
  │     ├─ 写 points_log（reason=payment_recharge）
  │
  └─ 返回 "success"
```

### 4.5 获取可用通道

**请求**：`GET /api/payment/channels`
**鉴权**：无（公开）

**响应**：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "enabled": true,
    "channels": [
      {
        "name": "xunhupay",
        "display_name": "虎皮椒聚合支付",
        "pay_types": ["WXPAY", "ALIPAY"],
        "min_amount": 1.00,
        "fee_rate": 0.02
      }
    ]
  }
}
```

## 五、前端交互设计

### 5.1 收银台页面（新增 /subscribe.html 改造）

**入口**：用户点击头像 → 充值积分 → 弹出收银台面板

**UI 结构**（参考微信扫码支付）：

```
┌─────────────────────────────────┐
│  充值积分                        │
├─────────────────────────────────┤
│                                 │
│  ┌─────────────────────────┐    │
│  │                         │    │
│  │     微信 / 支付宝         │    │
│  │      [扫码图标]          │    │
│  │                         │    │
│  └─────────────────────────┘    │
│                                 │
│  请使用微信扫描二维码完成支付      │
│                                 │
│  金额：¥ 9.90    到账：990 积分  │
│                                 │
│  [刷新二维码]  [我已付款]         │
│                                 │
│  支付状态：● 等待支付（2s 轮询）  │
│                                 │
│  ── 档位选择 ──                  │
│  ¥1 → 100  ¥9.9 → 990  ¥29.9 → │
│                                 │
└─────────────────────────────────┘
```

### 5.2 轮询策略

```
每 3 秒 调用 GET /api/payment/order/{no}
  │
  ├─ status=0（pending）→ 继续轮询
  ├─ status=1（success）→ 停止轮询，显示"支付成功"动画，2 秒后刷新用户积分余额
  ├─ status=2/3（failed/timeout）→ 停止轮询，提示失败，用户可重新创建订单
  │
  └─ 轮询上限：最多 60 次（约 3 分钟）→ 超时停止，提示"支付结果确认中"
       用户可点击"我已付款"手动触发一次查询
```

### 5.3 轮询 vs 实时推送

一期用**前端轮询**实现，理由：

- 实现简单，无需 WebSocket 改造
- 虎皮椒回调保证最终一致性，轮询只是让前端尽快感知
- 3 秒间隔对用户体验可接受（参考微信支付等待状态）

二期如需要可升级为 **WebSocket 推送**：服务端收到回调后，通过现有 WS 连接给对应用户推送 `payment_notify` 信令，前端停止轮询。

## 八、安全要点

### 8.1 签名校验（必做）

- **下单请求**：服务端 → 虎皮椒，签名后发送（防篡改）
- **回调验签**：虎皮椒 → 服务端，必须校验 `sign`，未通过直接拒绝

### 8.2 金额校验（必做）

回调到达时必须比对 **回调 amount == 本地订单 amount**，不一致则 **不** 入账，记录告警。

### 8.3 幂等处理（必做）

- 回调可能被通道重试 3 次，必须保证同一份订单积分只加一次
- 实现方式：`UPDATE ... SET status=1 WHERE order_no=? AND status=0`，RowsAffected=0 即表示已处理

### 8.4 防订单冒用

- 查询订单状态接口必须校验：`username == 当前登录用户`
- 即便知道 `order_no`，别的用户也查不到他人的订单

### 8.5 回调 IP 白名单（可选加固）

虎皮椒回调 IP 可在其文档查询，加到 Nginx / 防火墙白名单（有条件可加，非必须——签名校验已是核心防线）。

### 8.6 密钥安全

- `appsecret` 仅存 `config.yaml`，**绝不下发客户端**
- 前端轮询只能查订单状态（pending/success），拿不到任何通道凭据
- 生产环境建议用环境变量注入密钥，`config.yaml` 留占位

## 九、定时任务

### 9.1 订单超时清理

服务端启动时挂起一个后台协程，每 5 分钟扫一次：

```
UPDATE im_payment_order
SET status = 3, update_time = NOW()
WHERE status = 0 AND create_time < NOW() - INTERVAL {order_timeout} SECOND;
```

- 标记超时后，前端轮询会看到 `status=3` 并停止
- 超时订单 **不自动退款**（用户未付款，无款可退）
- 用户需要充值时创建新订单即可

### 9.2 补偿扫描（可选，二期）

支付成功但回调丢失（网络抖动、服务宕机），定时任务主动向虎皮椒 **查询订单状态** 做补偿。虎皮椒提供查单接口：

```
POST https://api.xunhupay.com/payment/query
参数：appid、out_trade_no、sign
```

- 每 10 分钟扫 `status=0` 且创建超过 5 分钟的订单
- 主动查单，若通道侧已支付则补做积分入账

**一期不做此功能**——回调本身有 3 次重试，概率很低；真丢单可手动补偿或用户重新支付（未支付不会扣款，已扣款用户联系客服）。

## 十、错误码设计

| code | 含义 | 场景 |
|---|---|---|
| 0 | 成功 | — |
| 4001 | 支付功能未启用 | `payment.enabled=false` |
| 4002 | 参数非法 | `amount` 不在范围 / `pay_type` 不支持 |
| 4003 | 通道下单失败 | 虎皮椒返回 `code!=1`，`msg` 透传给前端 |
| 4004 | 订单不存在 | 查单时 `order_no` 无效 |
| 4005 | 订单非本人 | 查单时用户名不匹配 |
| 4006 | 订单已失效 | timeout/failed 状态的订单不能再查 |

## 十三、已知限制与风险

| 风险 | 等级 | 应对 |
|---|---|---|
| 聚合通道跑路 | 🔴 高 | 接入前考察通道口碑；不预充值；小量小额；可同时接 2 个通道做冗余 |
| 微信/支付宝风控 | 🟡 中 | 通道方养号，我们不直接碰收款号；控制单笔金额 |
| 回调丢失 | 🟡 中 | 通道有 3 次重试兜底；二期补偿查询接口 |
| 订单号撞单 | 🟢 低 | `order_no` = PAY + 毫秒时间戳 + 4 位随机，配合唯一索引，概率≈0 |
| 前端轮询被刷 | 🟢 低 | 已在用户维度（每订单）轮询，每单最多 60 次，后端可加单 IP 限流 |

## 十四、后续扩展方向（不在本期）

1. **支付宝当面付**：虎皮椒接口同结构，`pay_type=ALIPAY` 已预留
2. **补偿查单定时**：订单超时前主动向通道查询状态
3. **Nginx 白名单**：限制回调来源 IP
4. **WebSocket 推送**：回调到达后即时 WS 推送，取消前端轮询
5. **退款**：个人通道通常不支持，需接官方商户号或通道提供退款接口
6. **对账**：每日拉通道账单与本地订单比对（防止通道侧扣款但回调丢失）
7. **多通道冗余**：同时配置 2~3 个聚合通道，主通道挂了自动切换备用

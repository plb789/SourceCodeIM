## 1. 需求背景

玩家持有 IM 积分（`users.points`，AI 积分钱包），希望把积分**兑换成游戏内货币/资源**，为游戏账号充值：

- 玩家在 **PC 客户端**选择游戏 → 选择充值数量 → 确认，积分被扣除，游戏库内到账；
- 实际写库动作由**网关**执行（网关直连游戏数据库，im-server 与玩家均不直连游戏库）；
- 各游戏的充值 SQL 语句在**网关 Web 后台**按游戏配置，可在线编辑、测试、热生效；
- 复用现有积分钱包与流水审计（reason=game_recharge / game_recharge_refund），不另立账本。

### 1.1 已拍板决策（2026-11-02）

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 充值账号口径 | **IM 账号即游戏账号**（与 dbwrite 同口径），玩家无需填写账号，模板用 `{user}` |
| 2 | gateway-legacy | **两边同步实现**（legacy 保持其单监听代码风格） |
| 3 | 失败处理 | **自动退分**：订单超时/网关明确失败 → 标记 failed 并全额退积分，玩家可见 |
| 4 | 汇率/限额归属 | **im-server 管理后台**按游戏配置（业务数据不下放网关）；网关后台只配 DSN+SQL |
| 5 | 充值交互（2026-11-03） | **Steam"添加资金"同款档位式**：服务端按游戏配置积分档位，客户端纯点选确认，不做自由输入（防误输、限额天然可控、审计清晰） |

## 2. 总体链路

复用 dbwrite 的"队列 → 网关拉取 → 参数化执行 → 回执 ack"模式（网关开发文档 §2/§3），不引入新通信形态：

```
┌────────────┐  ①提交兑换   ┌──────────────────┐
│ PC 客户端   │─────────────▶│ im-server         │
│ game-store │  ③轮询状态    │ · 校验开关/限额/余额│
└────────────┘◀─────────────│ · 事务:扣积分+建订单│
                            └───────┬──────────┘
                                    │ ②拉取 pending 订单
                                    │ GET /internal/gateway/recharge
                                    │ (HMAC 签名 + AES-GCM 响应)
                            ┌───────▼──────────┐
                            │ im-gateway        │
                            │ · 按 recharge_gw  │
                            │   过滤归属        │
                            │ · 按游戏配置的     │
                            │   SQL 模板执行    │
                            └───────┬──────────┘
                                    │ ④成功 ack（body 纳签）
                                    ▼
                              游戏数据库（MySQL/MSSQL/PostgreSQL/SQLite）
```

要点：

- **扣分先行、写库异步**：积分扣减与订单创建在同一事务内原子完成；游戏库写入由网关周期拉取执行，玩家侧轮询订单状态感知结果。
- **失败可退**：订单下发后超时未 ack（30 分钟）或网关明确回执失败 → 定时任务标记 failed 并自动退分，玩家在兑换记录中可见。
- **幂等防重复加钱**：网关侧本地落盘已处理订单号 + 模板支持 `{order}` 供游戏库端存储过程二次去重（见 §5）。

## 3. 各角色设计

### 3.1 im-server（订单 + 用户 API + 内部 API + 退分）

#### 3.1.1 数据模型（`model` 包）

**新表 `im_recharge_order`（模型 `RechargeOrder`）：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uint64 主键 | 订单号（即模板占位符 `{order}` 取值） |
| username | varchar(64) 索引 | 兑换用户（=游戏账号 `{user}`） |
| game_id | uint 索引 | 游戏 ID（=模板 `{game}`，用于网关侧路由到对应 DSN/SQL） |
| points | double | 扣除积分数（>0，3 位小数口径同 AI 积分） |
| amount | double | 到账数值（=points × recharge_rate，下发前由 im-server 算好） |
| status | tinyint | 0=pending 1=success 2=failed(已退分) |
| gw | varchar(64) | 归属网关名（下单时快照 recharge_gw，防游戏后续改归属歧义） |
| fail_reason | varchar(255) | 失败原因（网关回执/超时退分说明） |
| created_at / done_at | datetime | 下单/终态时间 |

AutoMigrate 自动建表；**扣积分与建订单在同一事务**（积分扣减复用现有积分服务归口，流水 reason=`game_recharge`）。

**`Game` 表新增字段（AutoMigrate 加列，存量默认关闭不影响现状）：**

| 字段 | 类型 | 说明 |
|------|------|------|
| recharge_enabled | tinyint default 0 | 积分充值开关 |
| recharge_gw | varchar(64) default '' | 归属网关名（同 dbwrite_gw 语义；空=无网关承接，开关无效） |
| recharge_rate | double default 1 | 汇率：1 积分 = N 游戏币 |
| recharge_tiers | varchar(255) default '' | **积分档位 JSON 数组**（Steam 同款，如 `[100,500,1000]`）；下单 points 必须与某档完全一致；空=未配置档位，开关视为无效 |
| recharge_daily_max | double default 0 | 单用户单日累计积分限额（0=不限） |

单笔上下限不再单独配字段：min=档位最小值、max=档位最大值，由 `recharge_tiers` 天然约束。

#### 3.1.2 用户 API（登录态）

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/game/recharge` | POST | 提交兑换：`{game_id, points}`。校验链：游戏存在且 `recharge_enabled` 且 `recharge_gw` 非空 → **points 必须与 `recharge_tiers` 中某档完全一致**（档位式，拒绝任意数值，3 位小数口径）→ 当日累计不超 daily_max → 余额充足 → 事务扣分+建单。返回订单号与到账数值 |
| `/api/game/recharge/orders` | GET | 本人订单列表（分页，倒序），供兑换记录页与提交后状态轮询 |
| `/api/game/recharge/config` | GET | 某游戏的充值配置回显（汇率/档位列表/日限额/开关），详情页充值弹窗渲染档位按钮用 |

每日累计口径：`SUM(points) WHERE username=? AND game_id=? AND status IN(0,1) AND created_at>=今日`（pending 也占用额度，防并发绕过）。

#### 3.1.3 内部 API（网关拉取/回执，照抄 gatewaydbwrite.go 鉴权）

- `GET /internal/gateway/recharge?gw={网关名}`：gwproto HMAC 签名（X-GW-Auth，body 纳签，±300s 防重放）；响应体 AES-256-GCM 强制密文（X-GW-Enc）。返回该网关名下 status=pending 订单（按 `game.recharge_gw==gw` 动态过滤，同 gwGamesForGateway 思路），条目含 `{order_id, username, game_id, amount}`——**绝不下发 points 与用户敏感字段**。
- `POST /internal/gateway/recharge/ack`：成功订单号列表回执（body 纳入 HMAC 签名，防篡改）；落 status=success、done_at。**只收 success 回执**，失败不 ack=天然重试（与 dbwrite 一致）；网关如需主动报失败，走 ack 接口附带 `failed` 列与原因，服务端直接标 failed 退分（不再等待超时）。

#### 3.1.4 超时退分定时任务

- 周期扫描：`status=pending AND created_at < now-30min` → 标记 failed（fail_reason=处理超时自动退分）→ 事务内退积分（reason=`game_recharge_refund`，全额按 points 原值退还）。
- 幂等：仅状态机 pending→failed 单向迁移（带条件更新），并发扫描不重复退分。
- 退分走现有积分服务归口，保证 `users.points` 与 `im_points_log` 一致。

#### 3.1.5 管理后台

游戏管理编辑处新增上述 5 个 recharge 字段配置（自绘 UI，跟随现有后台样式；档位以逗号分隔数字编辑，服务端存为 JSON 数组并校验）；管理后台增加"充值订单"查询页（按用户/游戏/状态筛选，只读审计）。

### 3.2 im-gateway / gateway-legacy（拉取器 + 充值执行器）

结构与 dbwrite 完全同构（独立 goroutine、异常自恢复、绝不阻塞游戏隧道转发、热重载原子替换）：

**配置节 `recharge`（gateway.yaml，Web 后台在线编辑+热生效+落盘）：**

```yaml
# ===== 积分兑换充值（可选；不启用则拉取器不启动） =====
recharge:
  enabled: false                 # 总开关
  im_addr: http://im服务器:2087   # im-server 拉取地址（同 dbwrite.im_addr 归一化规则）
  poll_sec: 15                   # 拉取周期秒（clamp 5~600）
  games:                         # 每游戏一组（一个网关可服务多个游戏库，区别于单库 dbwrite）
    - game: 1                    # 游戏 ID（im-server 侧 Game.ID，订单按 game_id 路由）
      type: mysql                # mysql / mssql / postgres / sqlite
      dsn: root:root@tcp(127.0.0.1:3306)/gamedb
      sql: "UPDATE members SET gold=gold+{amount} WHERE account={user}"
      # 复杂逻辑建议存储过程（按订单号幂等）：
      # sql: "CALL recharge_gold({user}, {amount}, {order})"
```

- `recharge` 节落盘沿用 yaml.Node 原位编辑（保留注释格式）；热重载：校验失败拒绝保存且不影响运行中配置（同 dbwriteReload 语义）。
- Web 后台新增"积分充值"卡片页：游戏条目增删改、每条独立"测试连接"、SQL 模板编辑与校验提示、运行状态展示（IE 兼容 XHR + ES5，同现有页面）。

**SQL 模板规范（在 dbwrite §4 基础上扩展）：**

- 语句白名单不变：仅 `INSERT / UPDATE / MERGE / CALL / EXEC / EXECUTE` 开头；禁多语句（分号）、禁 `--` 与 `/*` 注释、替换后禁残留花括号；**强制参数绑定**。
- 占位符扩展（dbwrite 仅 `{user}/{password}`，充值新增两个并停用密码占位符）：

| 占位符 | 含义 | 校验 |
|--------|------|------|
| `{user}` | IM 账号（=游戏账号） | 服务端已限字符集，绑定传参 |
| `{amount}` | 到账数值 | **网关二次校验必须为合法数字**（正则 `^\d+(\.\d+)?$`，超长拒绝），绑定传参 |
| `{order}` | 订单号 | 纯数字 uint64 校验，绑定传参 |

- `{password}` 在充值模板中**不允许出现**（充值链路无密码语义，出现即校验失败拒绝保存）。

**幂等防重复加钱（双保险）：**

1. **网关本地已处理订单号落盘**（如 `recharge_done.json`，滚动上限裁剪）：执行成功先落盘再 ack；重启后重放订单先查本地记录，已处理直接补 ack 不再执行 SQL——防"已写库但 ack 丢失/进程崩溃"场景重复加钱；
2. **游戏库端存储过程按 `{order}` 去重**（推荐姿势，文档给模板）：充值流水表 + 过程内 `IF EXISTS(order_id) RETURN`，即使双保险 1 失效（换机器/清目录）仍不重复加钱。

**执行流程：**

```
loop(每 poll_sec):
  fetch /internal/gateway/recharge?gw=名     # HMAC + 强制解密
  for 订单 in 响应:
    游戏条目 = games[订单.game_id]            # 未配置该游戏 → 不执行不 ack，记日志（等管理员配好）
    本地已处理? → 直接收集 ack 跳过执行
    参数化执行 SQL（绑定 user/amount/order）
    成功 → 本地落盘订单号 → 收集 ack
    失败 → 记日志不 ack（下轮重试）
  ack(成功订单号列表)                          # body 纳签
```

`gateway-legacy`：同文件级复制实现（其单监听结构不变），配置节、模板校验、幂等落盘、后台页保持同口径，避免两版行为漂移。

### 3.3 PC 客户端（im-client/web，自绘 UI）

入口放在游戏商店（game-store）**游戏详情页**价格区旁（仅 `recharge_enabled` 且有网关承接的游戏显示"积分充值"按钮）：

1. **充值弹窗（Steam"添加资金"同款档位式，自绘，无系统弹窗，跟随主题色，微信风格布局）**：
   - 游戏名 + 汇率说明（"1 积分 = N 游戏币"）+ 当前余额（`GET /api/game/points` 实时取）；
   - **档位点选**：按 `/api/game/recharge/config` 下发的 `recharge_tiers` 渲染档位卡片（如 100 / 500 / 1000 积分），每档显示对应到账游戏币数；无自由输入框；
   - 点选档位高亮 → 自绘确认（本次扣分、到账数值、余额）；
   - 余额不足/超日限额：自绘提示（同现有 showConfirm 风格，见 game-store.js L4239-L4244 模式）；
   - 确认按钮 → `POST /api/game/recharge`（服务端仍以档位一致性 + 日限额 + 余额为准，客户端预校验仅作提示）。
2. **提交后**：轮询 `GET /api/game/recharge/orders`（3s 间隔）；success → 到账提示；failed → 显示失败原因与"积分已退还"；30s 未终态 → 提示"处理中，可稍后在兑换记录查看"。
3. **兑换记录**：详情页/商店侧入口进入，列表展示（时间/游戏/积分/到账/状态），自绘滚动条（禁止系统默认滚动条）。
4. i18n：zh-CN / en-US 词条补齐；WEB 端先行，APP 端（Capacitor）界面同源 Web 复用。

## 4. 安全设计汇总

| 风险 | 对策 |
|------|------|
| SQL 注入 | 全部占位符强制参数绑定；`{amount}`/`{order}` 数字正则二次校验；禁多语句/注释；语句动词白名单；网关保存模板即校验，非法不进运行期 |
| 重复加钱 | 网关本地订单号落盘去重 + `{order}` 存储过程幂等（推荐）+ pending→终态单向状态机 |
| 重复扣分 | 扣分与建单同事务；限额校验含 pending 占额（防并发双下单绕过 daily_max） |
| 越权 | 用户 API 登录态 + 仅操作本人订单；内部 API gwproto HMAC（body 纳签、防重放、响应强制 AES-GCM）；网关身份=自报名+地址簿存在性 |
| 信息泄漏 | 拉取响应不下发 points；订单/凭证不落网关日志；DSN 仅本机后台回显（同 dbwrite 语义） |
| 业务滥用 | 档位白名单（points 必须命中 recharge_tiers，杜绝任意数值）+ daily_max 日累计限额；退分原值全额、留痕 `im_points_log`；管理后台订单审计页 |
| 可用性 | 充值链路独立 goroutine，写库异常绝不影响游戏隧道转发；im-server 侧网关离线只导致订单 pending，超时自动退分无损 |

## 5. 数据库支持矩阵

同 dbwrite（全部纯 Go 零 CGO，单二进制不变）：MySQL、MSSQL（sqlserver 驱动，老版本 TLS1.0 用 `;encrypt=disable`）、PostgreSQL（pgx）、SQLite（modernc，单连接）。存储过程幂等模板仅 MySQL/MSSQL/PG 可用（SQLite 不支持过程，依赖网关本地落盘去重）。

## 7. 验收清单

- [ ] 开关关闭/未配网关/未配档位的游戏不显示充值入口，直接调 API 被拒
- [ ] points 不在档位白名单内（如 377、负数、小数篡改）一律拒绝且不扣分
- [ ] 余额不足、超 daily_max 均拦截且不扣分
- [ ] 并发双下单不超扣、不绕过日限额
- [ ] 网关执行成功 → 订单 success，游戏库数值准确到账（四库各验一）
- [ ] 网关执行失败不 ack → 重试成功不重复加钱；kill 网关进程重启后重放订单不重复执行
- [ ] 网关长期离线 → 30 分钟后订单 failed、积分原额退还、流水可查
- [ ] 模板含 `{password}`/`{role}`/分号/注释/SELECT 开头 → 后台保存被拒
- [ ] 客户端全流程：提交→轮询→到账提示；失败→退分提示；记录列表正确
- [ ] 回归：游戏商店积分购买/退款、积分红包、AI 积分扣费不受影响
- [ ] gateway 与 gateway-legacy 行为一致；配置热更与落盘重启不丢

## 8. 接口文档摘要（2026-11-03）

### 8.1 用户端（游戏中心，username 查询参数标识身份）

**① 提交兑换** `POST /api/game/recharge?username={账号}` —— 资金接口，**X-Drive-Token 强校验**（401=未登录/过期）
- Body：`{"game_id": 1, "points": 500}`
- 校验链：上架+开关+归属网关 → **档位白名单**（points 须与 recharge_tiers 某档一致）→ 日限额 → 余额 → 事务扣分+建单
- 成功：`{"ok":true,"data":{"order_id":17,"points":500,"amount":5000,"balance":300}}`（amount=points×汇率，服务端快照）
- 失败：400 档位不符/超日限额/积分不足｜403 未开放｜401 鉴权失败

**② 兑换记录/状态轮询** `GET /api/game/recharge/orders?username={账号}&game_id={可选}&page=1&size=20` —— **X-Drive-Token 强校验**
- 成功：`{"ok":true,"data":{"total":2,"items":[{"id":17,"game_id":1,"game_name":"…","points":500,"amount":5000,"status":1,"fail_reason":"","create_time":"…","done_time":"…"}]}}`
- status：`0` 处理中（积分已扣）｜`1` 成功（已到账游戏库）｜`2` 失败已退分

**③ 充值配置回显** `GET /api/game/recharge/config?username={账号}&game_id={id}` —— 公开（档位/汇率渲染用）
- 成功：`{"ok":true,"data":{"enabled":true,"rate":10,"tiers":[100,500,1000],"daily_max":600,"today_used":100,"balance":700}}`
- 未开放：`enabled:false`（客户端据此隐藏入口；直调下单仍被服务端拒绝）

### 8.2 网关内部（网关专用，与 dbwrite 同鉴权：X-GW-Auth HMAC 签名 ±300s 防重放，响应 AES-256-GCM 强制密文）

**④ 拉取待执行订单** `GET /internal/gateway/recharge?gw={网关名}`
- 解密后：`{"items":[{"id":17,"username":"玩家账号","game_id":1,"amount":5000}]}`（绝不下发 points/密码）
- 过滤：`game.recharge_gw==gw` 且订单 `gw` 快照匹配，仅 pending，单轮 ≤500

**⑤ 回执** `POST /internal/gateway/recharge/ack`（body 纳入 HMAC 签名）
- Body：`{"gw":"gw名","ok":[17],"failed":[{"id":18,"reason":"游戏账号不存在（影响 0 行）"}]}`
- 语义：ok → status=success；failed → 立即标 failed 并**全额退分**；缺失不回执=自动重试，30 分钟未终态由服务端超时退分
- 成功：`{"ok":true,"data":{"acked":1,"refunded":0}}`（重复回执幂等，acked/refunded 计 0）

### 8.3 管理端（Bearer 管理令牌）

**⑥ 充值订单审计** `GET /admin/api/game/recharge/orders?username={模糊}&game_id={可选}&status={0|1|2|空}&page=1&size=20`
- 成功：`{"ok":true,"data":{"total":n,"items":[…同②多 gw 字段…]}}`（只读审计）

### 8.4 业务配置（经既有游戏创建/编辑接口，字段随 Game 模型）

| 字段 | 说明 |
|---|---|
| `recharge_enabled` | 开关（bool） |
| `recharge_gw` | 承接网关名（=网关地址簿条目） |
| `recharge_rate` | 汇率：1 积分 = N 游戏币 |
| `recharge_tiers` | 档位 JSON 数组串 `[100,500,1000]`（单笔白名单） |
| `recharge_daily_max` | 单用户单游戏日累计积分限额（0=不限，pending 占额） |

### 8.5 网关侧配置（gateway.yaml `recharge` 节，Web 后台在线编辑+热更+落盘）

```yaml
recharge:
  enabled: true
  gateway_name: gw-hz          # 空=回退 dbwrite.gateway_name
  im_addr: http://im服务器:2087
  poll_sec: 15
  games:
    - game: "1"                # im-server 游戏 ID（订单路由键）
      type: mysql              # mysql/mssql/postgres/sqlite
      dsn: root:root@tcp(127.0.0.1:3306)/gamedb
      sql: "CALL recharge_gold({user}, {amount}, {order})"  # {user}/{amount}/{order}，禁 {password}/SELECT/多语句
```

### 8.6 状态机与时序

`pending`（扣分建单）→ 网关拉取（15s 默认）→ 参数化写游戏库 → ack → `success`；
失败不回执自动重试；30 分钟未终态或网关明确报失败 → `failed` + 全额退分（`im_points_log` reason=game_recharge_refund）。
幂等：网关本地订单号落盘（先落盘再 ack）+ 模板 `{order}` 存储过程去重（推荐）。

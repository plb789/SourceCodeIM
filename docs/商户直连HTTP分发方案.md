# 商户直连 HTTP 分发方案（商户自带文件服务器 · 可行性评估）

> **实现状态（已完成，见下方"一期实现修正"）**：dm=3 全链路已落地——服务端登记/manifest 分流、
> 商户后台 dm 选择与清单登记 UI、管理端 dm=3 表单、PC 客户端直连下载（https 强制+SHA256 校验+
> 错误文案分流）。测试：TestMerchantDirectHTTP 全链路回归。

> 需求：商户在商户后台登记**自己服务器**的文件地址（base_url），游戏本体与补丁文件不上传
> im-server，PC 客户端直接从商户服务器下载。服务端只持有"清单元数据"（文件名/大小/SHA256）。

---

## 〇、一期实现修正（相对原方案的一处收紧）

**直连版本一期仅支持 pack_type=0（散文件完整清单），pack 1/2/3 不支持**。原因：pack 3 补丁的
服务端合成（读 patch.zip 提取 patch.json）与 pack 1 的 ZIP 实算均需文件本体在服务端——直连下
文件不存在，若强行支持需服务端拉取商户外部文件（引入 SSRF 面+信任问题），违背本方案 §四
安全原则。**补丁更新的等价形态**：商户在本地对完整目录做变更后，在商户后台选择游戏目录
登记新版本完整清单（前端本地计算 SHA256，不走上传），玩家侧表现为正常版本更新。
原方案 §六"pack 0-3 全支持"以此修正为准。

## 一、结论

**可行，且改动面小**。三个决定性前提均已具备：

1. **PC 下载器已具备直连所需的全部能力**（download-manager.js）：`.part + Range` 断点续传、
   **SHA256/大小双校验（失败删文件重试 ≤2 次）**、并发调度、暂停恢复——且下载清单的每个文件
   条目本来就带独立 `url` 字段。直连模式 = manifest 下发时把 `url` 从服务端地址换成商户地址，
   客户端校验链路**零改动**。
2. **manifest 按下载方式分流已有先例**：`gameManifest` 对 BT·上传种子（download_method=2）
   已做"清单按方式合成"分流（game.go:1099-1126）。直连（download_method=3）照此模式扩展。
3. **商户自担分发的产品形态已有先例**：BT·上传种子（dm=2）就是"商户自己的分发方式"。
   直连 HTTP 是同一思路的 HTTP 版（BT 适合无服务器有带宽的场景，直连适合有服务器/网盘/OSS 的场景）。

## 二、Steam 参考事实澄清

- **Steam 不允许第三方自托管游戏内容**：Steamworks 开发者把 build 上传到 Valve 的
  SteamPipe 系统，由 Valve 自家 CDN 全球分发；开发者无法提供自己的 HTTP 服务器作为
  Steam 游戏内容源，也没有"直链模式"。
- **支持"开发者自带文件地址"的参考是 itch.io**：其 external file 模式允许开发者填外部
  下载链接（平台只存链接与元数据，文件本体在开发者处）。
- **国内常见做法同构**：官网直链下载 / 网盘链接分发（平台不承载文件本体）。
- 本项目视角：**BT·上传种子（dm=2）≈ 商户自担分发的内部先例**；直连 HTTP 是它的
  HTTP 对照形态，两者互补——BT 无需商户有服务器（有带宽即可），直连需要商户有
  可公网访问的 HTTP 服务（自建 nginx / 阿里云 OSS / 七牛 / 网盘直链均可）。
  商户把 base_url 指向自己的 OSS/CDN 时，天然获得加速与带宽成本转移——这是本功能
  的核心价值。

## 三、架构设计

### 3.1 数据与配置

- `game.download_method` 新增枚举 **3 = HTTP·商户直连**（0=服务端清单 / 1,2=BT / 3=直连）。
- `game` 表（或复用现有字段约定）新增 `direct_base_url varchar(512)`：商户文件服务器根地址，
  商户后台「下载方式」选"直连 HTTP"时必填。清洗规则：
  - 仅允许 `http(s)://`；**生产默认强制 https**（`game.direct_http_only=true` 可放开，适配
    内网部署）；禁 `..`、空白、控制字符、查询串以外的非法字符；长度 ≤512；
  - 尾部 `/` 归一；不支持带查询串/鉴权头的模板（一期固定根地址，防注入面）。

### 3.2 版本登记（服务端）

- 商户选直连方式后，版本登记仍走现有 `gameVersionCreateCore` 清单协议
  （rel_path / size / sha256 / 版本号 / pack_type 0-3 全复用，商户用现成 GamePatchTool
  生成清单），**唯一差异：跳过"合并落位"步骤**（文件本体不上传，`upload_id` 留空，
  服务端不落盘、只登记 `im_game_file` 行，`storage_path` 置空）。
- **配额口径**：直连版本**不计入商户存储配额**（文件不在 im-server 磁盘上，配额语义=
  服务端磁盘占用），`size_bytes` 照常登记用于展示/统计。
- **ClamAV 边界（重要）**：文件本体不在服务端，病毒扫描**天然失效**。直连版本的完整性
  由 SHA256 清单兜底（客户端逐文件校验，服务端持权），但"商户放了什么内容"服务端无法
  自动检测——维持上架人工审核（audit=1），审核员可凭 base_url 抽样核验；此边界写入
  审核提示与商户协议文案。

### 3.3 清单下发（gameManifest dm=3 分流）

```
正常下发 files（id/rel_path/size/sha256），但每个文件的 url =
    direct_base_url + "/" + url.QueryEscape(rel_path)
并附 "download_method": 3、"base_url"（客户端可展示来源）
```

- manifest_hash 逻辑不变（清单完整性由服务端签名体系持有，商户服务器只提供字节流，
  **无法投毒**：篡改任意文件都会在客户端 SHA256 校验失败并被拒装）。

### 3.4 客户端（PC）

- **下载器零改动**：现有 per-file url + Range 断点 + SHA256 校验 + 重试直接适配外部 URL
  （Electron net 下载无 CORS 限制）。
- 需要的客户端适配（小改）：
  1. 直连模式的错误文案差异化（"商户服务器连接失败/校验失败"，提示稍后重试而非怪服务器）；
  2. 直连下载建议强制 https 校验（证书失败即拒绝，防降级）；
  3. WEB 端：浏览器导航下载不受 CORS 影响，但直连模式大文件分文件下载体验与 PC 端不同
     ——**一期 WEB 端对 dm=3 游戏仅展示"请在 PC 客户端下载"引导**（与 BT 模式同策略，
     BT 现状即 PC 专属）。

### 3.5 补丁（pack_type=3）兼容

- 直连 + 补丁：商户在自己服务器放 patch.zip 与变更文件，登记 patch 清单（基底合成链路
  全复用），合成后 manifest 的每个文件 url 均指向商户服务器——客户端按清单直连下载差异
  文件。**补丁更新 = 商户在自己服务器替换文件 + 登记新版本**，im-server 全程不碰字节流。

## 四、安全设计

| 威胁面 | 对策 |
|---|---|
| 商户服务器文件被篡改/投毒 | 客户端逐文件 **SHA256 校验**（清单由服务端持权下发，商户无法改清单）+ 大小校验；失败拒装并重试 |
| 中间人篡改 | 生产默认**强制 https**（可配置放开适配内网） |
| URL 注入/穿越 | base_url 白名单清洗（禁 `..`/控制字符/查询模板）；rel_path 走既有 `gameRelPathClean` 后再 QueryEscape 拼接 |
| 服务端 SSRF | **服务端绝不代理外部 URL**——下载纯客户端直连，服务端只存 base_url 字符串，SSRF 面为零 |
| 恶意商户放病毒文件 | 服务端扫描不可达（文件不在本地）——人工审核 + 客户端哈希校验 + 责任前置到商户协议；审核页对 dm=3 游戏显示"外部文件源"标识提示审核员 |
| 防盗链/热链 | 一期固定 base_url 不做 token 模板；商户可自行在其服务器侧加 Referer/IP 防盗链（方案留二期 URL 模板扩展位） |

## 五、风险与对策（商户自行托管固有代价，需产品侧知情）

| 风险 | 说明 | 对策 |
|---|---|---|
| 商户服务器可用性不可控 | 商户服务器宕机=玩家下不了游戏 | 客户端错误文案明确指向"游戏来源服务器"；表单提示商户自备稳定服务器/CDN；二期可支持多 base_url 镜像轮询 |
| 无下载量统计 | 直连不经服务端，下载行为统计缺失 | 一期接受（上架/购买/库数据不受影响）；二期可做客户端匿名回执 |
| 病毒检测盲区 | ClamAV/存量扫描对直连版本失效 | 审核强提示 + 哈希白名单兜底 + 责任协议；未来可做"服务端按需拉取抽样扫描"（拉取会产生 SSRF 面，须独立评审） |
| 下载失败无服务端回退 | 服务端无文件本体 | 一期接受（BT 模式同现状）；二期可做"双源：商户直连 + 管理员代传兜底" |

## 六、改动点清单与工作量

### 服务端（im-server）
1. `model.Game`：`DirectBaseURL` 字段（AutoMigrate 自动加列）；
2. `gameadmin.go`/`merchantgame.go`：dm 白名单 +3；商户端放开 dm 选择（当前商户固定 0）；
   base_url 清洗 helper（复用 merchantImgURLClean 风格）；
3. `gameVersionCreateCore`：dm=3 时跳过合并落位与配额预检/复检（清单校验/查重/回滚语义保留）；
4. `gameManifest`：dm=3 分流——下发 files，url 改拼商户地址；
5. 商户后台接口：下载方式枚举 + base_url 字段下发/保存。

### 客户端（PC）
6. download-manager.js：错误文案分流 + https 强制校验（约 30 行）；
7. 商店页 dm=3 提示"来源：商户服务器"。

### 后台 UI
8. 商户后台「下载方式」radio 增加"直连 HTTP"项 + base_url 输入（管理端同步可见）。

**预估**：服务端 + 后台 UI 一期 ~1 个开发日；客户端适配 ~0.5 个开发日（含联调）。

## 七、建议分期与决策点（动手前需拍板）

| 决策点 | 建议 |
|---|---|
| D1 https 是否强制 | 生产强制（`game.direct_http_only` 默认 true），内网部署可放开 |
| D2 直连是否计配额 | **不计**（配额=服务端磁盘占用语义） |
| D3 直连版本审核 | 维持 audit=1 人工审核（加"外部文件源"审核提示），不做自动扫描 |
| D4 一期范围 | 整版直连 + 补丁直连（pack 0-3 全支持）；多镜像/统计回执/双源回退留二期 |
| D5 WEB 端 | dm=3 与 BT 同策略：仅 PC 客户端可下载，WEB 展示引导 |

## 八、后续增强规划（2026-11-08 记录，暂缓实施）

按"方便程度 × 复用度"排序的商户发布增强候选（确认后单独立项）：

1. **gametool 一键发布（优先推荐）**：扩展 gametool.exe 加 publish 子命令——本地多线程算 SHA256（带缓存只重算变更文件）+ 直连模式零上传直接登记清单 / 平台模式自动走分片上传；可加 watch 监控目录自动发版。约 1 天，服务端零改动。
2. **WebDAV 同步入库**：复用网盘 WebDAV 模块，分配 webdav://平台/merchant/<用户名>/ 目录，商户用 rclone/WinSCP 同步游戏目录，后台识别清单完整后一键入库转 dm=0。约 1-2 天。
3. **增量上架向导**：登记时对比上一版本清单只上传 diff 文件（推广现有 pack3 能力为通用网页向导）。约 1 天。
4. **OSS 预签名直传**：MinIO 预签名 URL，商户本地工具直传对象存储（绕过 im-server 带宽）。约 1-2 天，依赖 MinIO 部署。
5. **服务端拉取（直连→托管反向）**：平台从商户 base_url 拉文件转存托管。有 SSRF 面，须管理员触发+地址白名单，优先级最低。
6. **开放 API + 商户自助 Token**：脚本/CI 发布（配合 1，面向批量发行工作室）。

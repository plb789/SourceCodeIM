# IM 即时通信系统开发步骤（按优先级排序）

> 依据《开发文档.md》整理。优先级定义：
> P0 = 核心基础（缺它系统无法运行）｜P1 = 核心功能｜P2 = 增强与体验｜P3 = 拓展/可选。
> 开发遵循"先打通最小闭环，再逐层增强"的原则。
>
> 完成状态标记：✅ 已完成 ｜ 🔶 部分完成（剩余项见括号说明）｜ ⬜ 未开始

---

## 阶段一：项目初始化与基础架构（P0）✅

1. 搭建项目目录结构：服务端 `im-server/`、客户端 `im-client/web/`、`im-client/pc/`。
2. 准备技术环境：Go 1.21+、MySQL 8.0、Redis 6.0+。
3. 创建 MySQL 数据表（首次启动自动建表）：
   - `im_user`（id、username、password、avatar、create_time、update_time）
   - `im_message`（id、msg_type、from_user、to_user、content、create_time）
   - `im_file`（id、file_name、file_size、file_path、from_user、to_user、status、create_time）
4. 落地 Redis 缓存键设计：
   - `im:online:username`（在线状态，120s 过期）
   - `im:file:chunk:fileid`（分片进度）
   - `im:session:username`（最近会话）
   - `im:offline:msg:username`（离线消息队列，7 天过期）
5. 搭建 Go 服务端骨架：MySQL/Redis 连接池、日志模块、缓存预热、WebSocket 监听入口。

## 阶段二：WebSocket 连接与用户体系（P0）

1. 定义 JSON 通用消息协议字段：`msg_type`、`from_user`、`to_user`、`content`、`file_name`、`file_size`、`file_data`、`chunk_index`、`timestamp`。
2. 服务端 WebSocket 监听（端口 8888），Goroutine per connection。
3. 用户注册/登录：MySQL 校验（用户名查重、密码加密）。
4. 连接管理模块：写入 Redis 在线缓存、维护在线用户列表。
5. 上下线通知广播 + 在线用户列表实时同步（msg_type=5/6）。
6. 心跳检测机制：客户端 30s 心跳、服务端 90s 超时判定离线。
7. 断线重连：客户端自动重连，恢复在线状态。

## 阶段三：文字聊天核心功能（P0/P1）

1. 消息调度模块：解析消息、区分群聊/私聊、格式校验。
2. 群聊：`msg_type=1`，先写 MySQL 再遍历在线用户广播。
3. 私聊：`msg_type=2`，持久化后定向转发至目标用户。
4. 消息持久化：写入 `im_message`，支持历史记录分页检索。

## 阶段四：文件传输功能（P1）

1. 文件分片：客户端按 4KB 固定大小分片，生成分片序号/总分片数。
2. 文件头消息：文件名、大小、总分片数，服务端写入 `im_file` 并初始化 Redis 分片缓存。
3. 分片中转：逐片发送、实时中转、更新 Redis 分片进度。
4. 断点续传：基于 Redis 分片记录校验已完成分片。
5. 接收方拼接、校验文件大小与完整性，完成后更新传输状态。

## 阶段五：离线消息与消息增强（P1）✅（已全部完成，含已读/撤回/删除、关键词搜索）

1. 离线判定：目标用户无 Redis 在线缓存即视为离线。
2. 离线消息入队：写入 Redis 离线消息队列，按时间排序。
3. 上线批量推送：登录成功后批量推送离线消息，推送完清空缓存。
4. 消息唯一性：唯一消息 ID + 时间戳，客户端去重。
5. 消息时序保序、消息去重。
6. 消息已读/未读状态、消息撤回、消息删除。
7. 消息关键词全局搜索。

## 阶段六：用户资料与头像（P1）

## 阶段十六：消息撤回与多端同步（P1）✅

5. 验证：脚本客户端 9 项全通过（LOGIN_RESP 窗口下发=120、双方摘要联动、离线补发过滤、撤回通知过滤）；场景 D 配置生效验证 3 项全通过（`recall_window: 2` 时超窗撤回被拒、窗内撤回成功、证明配置真实读取而非默认值）；浏览器双账号实测通过（登录流程、撤回执行、p10e/p10f 新会话摘要"[消息已撤回]"两端同步、blka/blkb 中间撤回摘要重算同步、控制台无 JS 错误）。✅

## 阶段三十四：登录失败无提示修复——错误消息送达保障 + 无限重连治理（P1）✅

**问题**：密码错误等登录失败场景无任何提示（页面表现为点击登录后毫无反应），且后台每 3 秒无限重连。

1. 根因一（服务端消息竞态）：handleLogin 失败时 sendError 走 sendCh 发送队列**异步**写出，紧接 Close() **立即**关闭连接——writePump 常来不及把错误消息写出连接就已被关闭，错误提示丢失。✅
2. 修复一（server/client.go 新增 SendErrorAndClose）：绕过发送队列**同步写**错误消息到连接（writePump 此刻阻塞在 sendCh 上不会并发写，gorilla 连接写操作安全），确保错误提示送达后再断开；handleLogin 失败分支改用该方法，与 HandleWS 连接数上限处已有的同步写错误模式对齐。✅
3. 根因二（错误文案误导）：verifyUser 对"用户不存在"与"密码错误"返回同一错误 ErrInvalidLogin，handleLogin 一律尝试自动注册——密码错误场景注册必然失败，最终提示误导性的"用户名已存在"而非真实的"用户名或密码错误"。✅
4. 修复二（server/auth.go + server/server.go）：新增 ErrUserNotFound，verifyUser 用户不存在返回 ErrUserNotFound、密码错误返回 ErrInvalidLogin；handleLogin 仅在 ErrUserNotFound 时尝试自动注册，密码错误直接下发"用户名或密码错误"。"首次登录自动注册"功能保持不变。✅
5. 根因三（前端无限重连）：ws.onclose 无条件 3 秒重连，且重连密码取 window._lastPassword（原代码从未赋真实值，恒为空字符串）——登录失败断开后陷入"失败→3秒重连→失败"循环，每次都无提示。✅

7. 附带修复（chat.js v1.30→1.31）：doLogin 的 alert('请输入用户名') 为系统默认弹窗违反 UI 规范，改用页面内 Toast 轻提示，并补充空密码校验提示。✅

## 阶段三十六：图片消息滚动条停半截修复（发送/接收/历史三链路贴底）✅

1. 现象（用户实测反馈）：发送图片后滚动条不在最底，图片只显示一半，需手动下移滚动条才能看到全图。✅
2. 根因：图片为异步加载——气泡插入 DOM 时 img 高度为 0，appendImageMsg 在插入后立即 scrollTop=scrollHeight（此时滚的是"图片未撑高"的列表），图片加载完成后撑高（.chat-image 最高 200px），滚动位置停在原处，新增高度全部落在视口下方。✅
3. 修复（chat.js v1.40→1.42，服务端零改动）：新增 isNearBottom()（容差 80px）；appendImageMsg 与 createMediaMessageEl（历史图片分支）两处 img 均挂 load 监听，加载撑高后按需再次滚底。**关键点（v1.41→1.42 修正）**：贴底判定必须在**插入前采样**（stick 快照）——v1.41 在 load 回调内实时 isNearBottom() 判定，此时图片已把列表撑高（gap 瞬间≈图片高度，突破 80px 容差）被误判为"翻历史中"而放弃滚底，图片仍只显示一半（用户复测暴露）；v1.42 改为 appendImageMsg 函数首行快照 stick=isNearBottom()、createMediaMessageEl 由 renderHistoryRecord 传入 stickBottom=!beforeEl && isNearBottom()（向上补插历史不参与滚底），load 时按快照滚底——快照不受加载撑高影响，判定恒准确；翻历史时（不在底部）不强行拉底打断浏览。原实现均已注释保留。✅
4. 验证（浏览器端到端，v1.42）：页面内构造 400×800 竖图 File 走真实 change 发送链路——①贴底连发两张（第二张在第一张加载后发送，即用户失败场景）：gap=0 精确贴底、最后一张完全可见；②刷新后历史加载贴底再发一张：gap=0 完全可见；③从列表顶部（翻历史中）发送：不被 isNearBottom 误拉底，终态由发送跳底归口；node --check 语法通过、UTF-8 无 BOM。✅

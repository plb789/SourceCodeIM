# IM 即时通信系统开发步骤（按优先级排序）

> 依据《开发文档.md》整理。优先级定义：
> P0 = 核心基础（缺它系统无法运行）｜P1 = 核心功能｜P2 = 增强与体验｜P3 = 拓展/可选。
> 开发遵循"先打通最小闭环，再逐层增强"的原则。
>
> 完成状态标记：✅ 已完成 ｜ 🔶 部分完成（剩余项见括号说明）｜ ⬜ 未开始

---

## 阶段一：项目初始化与基础架构（P0）✅

1. 搭建项目目录结构：服务端 `im-server/`、客户端 `im-client/web/`、`im-client/pc/`。
2. 准备技术环境：Go 1.21+、MySQL 8.0、Redis 6.0+。
3. 创建 MySQL 数据表（首次启动自动建表）：
   - `im_user`（id、username、password、avatar、create_time、update_time）
   - `im_message`（id、msg_type、from_user、to_user、content、create_time）
   - `im_file`（id、file_name、file_size、file_path、from_user、to_user、status、create_time）
4. 落地 Redis 缓存键设计：
   - `im:online:username`（在线状态，120s 过期）
   - `im:file:chunk:fileid`（分片进度）
   - `im:session:username`（最近会话）
   - `im:offline:msg:username`（离线消息队列，7 天过期）
5. 搭建 Go 服务端骨架：MySQL/Redis 连接池、日志模块、缓存预热、WebSocket 监听入口。

## 阶段二：WebSocket 连接与用户体系（P0）

1. 定义 JSON 通用消息协议字段：`msg_type`、`from_user`、`to_user`、`content`、`file_name`、`file_size`、`file_data`、`chunk_index`、`timestamp`。
2. 服务端 WebSocket 监听（端口 8888），Goroutine per connection。
3. 用户注册/登录：MySQL 校验（用户名查重、密码加密）。
4. 连接管理模块：写入 Redis 在线缓存、维护在线用户列表。
5. 上下线通知广播 + 在线用户列表实时同步（msg_type=5/6）。
6. 心跳检测机制：客户端 30s 心跳、服务端 90s 超时判定离线。
7. 断线重连：客户端自动重连，恢复在线状态。

## 阶段三：文字聊天核心功能（P0/P1）

1. 消息调度模块：解析消息、区分群聊/私聊、格式校验。
2. 群聊：`msg_type=1`，先写 MySQL 再遍历在线用户广播。
3. 私聊：`msg_type=2`，持久化后定向转发至目标用户。
4. 消息持久化：写入 `im_message`，支持历史记录分页检索。

## 阶段四：文件传输功能（P1）

1. 文件分片：客户端按 4KB 固定大小分片，生成分片序号/总分片数。
2. 文件头消息：文件名、大小、总分片数，服务端写入 `im_file` 并初始化 Redis 分片缓存。
3. 分片中转：逐片发送、实时中转、更新 Redis 分片进度。
4. 断点续传：基于 Redis 分片记录校验已完成分片。
5. 接收方拼接、校验文件大小与完整性，完成后更新传输状态。

## 阶段五：离线消息与消息增强（P1）✅（已全部完成，含已读/撤回/删除、关键词搜索）

1. 离线判定：目标用户无 Redis 在线缓存即视为离线。
2. 离线消息入队：写入 Redis 离线消息队列，按时间排序。
3. 上线批量推送：登录成功后批量推送离线消息，推送完清空缓存。
4. 消息唯一性：唯一消息 ID + 时间戳，客户端去重。
5. 消息时序保序、消息去重。
6. 消息已读/未读状态、消息撤回、消息删除。
7. 消息关键词全局搜索。

## 阶段六：用户资料与头像（P1）

1. 头像上传/修改：前端选择、预览、裁剪提交。
2. 服务端校验：仅 jpg/png/gif、最大 5MB。
3. 资源存储：统一存服务端静态目录，唯一文件名。
4. 更新 `im_user.avatar`，同步更新缓存。
5. 广播用户信息更新通知，全端头像刷新。
6. 个人资料编辑、登录态持久化、多设备同时在线管理。

## 阶段七：会话管理（P2）✅

1. 最近会话列表自动维护，按最新消息倒序。✅（新增 `im_conversation` 表服务端统一归口，私聊/群聊消息实时刷新双方会话）
2. 会话置顶/取消置顶，配置持久化。✅（右键菜单操作，置顶优先+时间倒序排序，浏览器实测通过）
3. 会话清空、删除（保留云端记录）。✅（清空复用 `im_msg_delete` 表仅影响自己视图并清空未读与摘要；删除移除会话行并清零未读，收到新消息自动重建；浏览器实测通过）
4. 「对方正在输入」状态实时提示。✅
5. 未读消息计数与角标，点击清零。✅（服务端按未读私聊消息统计，打开会话自动清零，浏览器实测通过）
6. 多端会话、未读、置顶状态同步。✅（状态全部服务端归口：操作后即时推送最新列表，重连/重登自动恢复，实测服务重启后会话/置顶/未读全部还原）

## 阶段八：微信同款 UI 与三套主题（P2）

1. 微信标准三栏布局：左侧会话列表栏 + 中间聊天主窗口。
2. 聊天气泡样式：己方绿色、对方白色，大圆角。
3. 底部输入栏：表情/图片/文件/截图/清空按钮，回车发送、Ctrl+回车换行。
4. 三套主题（浅色/深色/跟随系统）：CSS 变量 + prefers-color-scheme + JS 状态管理。
5. 主题偏好 localStorage 持久化，双端同步生效。
6. 消息滚动、状态同步、会话排序等交互细节对齐微信。

## 阶段九：安全风控与日志审计（P2）✅

1. 敏感词内容过滤：违规消息拦截、不转发、不落地。
2. 文件安全校验：格式、大小、文件头校验，拦截可执行/恶意文件。
3. 异常连接防护：限制单 IP 高频连接、重复用户名恶意登录。
4. 全链路日志审计：消息、文件、登录、资料修改、违规操作留存。

## 阶段十：PC 端 Electron 适配（P2）

1. 基于 Web 源码无损打包：`main.js` 主进程、`preload.js`、`package.json`。
2. 桌面通知推送、任务栏角标、后台驻留、最小化托盘。
3. 快捷键操作、开机自启保留主题偏好。
4. 双端消息、状态、会话互通验证。

## 阶段十一：AI 智能问答（P3）

4. 私聊 AI 对话、群聊 @AI 唤醒应答。

## 阶段十三：好友与社交关系（P1）✅

1. 好友申请（msg_type=20）：写入 `im_friend_request` 表，在线实时推送、离线登录补发。
2. 申请响应（msg_type=21）：同意后双向建立好友关系（`im_friend` 表），拒绝更新状态。
3. 好友列表同步（msg_type=22）：含备注、分组、在线状态、头像，变更实时刷新。
4. 删除好友（msg_type=23）：双向解除好友关系，双方列表实时刷新。
5. 黑名单（msg_type=24）：拉黑时同步删除好友关系，任一方向拉黑即拦截私聊；黑名单列表同步（msg_type=26）+ 侧栏黑名单分组管理，支持查看与移出黑名单。
6. 好友备注/分组更新（msg_type=25）。
7. **申请重复推送竞态修复**：三重保险——服务端记录 `loginTime` 仅补发登录前的历史申请、申请消息携带唯一 `msg_id`（数据库记录 ID）、前端按 `msg_id` 去重；已通过测试客户端验证无重复推送。
8. **UI 规范落地**：全部弹窗改为自定义弹窗（确认/输入弹窗 + Toast 轻提示），禁止系统默认 alert/confirm/prompt；删除好友、拉黑、好友申请均带二次确认；弹窗样式跟随三套主题。

## 阶段十四：消息搜索与消息置顶（P2）✅

1. 消息置顶/取消置顶（msg_type=29）：新增 `im_msg_pin` 表（`conv_key` 会话唯一键：群聊固定 group、私聊按字典序拼接，每会话仅一条置顶），服务端校验消息归属与撤回状态，新置顶自动替换旧置顶。✅
2. 置顶状态多端同步（msg_type=30）：服务端归口推送（群聊广播、私聊双方视角各自推送 target），登录时批量补发全部会话置顶列表；置顶消息被撤回时自动联动取消并同步。✅（脚本客户端 + 双账号浏览器实测通过）
3. 置顶消息条 UI：聊天窗口顶部置顶条（发送者 + 内容 + 取消按钮），消息右键菜单动态显示「置顶/取消置顶」，样式跟随主题色。✅
4. 会话内消息搜索（msg_type=31）：在当前聊天窗口对应会话范围内检索关键词（私聊双向、群聊全体），排除已撤回与自己删除的消息，LIKE 通配符转义，最多返回 50 条。✅
5. 搜索结果定位高亮（msg_type=32）：搜索浮层展示结果（发送者/时间/内容），点击结果若消息已渲染直接滚动居中渐隐高亮；否则利用历史分页向前翻页加载（prepend 渲染）直至定位，高亮动画 2 秒渐隐。✅（实测翻页定位 66 条消息后高亮成功）
6. **历史消息渲染修复**：拆分 `createMessageEl` 构建函数（返回节点不插入）供历史 prepend 渲染复用，修复历史消息无法渲染的遗留问题；实时 `appendMessage` 复用该函数。✅

## 阶段十五：消息已读回执与多端同步（P1）✅

1. Hub 多连接化：连接管理由"用户名->单连接"升级为"用户名->连接集合"（`map[string]map[*Client]bool`），同一账号多设备同时在线互不踢。✅
2. 连接级注销修复竞态：断开按连接对象移除并返回剩余连接数，仅最后一个连接断开才下线（删缓存+广播），彻底修复旧连接断开误删新连接的竞态问题。✅
3. 上线通知去重：仅首个设备上线广播上线通知，多端登录不重复广播；在线列表按用户名去重。✅
4. 推送多端化归口 `sendToUser`：私聊消息（接收方+发送方回显）、已读回执、撤回通知、置顶同步、会话列表、好友列表/申请、文件头/分片、输入状态、AI 回复全部推送用户全部在线连接。✅
5. 已读回执多端同步：读取方回执转发对方全部设备（气泡"已读"多端一致）；读取方全部设备会话列表未读角标同步清零。✅
6. 验证：脚本客户端 8 项链路测试全通过（双连接在线、多端收发、回执转发、未读同步、单设备断开不下线、最后连接才下线、置顶回归）；浏览器三标签页实测 17 项全通过（多端未读角标、已读状态、撤回提示、存活检测、无新增 JS 错误）。✅

## 阶段十六：消息撤回与多端同步（P1）✅

1. 撤回时间窗口配置化：原服务端硬编码 2 分钟改为读取 `config.yaml` 的 `recall_window` 参数（`config.Load()` 默认值兜底 120 秒），修改配置重启即生效，无需改代码。✅
2. 登录响应下发窗口参数：`LOGIN_RESP` 的 content 由纯字符串 "ok" 升级为 JSON（`result` + `recall_window`），前端 `socket.js` 解析存储（兼容旧格式），撤回右键菜单按服务端窗口动态显隐（预留 10 秒网络余量）；同步修复 `chat.js` 登录判定仅认旧格式导致登录误报失败的兼容问题。✅
3. 撤回后会话摘要联动（服务端归口）：撤回最后一条可见消息时，相关会话行摘要更新为"[消息已撤回]"；撤回中间消息时摘要重算为最新可见消息内容，杜绝摘要残留已撤回内容；修复接收方会话行 target 匹配错误与全会话撤回时 `ErrRecordNotFound` 误判两处缺陷，摘要更新后推送双方全部在线连接多端同步。✅
4. 离线补发撤回修正：离线消息补发前以数据库 `recalled` 状态为准校验，离线期间被撤回的消息及其撤回通知不再补发，撤回提示由历史加载按 `recalled` 字段统一渲染。✅
5. 验证：脚本客户端 9 项全通过（LOGIN_RESP 窗口下发=120、双方摘要联动、离线补发过滤、撤回通知过滤）；场景 D 配置生效验证 3 项全通过（`recall_window: 2` 时超窗撤回被拒、窗内撤回成功、证明配置真实读取而非默认值）；浏览器双账号实测通过（登录流程、撤回执行、p10e/p10f 新会话摘要"[消息已撤回]"两端同步、blka/blkb 中间撤回摘要重算同步、控制台无 JS 错误）。✅

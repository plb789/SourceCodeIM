## 3. 协议信令扩展（MsgType 113-120）

在 `protocol/message.go` 中新增 8 个消息类型常量。

### 3.1 新增类型一览

| MsgType | 常量名 | 方向 | 说明 |
|---------|--------|------|------|
| 113 | `MsgTypeOfficialSubList` | 下行 | 登录推送：已关注的服务号列表 + 服务号基本信息（content 为 JSON 数组） |
| 114 | `MsgTypeOfficialSubAction` | 双向 | 上行：关注/取消关注；下行：回执（content: `{action, app_id}`） |
| 115 | `MsgTypeOfficialMenu` | 下行 | 打开服务号会话时拉取底部自定义菜单（content 为菜单树 JSON） |
| 116 | `MsgTypeOfficialMenuClick` | 上行 | 点击底部菜单事件（content: `{app_id, action, value}`）；服务端自动回复 |
| 117 | `MsgTypeOfficialMsg` | 下行 | **核心**：服务号消息推送（服务号→用户；落库 msg_type=117；会话气泡渲染为服务号卡片样式） |
| 118 | `MsgTypeOfficialMsgAck` | 下行 | 审核状态变更通知（审核人/发起方收；content: `{message_id, status, remark}`） |
| 119 | `MsgTypeOfficialSearch` | 双向 | 上行：搜索服务号（content: keyword）；下行：搜索结果列表 JSON |
| 120 | `MsgTypeOfficialCard` | 双向 | 聊天内服务号名片（类似联系人名片 107；content: `{app_id,name,avatar,desc}`；落库 msg_type=120） |

### 3.2 服务号消息信封详解（MsgType=117）

推送消息写入 `im_message.content` 字段，格式：

```json
{
  "official": {
    "app_id": "o_shop001",
    "name": "精选商城",
    "avatar": "/static/upload/xxx.jpg",
    "msg_type": "text",
    "title": "您的订单已发货",
    "content": "快递单号 SF1234567890，预计3天内送达",
    "url": "https://xxx.com/track",
    "template_id": "tpl_order_notify",
    "link_btn": "查看详情"
  }
}
```

- 会话摘要提取 title 前 50 字；title 为空时取 content 首行
- 气泡渲染前先解析 JSON 信封，失败时降级为纯文本

### 3.3 服务号列表推送（MsgType=113）

```json
[
  {
    "app_id": "o_shop001",
    "display_name": "精选商城",
    "avatar": "/static/upload/shop.jpg",
    "description": "优质商品每日上新",
    "subscribe_time": "2026-11-01T10:00:00Z",
```

## 4. 会话集成方案

### 4.1 会话列表中的显示（与好友/群混排）

服务号会话 target = `o_<appid>`，和现有好友 target（用户名）、群聊 target（`g<群ID>`）统一进入 `im_conversation` 表，按 `last_time` 排序。

**`renderConvList()` 改造要点**（前端 `im-client/web/js/chat.js`）：

```js
// 新增判定
function isOfficialTarget(target) { return target && target.startsWith('o_'); }

// 新增渲染逻辑（在现有好友/群渲染分支后追加）
if (isOfficialTarget(cv.target)) {
  var acc = officialMap[cv.target];
  var convName = acc ? acc.display_name : cv.target;
  var avatarFallback = '🏢';  // 服务号专属 emoji 占位
  // 头像、摘要、角标复用现有 DOM 结构，仅 avatar 降级回退不同
  // 未读角标 conv-badge 颜色区分（.conv-badge.official 样式覆盖）
}
```

### 4.2 聊天窗口中的显示

打开服务号会话后：

1. **顶部标题栏**：服务号头像 + 名称（点击进服务号资料页：显示简介、订阅时间、已推送消息历史）
2. **底部菜单面板**：微信同款底部 tab bar，点击 ▼ 展开服务号自定义菜单（最多 3 一级 × 5 二级）
3. **气泡样式**：
   - 服务号推送消息（from_user 以 `o_` 开头）→ 左侧气泡，带 🏢 小图标或特殊底色区分
   - 用户发送的消息（to_user = `o_appid`）→ 右侧气泡（用户发送触发菜单关键词自动回复）
4. **自动回复规则**：用户发送普通文字 → 服务端查 `im_official_menu.value`（click 类型菜单的关键词）→ 命中则自动回复对应模板消息

### 4.3 未读角标

**完全复用现有 `im_conversation.unread` 机制**：

1. 服务号消息发送成功 → 调用 `touchConversation(接收者, 'o_' + appid, 摘要)`
2. 客户端收到 CONV_LIST(18) 帧 → `renderConvList()` 遍历所有 cv.unread → 渲染角标
3. 导航栏总角标 = 所有 cv.unread 之和（含好友、群、服务号）

**无需新增未读计数机制**，服务号会话和普通会话一视同仁。

## 5. API 接入设计（企业内部系统对接）

### 5.1 认证机制

每个服务号独立 `AppID` + `AppSecret`（bcrypt 存储不可逆），两种认证方式二选一：

**方式 A：Access Token（推荐）**

```
POST /api/official/token
Body: { "app_id": "o_shop001", "app_secret": "plaintext_or_bcrypt_compare" }
Response: { "access_token": "eyJ...", "expires_in": 7200 }
```

后续请求 Header：`Authorization: Bearer <access_token>`
Token 存储：Redis `im:official:token:<token>`，TTL 2h

**方式 B：HMAC-SHA256 签名**

```
Header:
  X-Official-AppID: o_shop001
  X-Official-Signature: <hmac>
  X-Official-Timestamp: 1731148800
  X-Official-Nonce: <uuid>

签名算法：
  string_to_sign = `${timestamp}\n${nonce}\n${sha256(body)}`
  signature = hex(HMAC-SHA256(string_to_sign, app_secret_plaintext))
```

校验规则：
- timestamp 与服务端时差 ≤ 5 分钟（防重放）
- nonce 在 Redis 黑名单（TTL=10min）→ 拒绝
- body SHA256 匹配（防篡改）
- AppSecret 明文 bcrypt 比对（服务端启动时缓存明文或走 bcrypt.CompareHashAndPassword）

### 5.2 API 端点一览

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/official/token` | 获取 Access Token（无需认证） |
| POST | `/api/official/notify` | **核心推送**：单推 / 多推 / 群发 |
| POST | `/api/official/batch-notify` | 批量推送（一次最多 1000 用户，异步队列） |
| POST | `/api/official/template/render` | 渲染模板（template_id + 变量 → 渲染后 content） |
| POST | `/api/official/menu/set` | 更新自定义菜单 |
| GET  | `/api/official/menu/get` | 查询当前菜单 |
| GET  | `/api/official/stats` | 推送统计（今日/近7天推送量、阅读量） |
| POST | `/api/official/callback` | 自定义事件回调接收（可选，企业系统在菜单 value 里配回调 URL 时触发） |

### 5.3 核心推送接口详细设计

```
POST /api/official/notify

Request:
{
  "app_id": "o_shop001",
  "type": "single",               // single / batch / broadcast
  "recipients": ["user1", "user2"],  // single/batch 必填；broadcast 忽略
  "template_id": "tpl_order",    // 可选：模板消息优先
  "template_data": {              // 模板变量
    "order_no": "SF123456",
    "status": "已发货"
  },
  "title": "您的订单已发货",        // 非模板时
  "content": "快递单号...",        // 非模板时
  "url": "https://xxx.com",       // 可选：点击跳转
  "link_btn": "查看详情",          // 可选：按钮文字
  "need_audit": false             // 可选：覆盖服务号默认审核设置
}

Response (同步发送场景):
{
  "code": 0,
  "message": "ok",
  "sent": 1,
  "msg_id": 12345
}

Response (批量/群发异步场景):
{
  "code": 0,
  "message": "ok",
  "task_id": "task_abc123",
  "queue": 844          // 进入队列剩余数（已发送+入队=recipients.length）
}
```

### 5.4 推送完整链路

```
企业系统 ──POST /api/official/notify──→
    │
    ▼
[1] 鉴权（Token 或 HMAC 签名校验）
    │
    ▼
[2] 服务号归属校验（API 只能操作自己 app_id 的服务号）
    │
    ▼
[3] 频率限制（Redis 双限：服务级 + 用户级）
    │
    ▼
[4] 模板渲染（如有 template_id → 查表 + template_data 替换）
    │
    ▼
[5] 关键词/敏感词过滤（命中 need_audit=true 强制转审核）
    │
    ▼
[6] 入库 official_message（audit_status 按 need_audit 决定）
    │
    ├── need_audit=true ──→ 写入 official_audit + 向审核人推 118 信令
    │
    └── need_audit=false ──→ 直接进入发送队列
                                   │
                                   ▼
                            [7] 异步 Worker Pool（goroutine）
                                   │
                                   ▼
                            对每个 recipient:
                            a) 写 im_message（msg_type=117, from_user='o_appid'）
                            b) touchConversation(接收者, 'o_appid')
                            c) 推 WebSocket 帧给在线用户
                            d) 离线用户入 queueOffline
                                   │
                                   ▼
                            [8] 更新 official_message 统计（sent_count/fail_count）
```

## 6. 审核流程设计

### 6.1 审核人配置

| 审核人类型 | 配置位置 | 权限 |
|-----------|---------|------|
| 全局管理员 | `im_user.role=1` | 审核所有服务号消息 |
| 服务号归属商户 | `im_official_account.owner` | 审核自己服务号的消息 |
| 授权审核人 | `im_official_account.auditors`（扩展 JSON 字段） | 审核指定服务号的消息 |

### 6.2 审核状态机

```
                  ┌──────────────────────────────────────┐
                  │                                      │
     [创建/触发] ──┴──→  pending ──APPROVE──→ approved ──→ [进入发送队列]
                            │
                            └──REJECT──→ rejected ──→ [通知发起人]
```

审核驳回必须带 reason（audit_remark）。

### 6.3 三端审核入口

| 端 | 入口位置 | 交互 |
|----|---------|------|
| PC 端 | 左侧导航栏「审核待办」图标（红点角标） | 列表 → 详情 → 通过/驳回 |
| Web 端 | 同上（nav-chat-badge 旁追加 nav-audit-badge） | 同 PC 端 |
| APP 端 | 我的 → 审核中心 | 同 PC 端 |

### 6.4 审核界面原型

```
┌─────────────────────────────────────────────────┐
│  📝 审核中心  待办(3)  已通过(5)  已驳回(1)          │
├─────────────────────────────────────────────────┤
│  🏢 精选商城                        need_audit=✅ │
│  📋 您的订单已发货                                 │
│  📄 快递单号 SF1234567890，预计3天内送达            │
│  👥 接收者：156 用户                                │
│  ⏰ 2026-11-09 14:30:22  发起：系统 API              │
│                                                   │
│  [✅ 通过发送]   [❌ 驳回（填写原因）]               │
├─────────────────────────────────────────────────┤
│  🏢 会员俱乐部  ...                                 │
└─────────────────────────────────────────────────┘
```

## 7. 安全机制

### 7.1 API 签名校验（防篡改、防重放）

| 校验项 | 规则 | Redis Key |
|--------|------|-----------|
| 时间戳 | 与服务端时差 ≤ 5 分钟 | — |
| Nonce | 已在黑名单 → 拒绝 | `im:official:nonce:<nonce>`, TTL=10min |
| Body Hash | SHA256 匹配请求体 | — |
| AppSecret | bcrypt 哈希比对 | — |

### 7.2 频率限制（4 层）

| 层级 | 限制 | Redis Key |
|------|------|-----------|
| 单 API | 60 次/分钟 | `im:official:ratelimit:<appid>:api` |
| 单服务号日推送 | official_account.max_per_day | `im:official:daily:<appid>` |
| 全局推送 | config.official.global_qps | `im:official:global` |
| 单用户接收 | 5 条/小时（防骚扰） | `im:official:userlimit:<username>` |

### 7.3 内容安全

| 规则 | 处理方式 |
|------|---------|
| 关键词命中敏感词库 | API 拦截 + 强制转审核 |
| URL 白名单校验 | 非白名单自动转审核 |
| 单条消息长度上限 | 5000 字，超限拒绝 |
| 订阅关系校验 | 只能推送给 `im_official_subscribe` 已关注用户 |

### 7.4 归属隔离

所有 API 和后台操作均进行 SQL 层归属校验：
- 商户只能操作 `owner = 自己 username` 的服务号
- API 签名只能操作对应 AppID 的服务号（SQL 层 `WHERE app_id = ?`）

## 8. Redis 缓存设计

| Key 模式 | 用途 | TTL |
|---------|------|-----|
| `im:official:token:<token>` | Access Token 存储 | 2h |
| `im:official:ratelimit:<appid>:api` | API 频率限制计数器 | 1min（滑动窗口） |
| `im:official:daily:<appid>` | 服务号每日推送计数 | 当日 23:59:59 过期 |

| `im:official:userlimit:<username>` | 单用户接收频率计数 | 1h |
| `im:official:cache:accounts` | 服务号列表缓存（Hash Set） | 5min（变更时主动失效） |
| `im:official:subscribe:<appid>:<username>` | 用户订阅状态缓存 | 会话级（变更时失效） |
| `im:official:audit:pending` | 审核待办队列（Sorted Set） | 审核完成后移除 |
| `im:official:batch:<task_id>` | 批量推送任务状态 | 任务完成后 1h |

## 12. 测试重点

### 12.1 性能压测

| 场景 | 指标 |
|------|------|
| 10 万订阅者群发 | 端到端延迟 ≤ 5s（协程池异步 fan-out） |
| 100 并发 API 推送 | QPS ≥ 50（无 Redis 阻塞） |
| 会话列表 unread 聚合 | 5 万会话登录加载 ≤ 1s |

### 12.2 稳定性

| 场景 | 预期 |
|------|------|
| 服务端重启 | Redis 计数器恢复，在途消息自动补偿 |
| DB 短暂不可用 | 推送进入离线队列，DB 恢复后自动补发 |
| 群发期间新增订阅者 | 本次群发自动包含新增（Redis ZSET 动态扩展） |

### 12.3 安全

| 场景 | 预期 |
|------|------|
| 5 分钟过期重放请求 | 签名校验失败拒绝 |
| 相同 nonce 二次请求 | 被 Redis 黑名单拦截 |
| 跨 app_id 越权推送 | SQL 层 owner 校验 404 |
| 敏感词 API 推送 | 自动转审核，审核人收到待办 |

### 12.4 多端一致性

| 场景 | 预期 |
|------|------|
| PC 审核通过 → APP | 服务号会话角标实时消失 |
| Web 关注服务号 → PC | 服务号会话列表即时出现 |
| APP 查看审核待办 → Web | 审核人看到相同待办队列 |

### 12.5 零侵入保证

- 不改动现有 MsgType 1-112 的 switch case
- 不改动现有 im_message、im_conversation、im_friend 等核心表结构
- 新增会话 target 前缀 `o_` 与现有 `g` 不冲突，前端只加判定分支
